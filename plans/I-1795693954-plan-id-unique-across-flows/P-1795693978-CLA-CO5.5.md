### Strategy Rationale

**Root cause (verified while planning).** `planner.main` sets `plan_seq = int(time.time())`. It then calls
`taken_plan_ids(repo, repo_dir, intent_branch_prefix)`, which only collects (a) `plans/<prefix>/P-*.md`, (b)
`refs/heads|remotes/origin/<prefix>/P-*`, and (c) ledger rows whose `intent_branch` equals the prefix. Finally it calls
`build_plan_id(...)` in `ledger/rows.py`, a pure `distinct_stage_id(stage_id(...), taken)`. Two flows with different
prefixes in the same second therefore get the identical `P-<sec>-<TICKER>-<CODE>`. A scan of `plans.jsonl` on this
branch shows 6 duplicated plan ids: `P-1795154100-CLA-CO5.5`, `P-1795167432-CLA-CO5.5`, `P-1795184234-CLA-CO5.5`,
`P-1795246947-CLA-CO5.5`, `P-1795567904-ANA-G4N` and `P-1795584464-CLA-CO5.5`. These are historical, and the ledger is
immutable, so this plan does not touch them.

**Why `build_stage_disambiguator` is rejected.** It returns 8 hex characters. In `naming.parse_stage_id`, an id like
`P-<sec>-<8hex>-...` matches `_LEGACY_DISAMBIGUATOR` and is classified as `GENERATION_LEGACY_HEX`, so
`is_new_generation` returns false and ticker/model-code parsing (used by calibration and agent attribution) is lost.
Appending it as a trailing field would make `_parse_ticker_tail` ignore it as a non-digit variant. Ids would still
differ, but the result would be a fourth, undocumented shape. Neither keeps "the plan id format that existing parsers
accept".

**Chosen design: extend the taken set to every flow, plus an atomic claim.**

1. Build a repository-wide taken set from:
   - every `plan_id` in `plans.jsonl` merged with its pending fragments (`ledger.read_merged_rows` already merges
     `pending/plans/*.jsonl`);
   - every `P-*` path segment of every ref under `refs/heads/`, `refs/remotes/origin/` and the new claim namespace;
   - every `plans/**/P-*.md` file name except `_calibration` files.

   The result is unioned with the existing per-prefix `taken_plan_ids`.

2. Mint with the unchanged `build_plan_id(plan_seq, prefix, agent, model, taken=...)`. The result is the existing format
   `P-<sec>-<TICKER>-<CODE>` or its `-2`..`-9` same-second variant. `parse_stage_id` already parses both,
   `flow/in_flight.py`'s `P-\d+-[^/]+` matches both, and `build_plan_id` still calls `ensure_stage_segment_fits`.
3. Close the race window in which two flows scan before either has created a branch. The mint claims the id atomically
   with a create-only `git update-ref refs/holon/plan-ids/<plan_id> <HEAD> ""` (empty old value = must not exist). Git
   runs this as a locked ref transaction, so exactly one of two concurrent claimants in the same repository wins. A
   loser adds the id to its taken set and re-mints the next variant. This is what makes "two Stage 2 runs in the same
   second with different intent slugs mint different plan ids" hold even when neither flow has pushed or branched yet.
   All flow worktrees of one host clone share refs; Step 1 confirms this. Flows on other clones are covered once their
   `P-*` branches or ledger rows are fetched, and that is the stated scope ("anywhere in the repository").

`build_plan_id`, `build_stage_disambiguator` and `ledger/rows.py` stay unchanged.
`tests/test_unique_stage_ids.py::test_same_second_twin_intents_get_distinct_plan_files` asserts that the pure
`build_plan_id` returns the same id for twin prefixes, and `rows.py` has zero budget headroom.

**Why `taken_plan_ids` is not widened in place.** `tests/test_taken_ids.py` asserts that another intent's ledger row
(`P-9-CLA-CS5.5` for `I-1-b`) is not in `taken_plan_ids(..., "I-1-a/_")`, and that test must keep passing. The global
scan is therefore a new function in the new module, unioned with the unchanged per-prefix function.

**Why the root intent id is left alone.** `I-<sec>-<slug>` already differs between flows by slug. Adding a disambiguator
would change the shape that `fit_root_intent_branch`, `plan_paths`, `root_intent_id` and the `I-\d+-\S*` regex in
`flow/in_flight.py` expect. The intent says to leave it in that case, so `intent_creator.py` is not touched.

**Budget handling.** `planner.py` has 0 lines of headroom. The planner edit is line-neutral or negative: it swaps an
import, deletes the `taken_ids = ...` line and replaces the `build_plan_id(...)` call. All new logic goes into
`entrypoint/plan_id_unique.py`, about 70 lines against the 400 default.

**Aggregation.** `entropy_pred` is the sum of the step entropies, `0.4 + 1.2 + 0.8 + 0.8 + 0.6 = 3.8`. `cost_pred` is
the sum of the step costs, `1.5 + 3.5 + 2.0 + 3.0 + 2.0 = 12.0`. `p_success_pred` is a qualitative judgement. A naive
product `0.95 * 0.88 * 0.90 * 0.88 * 0.85 = 0.56` understates it because steps 2 to 5 are correlated and repaired in the
same execution loop, so the bottleneck (Step 2, the mint module, 0.88) is discounted to 0.80 for the planner-harness and
budget risks. Impact is the maximum step impact (Step 2, 75) plus 5 for removing a standing ledger-integrity defect,
so 80. Learning value is the sum of the small per-step values, 4.0.
`EV = P(success) * Impact + mu * LearningValue - lambda * Delta_S_intent - Cost` with `mu = 0.5`, `lambda = 0.3`:
`EV = 0.80 * 80.0 + 0.5 * 4.0 - 0.3 * 3.8 - 12.0 = 64.0 + 2.0 - 1.14 - 12.0 = 52.86`.
