## Plan Description & Strategy

Re-implement layered dotenv configuration with the same module design the previous execution verified, inside a touch
set that names every file it changes.

- **Core loader (Step 1):** `config_env.py` is the public entry point (`resolve_layered_config`, the per-invocation
  holder and `apply_to_environ`). `config_env_parse.py` holds the strict `KEY=VALUE` parser (comments, blank lines,
  optional single or double quotes, no expansion, nothing executed). `config_env_keys.py` holds the documented key table
  (name, default, secret flag, description) and the allow-list of secret mappings. `config_env_model.py` holds the
  frozen dataclasses (`LayerName`, `EffectiveSetting` with value, source layer and shadowed layers, `LayeredConfig`,
  warnings).
- **Empty-value decision:** `KEY=` in a layer is treated as not set in that layer, so the broader layer (or built-in
  default) supplies the value. Rationale: an empty line copied from `.env.example` must never silently blank a user-wide
  setting. The layer is still recorded as shadowed-empty in the report so the operator can see it. This is documented in
  the module docstring and the README.
- **Secrets (Step 2):** `config_env_secrets.py` maps `*_FILE` keys (for example `HOLON_AGENT_OAUTH_TOKEN_FILE`) to their
  secret values, checks file permissions (group- or world-readable warnings at every layer, including the `.env` files)
  and warns when a secret-bearing project `.env` is tracked by git. `claude_credential.py` prefers
  `HOLON_AGENT_OAUTH_TOKEN`. `role_dispatcher.sh` maps `HOLON_AGENT_OAUTH_TOKEN` to `CLAUDE_CODE_OAUTH_TOKEN`.
- **Inheritance (Step 3):** `cli.main` resolves the configuration once and applies it to the process environment,
  marking it with `HOLON_CONFIG_RESOLVED=1` so nested invocations do not re-resolve. `launcher/container_env.py`
  forwards every `HOLON_*` key only through the 0600 env-file. `preflight.py` and `agent_runner.py` treat the new secret
  as sensitive and the padded blob path as retired for this purpose.
- **Reporting and scaffolding (Step 4):** `config_env_report.py` builds the doctor rows (text and JSON) with secrets
  shown only as `set (layer)`; `cli/commands/doctor.py` calls it. `scaffold.py` (behind `cli/commands/init.py`) writes a
  commented `.env.example` and adds `.env` to `.gitignore`.
- **Docs (Step 5)** and **tests (Step 6)**, then **verification (Step 7)** including a touch-set self-check.

### Intent & Git Integration

- **Step Intent:** Provide a pure, side-effect-free resolver that parses the user-wide and project `.env` files and
  resolves each `HOLON_*` key independently with provenance.
- **Git branch:** I-1795409213-layered-env-config-v2/P-1795410717-CLA-CO5.5/E-{timestamp}-CLA-CO5.5/\_
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. `config_env_model.py`: frozen dataclasses for the layer enum (default, user, project, environment, cli, from broadest
   to most specific), a parsed entry (key, value, line number), a warning (key name and message, never the value), an
   effective setting (key, value, source layer, tuple of shadowed layers, secret flag) and the resolved configuration.
2. `config_env_parse.py`: a line parser accepting `KEY=VALUE`, an optional `export ` prefix is rejected (strict subset),
   full-line `#` comments, blank lines, and values wrapped in matching single or double quotes (quotes stripped, inner
   text kept literally, no escapes, no `$` expansion). Malformed lines produce a warning naming the line number and key
   only. Never call `os.path.expandvars`, `shlex` evaluation or any subprocess.
3. `config_env_keys.py`: the documented key table (name, built-in default, secret flag, one-line description) and the
   explicit secret allow-list (`HOLON_AGENT_OAUTH_TOKEN_FILE` mapping to `HOLON_AGENT_OAUTH_TOKEN`, and any existing
   documented secret such as `GITHUB_TOKEN` only if the README already documents it). Keys that are neither `HOLON_*`
   nor allow-listed are rejected with a warning that names the key and not the value.
4. `config_env.py`: `user_config_path()` (`~/.holon/.env`, overridable for tests through a module-level holder, not an
   environment variable), `project_config_path(repo_root)`, and
   `resolve_layered_config(repo_root, environ, cli_overrides)` that walks layers from most specific to broadest per key;
   the first layer with a non-empty value wins and every other layer defining the key is recorded as shadowed. An empty
   value (`KEY=`) means "not set in this layer" and falls back to the broader layer; document this in the module
   docstring. Add `apply_to_environ()` that writes effective values only for keys absent from the process environment
   and sets the `HOLON_CONFIG_RESOLVED=1` marker.
5. Keep each function within ruff complexity limits by delegating per-layer and per-key work to small helpers.
6. Optionally consult the previous execution ref read-only (`git show <ref>:<path>`) for these four files.
