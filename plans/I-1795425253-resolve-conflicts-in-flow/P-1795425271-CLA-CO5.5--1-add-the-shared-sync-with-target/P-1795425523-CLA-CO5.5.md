## Plan Description & Strategy

Today four per-stage variants handle a target-branch conflict and only ledger files are resolved
(`flow/stage_conflicts.py`, `flow/stage_conflict_resolution.py`, `flow/review/conflict_gate.py`,
`flow/stages/sync_conflict.py`). This child adds the single shared routine the sibling children will wire in, built
bottom-up in focused new modules so each layer is testable with local git fixtures and no agent:

1. **Probe** (`flow/target_probe.py`): fetch the target, resolve its SHA, and run
   `git merge-tree --write-tree --name-only -z` only when the (head SHA, target SHA) pair differs from the cached last
   probe. Replaces the heuristic word-scraping `_merge_tree_conflict_paths`.
2. **Mechanical conflict classes** (`flow/conflict_classes.py` classifier, `flow/conflict_classes_resolve.py`
   resolvers): `LEDGER` (append-merge via existing `ledger_reconcile` helpers), `KB_TIMESTAMP_ONLY` (keep the target
   copy), `DELETE_VS_TOUCH` (keep the deletion), `APPENDED_LIST` (ordered union), otherwise `CODE`. Every resolver
   verifies its own output and downgrades to `CODE` on any doubt.
3. **Routine** (`flow/target_sync.py`, `flow/target_sync_record.py`): `sync_with_target(...)` fetches, probes, merges
   with a normal `--no-ff` merge commit (never rebase, never force-push), resolves mechanical paths, hands `CODE` paths
   to an injected `code_resolver` (default fails closed by aborting the merge), verifies, commits, pushes via
   `host_remote.push_commit`, and appends exactly one `target_sync` row to `executions.jsonl` per sync that merged or
   blocked.
4. **Resume adoption** (`flow/target_sync_resume.py`): a resume that finds `MERGE_HEAD` in the flow worktree finishes
   the merge when it is the current target and fully resolvable mechanically, otherwise aborts it and redoes the sync.
   Hooked into `flow/resume_guard.py` so the budget-capped `pipeline.py` (430 of 431 lines) is not touched.
5. **Thin wrapper**: `check_and_resolve_stage_conflicts` keeps its signature and return dict for the four entrypoint
   callers but delegates classification and resolution to `conflict_classes`, so container-side callers gain the new
   mechanical classes without ever spawning an agent.
6. **Verification**: targeted tests, then `uv run task test`, `uv run task lint`, `uv run task lint-docs` once each, in
   the foreground.

All new modules stay under the 200-line default budget; `target_sync.py` is split into `target_sync_*.py` helpers if it
approaches the limit. The module budget file is never edited. No module in `entrypoint/` is imported by the new flow
modules.

## Step 1: Add the SHA-keyed `git merge-tree` target probe

- **Sub‑intent recommendation:** NO
- **Reasoning:** One small pure-git module with local-fixture tests; low risk and the base of every later step, so it
  stays in this plan.
- **Step Type:** IMPLEMENTATION
- **Exploration level:** BALANCED

- **Hypothesis being tested:** With git 2.47 in the image, `git merge-tree --write-tree --name-only -z <head> <target>`
  returns exact conflicted paths (exit status 1 on conflict) and, combined with a cache keyed on (head SHA, target SHA),
  an unchanged target costs one fetch plus two `rev-parse` calls, well under one second on this repository.
- **Learning target:** Probe wall time for unchanged, changed-clean and changed-conflicting targets; whether the
  structured output removes the false paths the current word parser reports.
- **Maximum acceptable cost for this learning:** One serial timing measurement (three scenarios, one run each, serial
  because single-probe latency is itself the measurement), reported in the execution record. If the changed-target probe
  exceeds two seconds, record it so sibling child 3 falls back to a SHA-only check at turn boundaries.

### Implementation Details (No code blocks, only logic/steps)

1. New `flow/target_probe.py` with a frozen dataclass `TargetProbe` (`target_ref`, `target_sha`, `head_sha`,
   `merge_base`, `moved`, `conflicted_paths` as a tuple, `cached`).
2. `probe_target(worktree, target_branch, last_probe=None, *, fetch=True)`: when `fetch`, call

4. Otherwise run `git merge-tree --write-tree --name-only -z HEAD origin/<target>`; exit 0 means clean, exit 1 means
   conflicts, any other exit raises `TargetProbeError`. Parse the NUL-separated output: first field is the tree OID, the
   following fields up to the first empty field are conflicted paths; informational messages after it are ignored. Keep

5. Keep the module under 120 lines; full docstrings and type annotations per `holon-config/world/ruleset.md`.
6. Tests in `tests/flow/test_target_probe.py` with temporary local repositories and a bare `origin` (reuse helpers in

   merge-tree call (assert via a `run_git` spy); cache hit returns `cached=True`; clean divergent target returns empty
   paths; conflicting target returns the exact path list, including a path with spaces; a file name containing a dot in
   a commit message never appears as a false path; a broken remote raises `TargetProbeError`.
7. Measurement: the executor times the three scenarios (unchanged, changed-clean, changed-conflicting) once, serially,
   with `time.perf_counter` against the test fixtures in a throwaway shell session (no permanent timing test, no
   repeated runs) and records the three numbers in the execution record.

### Implementation Details (No code blocks, only logic/steps)

1. New `flow/conflict_classes.py`: `ConflictClass` enum (`LEDGER`, `KB_TIMESTAMP_ONLY`, `DELETE_VS_TOUCH`,
   `APPENDED_LIST`, `CODE`) and `classify_path(worktree, path)` reading the index stages 1/2/3 with `git ls-files -u -z`
   and `git show :N:<path>` during an in-progress merge.
   - `LEDGER`: `holon-knowledge/ledger/*.jsonl` (reuse the existing `_is_ledger_path` rule, moved here).
   - `KB_TIMESTAMP_ONLY`: JSON under `holon-knowledge/kb/` or `holon-knowledge/wisdom/` where both sides parse and are
     equal after removing an explicit allow-list of timestamp keys (`created_at`, `updated_at`, `last_seen`,
     `timestamp`, at any nesting level). Any other differing key, a parse failure or a missing side is `CODE`.
   - `DELETE_VS_TOUCH`: stage 3 (target) absent, stages 1 and 2 present, and the branch-side change from the merge base
     is mechanical only: identical after normalising whitespace and sorting the contiguous import block (Python), or
     identical after whitespace normalisation (other text). Otherwise `CODE`.
   - `APPENDED_LIST`: a Python file where the only differences of both sides from the base are added entries inside the
     same `__all__` list or the same lazy-export mapping literal (checked with `ast`: all other top-level nodes equal,
     and both sides' list/dict is the base list/dict plus appended elements).
   - `classify_conflicts(worktree, paths)` returns an ordered list of (path, class).
2. New `flow/conflict_classes_resolve.py`, one resolver per class, each returning True only after verifying its result:
   - `LEDGER`: write the append-only union via `ledger_reconcile.resolve_append_only_conflict` / `reconcile_ledger_file`
     with the target side as prefix (target history first, branch-only rows appended), then `git add`; verify no
     conflict markers and every original row from both sides present byte-identically.
   - `KB_TIMESTAMP_ONLY`: `git checkout --theirs` (target copy) then `git add`.
   - `DELETE_VS_TOUCH`: `git rm` the path.
   - `APPENDED_LIST`: rebuild the file as the target side with branch-only entries appended to the list/mapping in
     branch order, without duplicates; re-parse with `ast` and compare all non-list nodes to the target side; `git add`.
   - Any verification failure restores the conflicted state for that path (`git checkout -m <path>`) and returns False,
     downgrading the path to `CODE`.
   - `resolve_mechanical(worktree, classified)` returns (resolved list with class, remaining `CODE` paths).
3. If `ledger_reconcile.py` needs a small public helper for target-prefix union it is added there (file at 99 of 224
   lines).
4. Tests in `tests/flow/test_conflict_classes.py`, each building a real conflicting merge in a temporary repository:
   ledger rows from both sides kept with earlier rows byte-identical; KB entry differing only in `updated_at` keeps the
   target copy; KB entry with a differing `title` is `CODE`; target-deleted file with whitespace-only branch edit is
   deleted; target-deleted file with a real branch edit is `CODE`; both sides appending to `__all__` gives an ordered

- **Git branch:** same execution branch as Step 1
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. New `flow/target_sync.py`:
   - `SyncBoundary` enum: `FLOW_START`, `STAGE_START`, `STAGE_END`, `TURN`, `PUSH`, `CALIBRATE`, `FLOW_END`.
   - Frozen `SyncResult`: `status` (`unchanged`, `deferred`, `merged`, `blocked`), `head_before`, `head_after`,
     `target_sha`, `resolutions` (path, class, how), `code_paths`, `resolver_tier`, `attempts`, `test_result`,
     `changed_paths` (for the next turn's prompt), `ledger_row_id`, `probe` (for caching by the caller).
   - `CodeResolver` protocol: callable taking (worktree, code paths, probe) and returning a resolution outcome with
     tier, attempts and test result. Default `fail_closed_code_resolver` returns "unresolved".
   - `sync_with_target(worktree, *, branch, target_branch, stage, boundary, ledger_path, execution_id, last_probe=None, code_resolver=fail_closed_code_resolver)`
     (or a small `SyncRequest` dataclass to stay within `PLR0913 <= 5`). Decision: probe; not moved means `unchanged`
     (no merge, no push, no row); moved without conflict at `TURN` means `deferred` (no merge); otherwise merge.
2. `flow/target_sync_merge.py`: `merge_target(worktree, target_ref)` runs `git merge --no-ff --no-edit <target_ref>`
   inside try/finally that runs `git merge --abort` on any unhandled error; collects unmerged paths
   (`git diff --name-only --diff-filter=U -z`); calls `resolve_mechanical`; passes remaining `CODE` paths to the
   injected resolver; on unresolved paths aborts the merge and returns `blocked`; on success verifies no unmerged paths
   and no conflict markers in changed files, commits with a message naming target SHA and classes, and pushes with
   `host_remote.push_commit(worktree, "HEAD", branch)` (plain push, never `--force`). `changed_paths` is
   `git diff --name-only head_before..HEAD`.
3. New `flow/target_sync_record.py`:
   `append_sync_row(ledger_path, result, *, stage, boundary, execution_id, supersedes)` builds an `ActionRecord`
   (`action: target_sync`, category `git`) with stage, boundary, target SHA, conflicted paths, class and resolution per
   path, resolver tier, attempts, test result and `supersedes`, and appends it with `ledger.append_action_record` (the
   only writer; no earlier row is read for rewriting). `supersedes` is the id of the latest `sync_conflict` row for this
   branch found by a read-only scan with `ledger.query` when the sync resolved it, else empty. Exactly one row per
   `merged` or `blocked` sync; none for `unchanged` or `deferred`.
4. Ordering: for a `merged` sync the row is appended after resolution and before the merge commit, so it is part of the
   merge commit and pushed with it. For a `blocked` sync the merge is aborted first and the row is then appended to the
   clean worktree (committed with the flow's next normal commit). A push failure after commit leaves the local merge
   commit for the resume path and returns `blocked` with the push error; no second row is written for it.
5. Tests in `tests/flow/test_target_sync.py` with a bare origin and a flow worktree: unchanged target makes no merge, no
   push and no row; a non-conflicting target change at `TURN` leaves `HEAD` unchanged; the same change at `STAGE_START`
   produces a merge commit with two parents and is pushed; a ledger-only conflict merges with one new row and earlier
   rows byte-identical; a `CODE` conflict with the default resolver returns `blocked`, leaves no `MERGE_HEAD`, pushes
   nothing and appends one blocked row; an injected fake resolver resolving the file returns `merged` with its tier;
   recorded git calls (spy on `run_git`) never contain `rebase` or `--force`; `holon-config/hygiene/module_budgets.json`
   is never written.
6. Run `uv run pytest apps/sandbox-executor/tests/flow/test_target_sync.py` in the foreground.

### Strategy Rationale

The intent is accepted as is: it is the first child of the parent plan's split, its predicted entropy (11.5) fits the
15.0 budget, and every part is testable with local git fixtures and no live agent. It runs as one plan with no
sub-intent list; splitting further (this intent is at depth 1 of a maximum of 2) would add review overhead for modules
that only make sense together. The order is bottom-up: probe and classifier (independent), then the routine composing
them, then resume adoption and the wrapper that reuse it. Keeping the code resolver injected with a fail-closed default
lets this child merge safely before the real resolver role (sibling child 2) exists.

Overall metrics: entropy is the sum of step entropies (`2.0 + 2.5 + 3.0 + 1.5 + 1.5 + 1.0 = 11.5`); cost is the sum of
step costs (`3 + 4 + 5 + 2 + 2 + 2 = 18`); impact is the sum of step impacts (`12 + 15 + 18 + 6 + 6 + 3 = 60`); learning
value is a qualitative `6.0` dominated by the Step 1 probe measurement plus the classifier's first exactness data.
p_success is a bottleneck estimate over Steps 1-3 (`0.85 * 0.75 * 0.75 = 0.48` raw), raised to `0.72` because the steps
are positively correlated, each has a fail-closed fallback (drop a class to `CODE`, fall back to messages parsing) and
the executor iterates on tests within the step. Then
`EV = 0.72 * 60.0 + 0.5 * 6.0 - 0.3 * 11.5 - 18.0 = 43.2 + 3.0 - 3.45 - 18.0 = 24.75`. Bottleneck steps: 1, 2 and 3;
Steps 2 and 3 carry the lowest p_success (0.75). Strong assumption: the image git (2.47.3 here) supports
`merge-tree --write-tree --name-only -z`, which Step 1 verifies first.
