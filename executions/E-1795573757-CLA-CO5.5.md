All three runs passed (2 of 2). Decision: 4 workers per child improves the outer wall time by
`1 - 149.1 / 188.7 = 21.0 %` over `auto`, above the 10 % threshold, so it is adopted. The plan's suggested formula
`max(1, os.cpu_count() // 2)` assumed oversubscription and would give 2 on CI, so it was not used. Instead `child_env()`
sets `PYTEST_XDIST_AUTO_NUM_WORKERS` to `os.process_cpu_count()` (honours CPU affinity) when the stress test runs in an
outer xdist worker and the caller has not set the variable; the reason is documented in the `stress_support.py`
docstring. A new unit test pins the behaviour (and the caller override). Learning: the child suite is IO- and
subprocess-bound (`sys` close to `user`), so 8 workers on 4 vCPUs beat 4; xdist `auto` under-uses the runner because it
counts physical cores. The same may hold for the unit job itself, a candidate follow-up.
`uv run pytest test_stress_support.py -n auto --dist worksteal`: 13 passed in 3.90 s.

Capping the workers per child is about 14 % slower, so it is not applied. One child alone with 4 workers takes 74 s on
the same 4 CPUs, so two concurrent children (`141 s`) are already at the CPU floor (`2 * 74 = 148 s`). No single test
dominates (`--durations`: the slowest call is 3.7 s of a 7,692-test run), and caching bytecode outside the workspace

substantial further cut needs less work per child (preference 3) under a mechanically checked selection rule with its
own canary-trip proof, as Step 6 proposes for a follow-up.

How much preference (3) could remove (review resolver, iteration 2): one unit run with `--durations=0`, test time summed
per file (279 files, `681 s` of test time in total). A selection rule that is safe for both guarantees may drop only
tests that cannot spawn a process or touch HOME, the workspace or the filesystem. A test file's own text is the most
such a rule can check by machine; a tested function in `src` can still resolve `get_workspace_dir()`, so even this rule
is optimistic. Only 18 files mention none of `subprocess`, `Popen`, `os.system`, `environ`, `HOME`, `home(`,
`expanduser`, `tmp_path`, `tempfile`, `rmtree`, `unlink`, `remove`, `open(`, `write_`, `mkdir`, `cleanup`, `workspace`,
`git`, `chdir`, `monkeypatch` or `patch`. Together they take `15.4 s`, so dropping them cuts about `2.3 %` of each
child's work. That is not a substantial cut, and it would cost a selection rule that could miss a test. So preference
(3) cannot give the substantial cut either: the child's work is the hazardous tests themselves. The measured cut
(`7.6 %` against the Step 1 median, `15.5 %` against same-day `main`) is the most these preferences give on one 4-vCPU
runner. To go further, the maintainer would need to re-scope the intent, for example by running the two children as
separate jobs or on a larger runner.
