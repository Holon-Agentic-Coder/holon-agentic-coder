Intended semantics changes:

1. Resume overwrites `token_reduce` and `proxy_attach` from the current run. A checkpoint with `token_reduce=True` (for
   example one written by the earlier image-probe bug) no longer spawns a sidecar on resume; a resumed run must repeat
   `--token-reduce` to keep one, and `HOLON_TOKEN_REDUCE=0` now wins on resume too. A checkpointed `mitm_web=True` is
   still only ever set, never cleared, as before (unchanged, outside this intent).
2. On the flow path a detected running proxy now yields `proxy_attach=True` with `token_reduce=False` (it used to yield
   `token_reduce=True`, which the launcher turned into a sidecar spawn).

## Sidecar connectivity root cause

**Verdict: HYPOTHESIS** (not confirmed). The executor has no Docker CLI or daemon, so the manual reproduction was
skipped and no code path proves a single cause.

Static evidence:

- The role container receives exactly one `--network`, the sidecar's `holon-net-*` (`launcher/sidecar.py:135`);
  `build_network_isolation_args` adds none (`launcher/mounts.py:49`, `network_mode` is never passed).
- The proxy URL is `http://holon-proxy-<pid>-<uuid>:8080` (`sidecar._sidecar_mounts_and_envs`), added after the
  forwarded env. Host `HTTP(S)_PROXY` is not forwarded (`container_env._host_env` forwards only `HOLON_*` and
  `GITHUB_TOKEN`), and `HOLON_PROXY_URL` is not read by curl, git or uv, so a forwarded value cannot shadow it.
- Teardown runs only in `ContainerLaunch._release` after the role container exits, and in the `flow/pipeline.py`
  `finally`; stages run serially, so no other launch tears the sidecar down mid-run.
- The host readiness probe goes through the loopback publish (`-p 127.0.0.1::8080`, `sidecar_plan.py:133`) and sends a
  real HTTP proxy request (`proxy_readiness.wait_for_proxy`), so mitmdump was listening on the container interface.
- curl's "Failed to connect to <host> port 8080" (not "Could not resolve proxy") means Docker's embedded DNS resolved
  the sidecar name, so the sidecar was attached to the network at lookup time.

Ranked hypotheses:

1. H4 (most likely): on Docker Desktop (the reported host runs a linuxkit kernel) the loopback publish path works while
   container-to-container traffic on the freshly created user-defined bridge is refused or not yet routable, for example
   under Enhanced Container Isolation or an inter-container-communication restriction. The host probe cannot see this
   route.
2. H2: the sidecar dies after the probe (OOM under `--memory=256m` once the addon loads its cache, or an addon crash on
   the first intercepted request) and the name still resolves briefly. Nothing records the sidecar's exit state.
3. H1 and H3 (unlikely): no nested container in `entrypoint/role_dispatcher.sh`, one `--network` flag, and no forwarded
   proxy variable that could shadow the sidecar URL. A literal `holon-proxy` without the per-run suffix in a report
   would point to an old image rather than this code.

Proposed follow-up intent:

- slug: `sidecar-in-network-readiness-diagnostics`
- scope: `launcher/sidecar.py`, `launcher/proxy_paths.py`, `token_reduction/proxy_readiness.py` and tests.
- acceptance criteria: readiness is also checked from inside the sidecar network (a short-lived probe on `holon-net-*`
  against `holon-proxy-*:8080`), and a failure degrades to direct egress with a named cause; when a role container exits
  non-zero with the sidecar active, the launcher logs the sidecar's `State.Status`, `OOMKilled` and exit code before
  teardown; hermetic tests with a stubbed `_run_docker`.
