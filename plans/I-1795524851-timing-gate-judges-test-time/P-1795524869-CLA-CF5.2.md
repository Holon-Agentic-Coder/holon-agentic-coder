### Strategy Rationale

**Intent assessment.** Accepted as is. The problem is real and frequent: seven unit-job gate failures in about eight
hours on 2026-11-24, none caused by the change under test. The acceptance criteria are concrete and testable with
fixtures, and the scope is four files.

**The measure.** Test time is read from the JUnit report the gate already receives through `--junit`. It is the suite
time when the report carries one, otherwise the sum of the test case times, exactly as the intent words it. The record
stores the value and which of the two it is, because the two differ by a factor of `2` to `4` under `pytest -n auto` and
must never be compared with each other. Jobs that pass no JUnit report (`build-images.yml`) keep today's wall-clock
behaviour and today's messages, byte for byte.

**Which measure is judged.**

- The ceiling needs no baseline, so it is judged on test time whenever the current run has it, otherwise on wall clock.
- The relative check is judged on test time only when every baseline record in the window carries test time of the same
  kind. One median cannot mix measures, so a single record without it moves the relative check to the old wall-clock
  comparison, and the output says how many records lacked the measure. This is the fallback of acceptance criterion (d).
  It lasts for the first five pushes to `main` after the merge.

**The noise verdict.** When a threshold is breached and the current run and the baseline both have per-test times, the
gate asks one question: does a small set of tests explain most of the excess?

- For every test the baseline is the median of its times in the baseline records. The suite-wide scale is the median of
  current over baseline across tests whose baseline is at least `0.05 s`, never taken below `1`.
- A test's attributed seconds are its growth beyond that scale: `current - baseline * scale`. A test in no baseline
  record is new and its whole time is attributed.
- Offenders are the tests whose attributed seconds exceed `5 s` and whose time exceeds the scaled baseline by more than
  `50 %` (the thresholds of the existing per-test report), largest first, at most `10`.
- The excess is the sum of every shared test's growth over its baseline, plus the time of new tests.
- Offenders explain at least `50 %` of the excess: the slowdown is concentrated. The gate fails and names the offenders
  with their before and after times. The label still turns a relative failure into a warning and never the ceiling.
- Otherwise the slowdown is spread across the suite: the gate passes with a `::warning::` that says runner variance and
  prints the evidence (median ratio, number of tests compared, offender share of the excess).
- Fewer than `20` comparable tests, no baseline per-test times, or no positive excess: the evidence is insufficient. The
  gate keeps the plain verdict (it fails) and says that runner variance could not be assessed. This keeps the stress job
  (2 tests) and every existing small-fixture test on today's behaviour.

Measuring growth beyond the suite-wide scale is what makes a uniform slowdown score zero even in a top-heavy suite,
where the ten slowest tests hold a large part of the total time. The same assessment runs whichever measure was judged,
because the per-test times exist in today's records already; pull requests therefore stop failing on noise from the
first run after the merge, not five pushes later.

**Alternatives considered and rejected.**

- **Sum of test case times as the only measure.** Fails every macOS run against the `600 s` ceiling (sums of `879` to
  `1659 s`).
- **Pass only when dividing the measure by the median ratio brings it under the threshold.** Real noise is heavy-tailed:
  the median ratio under-corrects (a `744 s` run with a median ratio of `1.2` still reads `620 s`), so this rule would
  keep failing the very runs the intent names.
- **A hard cap on how much noise may be forgiven.** Any cap re-creates false failures on a noisy enough runner, and the
  intent asks for none.
- **Net growth of the summed time as the denominator.** Near the ceiling the net growth is small, so ordinary jitter in
  ten unrelated tests would read as concentrated and fail marginal runs.
- **Counting every new test as attributed.** Renamed tests look new and would turn noise into a failure; new tests are
  instead offenders only when they pass the same `5 s` bar as any other test.
- **Fetching the baseline in `record` mode** to forgive noise on `main` too. It adds network calls to `main` pushes and
  is outside the intent, which is about pull requests. Listed as a follow-up.
- **Re-exporting the moved report helpers from the gate.** The repository convention is that tests import a name from
  the module that owns it, so the four tests of those helpers move with them instead.

## Plan Description & Strategy

The timing gate compares a pull-request job with the last five `main` runs and fails it when it is much slower or above
`600 s`. Today it measures the whole job by wall clock, so a slow runner fails a correct change. This plan changes what
is measured and adds a check for runner noise.

**What is measured.** The gate reads pytest's JUnit report, which it already receives. Test time is the suite time in
that report, or the sum of the test case times when the report has no suite time. On `main` the gate writes test time
into its record next to the wall-clock duration and the per-test times, as two new optional keys. Old records still
load.

**What is judged.** The ceiling is applied to test time. The comparison with `main` uses test time when all five
baseline records have it; if any lacks it, the comparison uses wall clock as today and says so. A job with no JUnit
report behaves exactly as today.

**Runner noise.** When a limit is breached, the gate looks at the per-test times. If the ten most-slowed tests explain
at least half of the excess, the slowdown is concentrated: the gate fails and names those tests with their times before
and after. Otherwise the slowdown is spread across the suite: the gate passes with a warning that says runner variance
and shows the evidence. If there is too little per-test data to tell, the gate fails as it does today and says why.

**Messages.** Every failure and warning is one line that states the measure judged, the baseline, the threshold and the
reason for the verdict. Wording that people and tests already rely on stays: `Timing gate passed`,
`::error::Timing regression`, `::notice::Cold start`, the ceiling sentence and the label name.

**Code layout.** A new module, `scripts/ci_timing_noise.py`, holds the per-test report (moved unchanged from the gate)
and the new evidence and verdict functions. `scripts/ci_timing_gate.py` keeps the measure, the record, the decision
order and the command line, and does not grow. No workflow file, argument name or budget file changes.

**Tests.** Pure-function tests go in the new `apps/sandbox-executor/tests/test_ci_timing_noise.py`; gate-level tests go
in the existing `apps/sandbox-executor/tests/test_ci_timing_gate.py`. They replay the five failures of 2026-11-24 with
their real numbers, a concentrated slowdown, both ceiling cases, old-format baseline records and the new record format.
Verification runs the affected tests, then the full suite once, then both lint tasks, all in the foreground.

   - Median ratio: the median of current over baseline across the comparable tests. Scale: the larger of `1` and the
     median ratio.
   - Attributed seconds per test: `current - baseline * scale` for a shared test, the whole current time for a new one.

     `baseline * scale * 1.5`; sorted by attributed seconds, largest first, ties by test id; at most `10`.
   - Excess: the sum over shared tests of the positive part of `current - baseline`, plus the time of all new tests. Not
     positive: insufficient.
   - Attributed: the sum of the offenders' attributed seconds.

   comparable tests with the count found, or no per-test excess), so the gate can state it.

  `uv run task lint-docs` all exit `0`, and the diff is confined to the touch set.
- **Discard:** A failure can only be fixed by changing files outside the touch set, a workflow file or the budget file:
  stop and report it with the failing output. Stop if cost exceeds `1.5 * cost_pred`.

### Step Metrics Rationale

`SSA = 0.5`, `IRR = 0.5`, `CL = 0.5`, `SER = 0.5`, `NOV = 0.5` gives
`0.30 * 0.5 + 0.25 * 0.5 + 0.20 * 0.5 + 0.15 * 0.5 + 0.10 * 0.5 = 0.50`. The step changes nothing unless a regression
appears. Cost is dominated by the single full suite run. The probability is below `1.0` because the full suite and the
lint tasks may surface an interaction the focused runs did not.
`EV = 0.92 * 4.00 + 0.5 * 1.00 - 0.3 * 0.50 - 2.00 = 3.68 + 0.50 - 0.15 - 2.00 = 2.03`.
