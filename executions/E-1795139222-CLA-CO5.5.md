## Steps Executed

### Step 1: Probe the post-execute guards (done)

- The empty-diff guard (`flow/stages/execute.py`, `git.changed_paths` / `has_effective_diff`) and the touch-set guard
  (`flow/stages/touch_set_guard.py`) diff the plan tip against the execution head and ignore `holon-knowledge/ledger/`,
  `plans/` and `executions/`, so the old run's notes and failure row are invisible to them.
- `_latest_execution_summary` keys on the execution id and the branch's plan (`is_row_of_execution`), so the old failure
  row never stands in for the new execution's row; notes validation reads only `executions/<new id>.md`.
- `attribution_allows_publish` scans `plan_tip..HEAD` commits for trailers; a branch-tip resume adds the failure commit
  (written by the executor, no trailer) and whatever a human added, exactly as a hand-written `partial_head` row did.
- `host_remote.new_local_child_branches` counts any local `<plan>/E-*/_` branch absent from the pre-dispatch origin
  snapshot as new.
- `partial_salvage._publish_partial` pushes the branch first and appends the superseding row afterwards through
  `_append_ledger_row`, which works on `refs/remotes/origin/<branch>`; on a never-pushed branch the push therefore
  publishes the branch before its row exists.
- Chosen Step 4 variant: the plain branch tip (no guard objects to the old notes file).

### Step 2: Record the `--allow-overlap` override once per plan (done)

- New `flow/admission_record.py` owns `ADMISSION_OVERRIDE_KIND` and `override_already_recorded(repo_dir, plan_branch)`:
  it reads the plan branch's `executions.jsonl` at the origin ref, then the local ref, and matches a row on `kind`,
  `plan_id` and `plan_branch`; an unreadable ledger reads as no row (fail towards recording).
- `admission_stage_failure` skips the write when the row exists and logs
  `Stage 3 admitted by --allow-overlap (override already recorded on '<plan_branch>')`; dry-run and refusal paths are
  unchanged. `flow/__init__.py` re-exports the new public function (package export test).
- Tests: `test_override_is_recorded_once_per_plan`, `test_an_override_row_of_another_plan_does_not_count`.

### Step 3: Accept partial work forked from an earlier ledger-only plan tip and merge the current plan tip (done)

- New `entrypoint/partial_resume.py`: `plan_lineage_refusal(repo, plan_tip, head, intent_tip)` accepts a head that
  descends from the plan tip, or whose fork point lies on `rev-list --first-parent <plan_tip> ^<intent_tip>` and after
  which the plan branch changed only `holon-knowledge/ledger/*.jsonl`; without a resolvable intent tip that sub-check is
  skipped with a stderr note. Refusals keep the prefix `not a descendant of the plan tip`, so the existing executor test
  of a plan revision still matches. `intent_branch_tip` resolves `<intent>/_` from the plan prefix.
- `resolve_partial_head` uses the rule instead of the strict ancestor check and returns a typed `ResumeStart`.
- `executor._resume_start` creates the execution branch at the chosen start and, through `_merge_plan_tip`, merges the
  current plan tip (`merge --no-edit`; ledger-only conflicts go through `_reconcile_conflicted_merge` with the plan side
  as prefix). On any other conflict or failure the merge is aborted, the branch is re-created at the plan tip and the
  reason is printed. `plan_tip` stays the empty-diff and attribution base.

### Step 4: Resume from the execution branch tip (done)

- `partial_resume.resume_from_branch_tip` keeps the recorded head when the tip equals it or adds only engine-owned files
  (the failure commit), returns the tip when it strictly descends from the head and passes the lineage rule (reason
  `resumed from the branch tip <tip12>, <n> commit(s) after the recorded partial head <head12>`), and otherwise keeps
  the head with the reason
  (`the branch tip <tip12> does not descend from the recorded partial head <head12>; resuming from the recorded head`),
  which the executor prints to stderr, redacted. The continuation note names the actual start commit.

### Step 5: Push an execution branch only once its ledger row exists (done)

- New `flow/execution_publish.py` (no `entrypoint/` imports). Revised in Step 8 (see there):
  `unrecorded_executions(repo_dir, plan_prefix, before)` lists the new local execution branches whose tip carries no
  summary row of their own (any status counts); `hold_unrecorded_executions` logs each
  (`Stage 3: execution branch '<branch>' has no ledger row; kept local and not pushed.`) and returns the pre-dispatch
  snapshot plus those branches, which `run_execute_stage` passes as the exclusion set of the existing
  `publish_new_child_branches` call; `held_execution_failure` fails Stage 3 naming the held branch when the executor
  exited 0 without a row.
- Salvage audit: `_publish_partial` pushed before appending its row. For a branch absent from origin it now calls
  `publish_with_first_row`, which stages the local branch as `refs/remotes/origin/<branch>` (must not exist), appends
  the row through the existing `_append_superseding_execution_row` and so creates the branch on origin in one push that
  already carries the row; the staged ref is dropped when the append or push fails. Already-published branches keep the
  old path.
