## Steps Executed

### Step 1: Confirm the exact-SHA CI source and the state a fresh Stage 4 must reset

- `probe_ci_checks` (`flow/github/ci.py`) uses `gh pr checks <target> --json bucket,name,state,event,workflow,link`: it
  reports the latest run per check name on the PR, not on a given SHA, and a cancelled run lands in the `cancel` bucket,
  counted neither as passed nor failed. It cannot express "on exactly this SHA" or `stale`.
- Exact-SHA source chosen: `gh api --paginate repos/{owner}/{repo}/commits/<sha>/check-runs` with
  `--jq '.check_runs[] | {id, name, status, conclusion, head_sha, details_url}'` (one JSON object per line, so paginated
  pages need no merging); `gh api` fills `{owner}/{repo}` from the checkout, the same way `gh run rerun` resolves it.
  Parsed fields: `check_run_id`, `name`, `status`, `conclusion`, `head_sha`, `run_id` (from `parse_run_id(details_url)`).
- `gh run rerun <run_id>` reruns a whole run under the same run id (a new attempt), so a run id cancelled again after a
  rerun is "cancelled twice"; the new attempt registers new check-run ids, so the newest check run per name wins.
- Fresh Stage 4 state: `_review_window` derives the first label and remaining budget from
  `context.review_iterations_done`, and `run_review_loop` builds the ensemble per call, so resetting the counter to 0
  restarts at iteration 1 with a fresh ensemble. `context.carried_review_findings` is also sent to the next loop, so the
  withdrawal clears it too. `approved_head_of` reads `stage_results["review"].payload["consensus"]`, so the withdrawal
  marks that consensus `approved: False` and records `withdrawn`.
- Merged SHA: `_merge_and_push` pushes the merge and `_follow_merged_head` moves the local ref; the gate reads
  `refs/remotes/origin/<branch>` and falls back to `pr_head_sha`, so `conflict_gate.py` needs no change.
- `rerun_calibration` returns any non-SUCCESS result unchanged, so a SKIPPED `review_restart` result passes through it.
- Ledger appends go through `record_review_action` (`try_append_action_record`, `preserve_shape=True`), which keeps
  extra keys (`approved_head`, `merged_head`, `failed_runs`).
- Resume hole found: a Stage 5 resumed after a withdrawal sees no approved head, so the gate must refuse a withdrawn
  consensus explicitly rather than treat "no approval" as "nothing to gate".

### Step 2: Exact-SHA CI check module and the merged-head CI gate

- New `flow/github/ci_head_checks.py` (160 lines): `probe_head_checks` (`gh api --paginate .../commits/<sha>/check-runs`
  with a `--jq` projection, None on any error), `latest_checks_for_head` (drops runs on another SHA, keeps the newest
  check-run id per name), `classify_head_checks` (`failed` beats `pending` beats `cancelled`; `passed` needs a non-empty
  list of `success`/`neutral`/`skipped`; unknown conclusions are `failed`), `gh_run_rerunner` (`gh run rerun <id>`) and
  `CancelledReruns` (one re-trigger per run id per head; a run cancelled again, or a cancelled check with no Actions run,
  fails closed). The rerun tracker lives here rather than in the gate to keep the gate module inside its budget.
- New `flow/review/merged_head_gate.py` (130 lines so far): `MergedHeadSeams`, `gate_merged_head_ci` (polls on the
  `CiWaitPolicy` clock: registration timeout for the first appearance of checks, then the review CI wait budget; never
  raises) and `format_merged_head_ci` (full SHA, run ids, check-run ids, conclusions, reruns, reason).
- `ruff check` and `ruff format --check` clean.

### Step 3: Consensus withdrawal

- New `flow/review/consensus_withdrawal.py` (163 lines): `withdraw_consensus` appends one ACT row through
  `record_review_action` (`ACT-WITHDRAW`, `action_origin: pr_review`, labels `review`, `consensus-withdrawn`,
  `merged-head-ci`, fields `approved_head`, `merged_head`, `failed_runs`, redacted bounded `error_context`), posts one
  comment per merged SHA (marker `<!-- holon-consensus-withdrawn:<sha> -->`, reusing the `approval_invalidation`
  lister and poster; none on dry run or `skip_push`; a failure is logged, never raised), then resets
  `review_iterations_done` to 0, clears `carried_review_findings` and marks the recorded consensus `approved: False`
  with `withdrawn: {merged_head, approved_head, action_id}`. `withdrawn_consensus_of` reads that mark back.
- `ruff check` and `ruff format` clean.

- `run_calibrate_stage` (`flow/stages/calibrate.py`, 275 of 349 lines): conflict gate, then `stage5_merged_head_gate`,

- Decision: dry run, `skip_push`, no execution branch or no Stage 4 approval keep today's path (gate `skipped`, logged);
  a consensus already withdrawn fails Stage 5 (a resume cannot calibrate it); the approved head, or a head moved past
  it only by non-merge commits touching bookkeeping paths (Stage 4's exit ledger commit), logs "Stage 5 relies on Stage
  4 CI" with the Stage 4 checks and runs immediately; any other head waits on `gate_merged_head_ci`. `passed` continues;
  `failed` calls `withdraw_consensus` and returns a SKIPPED result with `review_restart: true`, `merged_head_ci` and
  `consensus_withdrawal` (nothing prepared or pushed); `pending`, `unknown` and `failed_closed` fail Stage 5 closed.
- The bookkeeping-only fast path was added because Stage 4's exit commits and pushes pending ledger rows after the
  approved `target_commit`, so a plain SHA comparison would make every unmerged head wait on CI, contradicting
  acceptance criterion 4. A merge commit in the range always waits.
