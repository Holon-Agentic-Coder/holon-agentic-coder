### Strategy Rationale

The suite's time on CI is git-spawn time, so the plan attacks git process count directly and lets time follow. Three
levers, in descending yield:

1. **Layered read-only templates** (Steps 2 and 3). Every per-test `git init --bare` / `clone` / `commit` / `push` /
   `fetch` build, and every fixed scenario commit stacked on top of it in a fixture, is done once per test run by
   `shared_template` and handed to each test with `copy_template` (zero git processes per copy). Derived templates are
   built by copying a base template and adding commits, so `build_flow_repos(tmp_path, base_files)` with a given
   `base_files` set is built once per distinct set.
2. **Collapsing identical-coverage parametrised cases** (Step 4), only for the six groups the intent names, only where
   the parameter is data the code does not branch on, and with every case-specific assertion folded into the surviving
   case (for example the label-sanitising case loops over its three labels in one test against one repository copy).
3. **Shared scenarios** (Step 5, exploratory): a read-only scenario computed once (for example the docker argv per role
   in `test_worktree_all_stages.py`) with every original assertion kept as its own test.

Step 1 measures the baseline (per-file time, case count, setup- versus call-phase git count by `PYTEST_CURRENT_TEST`)
and a per-test coverage-context map, and projects the reduction before any edit. That projection is the bottleneck gate:
if levers 1 to 3 project below 40 percent on either measure, execution still lands the reductions it can prove safe but
records the shortfall honestly in the notes rather than cutting behaviour to hit the number.

**Aggregation of metrics.** Entropy is the sum of step entropies (`1.0 + 3.0 + 3.5 + 2.0 + 1.5 + 1.0 = 12.0`). Cost is
the sum of step costs (`2.5 + 3.5 + 4.0 + 2.0 + 2.0 + 2.5 = 16.5`). P(success) is set by the bottleneck: reaching 40
percent on both git count and summed time with three-run medians, which depends on Steps 2 and 3 together (`0.80 * 0.70`
is about 0.56, lifted slightly because the steps are independent levers that can compensate for each other, to 0.60).
Impact 60: about 30 s off every macOS unit job, 7 s off ubuntu and 7 s off workspace survival, for every pipeline run,
with no production risk. Learning value 5: a reusable layered-template pattern and a measured spawn profile of the 15
files.

`EV = P(success) * Impact + mu * LearningValue - lambda * Delta_S_intent - Cost`

`EV = 0.60 * 60.0 + 0.5 * 5.0 - 0.3 * 12.0 - 16.5 = 36.0 + 2.5 - 3.6 - 16.5 = 18.4`

**Strong assumptions.** (a) Git per-spawn cost dominates the in-scope time on both platforms, as the intent states, so a
40 percent count cut gives close to a 40 percent time cut; (b) templated copies behave identically to freshly built
repositories for the code under test (the flow `flow_repos` and resume-tip templates already show this); (c) linked
worktrees are never put in a template (`copy_template` refuses them), so `flow_worktree`-style fixtures keep one
`git worktree add` per test on top of a templated primary.
