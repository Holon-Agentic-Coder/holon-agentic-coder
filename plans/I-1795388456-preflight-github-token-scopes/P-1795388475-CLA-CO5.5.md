### Strategy Rationale

The incident (55 minutes of agent time lost to a push refused for lack of `workflow`) has two independent remedies: a
cheap pre-flight that refuses to start the agent, and a recovery path that keeps the commits if a push is refused anyway
(for any reason: scope, branch protection, ref length, a revoked token). Both are needed, because the pre-flight can
only judge classic and OAuth tokens (fine-grained tokens carry no `X-OAuth-Scopes` header and are reported as
unverifiable, never failed), so the recovery path is the backstop.

Reading the code changed two details of the intent. The host, not the container, pushes execution branches
(`dispatch_executor` calls `publish_new_child_branches`), so the commits do survive in the host worktree's local branch;
but they are not named anywhere, and a later salvage, resume or worktree clean can drop them. The recovery therefore
pins them on a dedicated local ref outside `refs/heads/` (immune to branch pruning and `git gc` since it is a ref) and
then attempts a remote copy; the stage error names the remote ref when that push succeeds and the local ref (with the
worktree path) when it too is refused. The second detail is the frozen 431-line budget of `execute.py`: the plan adds at
most about six lines there and puts the behaviour in two new focused modules.

Aggregation: overall `p_success` is driven by the bottleneck Step 3 (recovery, `0.85`) and Step 2 (Stage 3 wiring,
`0.88`), with independent smaller risks in Steps 1, 4, 5 and 6; a product of step successes
(`0.93 * 0.88 * 0.85 * 0.92 * 0.97 * 0.95 = 0.59`) understates it because failures in Steps 4 to 6 are cheaply
repairable in the same branch, so the estimate is lifted qualitatively to `0.80`. Entropy is the sum of step entropies
(`1.4 + 1.8 + 2.2 + 1.5 + 0.5 + 1.2 = 8.6`). Cost is the sum of step costs (`2.5 + 3.0 + 3.5 + 2.5 + 0.5 + 2.0 = 14.0`).

## Plan Description & Strategy

Six steps on one execution branch, in dependency order:

1. A pure, injectable module `flow/github/token_scopes.py` that classifies a token by prefix, probes
   `GET https://api.github.com/user` through an injectable fetcher, parses `X-OAuth-Scopes`, decides whether a path set
   needs the `workflow` scope, and renders doctor lines and the actionable failure message. Never stores or prints the
   token value.
2. A Stage 3 guard `flow/stages/token_scope_guard.py` that gathers the plan row's touch set and the intent's declared
   `scope`, calls the probe only when a `.github/workflows/**` path is involved, and returns a failed `StageResult`
   (`dispatched=False`, `token_scope_missing`) naming `gh auth refresh -h github.com -s workflow`. It is wired as the
   last check of `ExecuteStage.preflight`, before admission, plan refresh, fetches and any container.
3. A recovery module `flow/execution_recovery.py` that, when the Stage 3 host push of new execution branches fails, pins
   each unpushed branch tip on `refs/holon/recovery/<exec_id>`, attempts a non-forced push to `holon-recovery/<exec_id>`
   on origin, and returns a sentence naming where the commits are; `dispatch_executor` appends it to the push failure
   error and payload (`recovery_refs`).
4. The `holon doctor` environment section gains an isolated GitHub-token part printing
   `github_token=<type> scopes=<list|unverifiable|none>` and a `WARNING:` line when `workflow` is missing.
5. Documentation of the pre-flight, the recovery ref and the doctor line.
6. Verification: targeted tests, then the full suite once, then lint and docs checks.

- **Git branch:** the plan's execution branch

### Implementation Details (No code blocks, only logic/steps)

1. Create `apps/sandbox-executor/src/sandbox_executor/flow/github/token_scopes.py` with a module docstring explaining
   classic/OAuth versus fine-grained tokens and the never-print-the-value rule.
2. Constants: `WORKFLOW_SCOPE = "workflow"`, `WORKFLOW_PATH_PREFIX = ".github/workflows/"`,
   `GITHUB_USER_API = "https://api.github.com/user"`, `REFRESH_COMMAND = "gh auth refresh -h github.com -s workflow"`.
3. `token_type(token) -> str`: by prefix only: `ghp_` classic, `gho_` oauth (the `gh` CLI), `github_pat_` fine-grained,
   `ghu_`/`ghs_` app, anything else `unknown`; `none` for an empty or missing token.
4. A frozen dataclass `TokenScopeReport` with `token_type: str`, `scopes: tuple[str, ...] | None` (None means no header,
   so unverifiable) and `detail: str` (a value-free reason such as `no X-OAuth-Scopes header`,
   `HTTP 401 (bad credentials)`, `URLError`). Properties: `verifiable` (scopes is not None), `has_workflow` (the
   `workflow` scope present; GitHub has no broader scope that implies it), `rejected` (HTTP 401).
5. A `Fetcher` type alias: a callable taking a URL and a header mapping and returning `(status, headers)`; the default
   `_urllib_fetch` uses `urllib.request.Request` with `Authorization: Bearer <token>`,
   `Accept: application/vnd.github+json`, a 10 second timeout, and maps `HTTPError` to its status and headers. It never
   logs the request.
6. `probe_token_scopes(token, fetch=None) -> TokenScopeReport`: no token gives type `none`, unverifiable, no request.
   Otherwise call the fetcher; parse `X-OAuth-Scopes` case-insensitively, split on commas, strip, drop empties, sort.
   Any exception is caught and reduced to `type(exc).__name__` (never `str(exc)`, which could embed a URL). A 401 sets
   the rejected detail. Header lookup tolerates both `Message`-like and plain dict headers.
7. `needs_workflow_scope(paths) -> list[str]`: normalise each path or glob with `touch_set.normalise_touch_path` and
   return those that reach `.github/workflows/`: a path that starts with the prefix, a directory entry that is a prefix
   of it (`.github/`, `.github/**`), or a glob whose `touch_set.entry_matches` accepts the probe path
   `.github/workflows/holon-probe.yml`. Accept plain strings and `TouchSetEntry` objects.
8. `missing_workflow_message(report, workflow_paths) -> str`: names up to three of the workflow paths, the token type,
   the scopes found and the exact `REFRESH_COMMAND`, plus the alternative of a fine-grained token with
   `Workflows: write`. Built only from report fields.
9. `doctor_lines(report) -> list[str]`: `github_token=<type> scopes=<comma list | none | unverifiable (<detail>)>`, then
   a
   `WARNING: GitHub token lacks the 'workflow' scope; plans touching .github/workflows/** will fail the Stage 3 pre-flight. Run '<REFRESH_COMMAND>'.`
   line when verifiable and missing, and a `WARNING:` line when no token was found or the token was rejected.
10. `resolve_token() -> str | None`: lazily import `sandbox_executor.cli.find_github_token` (the same resolution order
    the sandbox uses; the flow already imports `cli` lazily in `dispatch.py`) so there is one source of truth.
11. Write `apps/sandbox-executor/tests/flow/github/test_token_scopes.py`: type classification table; header parsing with
    spacing and case variations; missing header gives unverifiable; 401 gives rejected; fetcher raising `OSError` gives
    unverifiable with only the class name; `needs_workflow_scope` for literal, `.github/`, `.github/**`, `**/*.yml` and
    non-workflow paths (`.github/CODEOWNERS`, `docs/x.md`); message names the refresh command; a sentinel token string
    never appears in any report field, message or doctor line. Every test injects a fake fetcher that records the URL
    and asserts no real network use.
