### Strategy Rationale

The defect has two parts, and both live in `calibration_ev.py`. (1) The final-row selection sorts by `ledger_revision`
first. A Stage 3 `sync_conflict` row (revision 2) therefore beats the later Stage 4 `halted_for_human` row (no revision,
defaulted to 1). (2) The observed-EV failure scan counts every row that is non-zero or failed, so a resolved conflict
zeroes `ev_with_bugs` even after the ordering is fixed. `calibration.py` repeats the same sort key when it picks
`best_record`, so it must use the same helper.

The plan is one tightly coupled change (a shared ordering helper, two call sites, and a superseded-conflict rule) plus
hermetic tests. Splitting it would cost more coordination than it saves.

Aggregation: overall `p_success` is the product of the implementation step (0.92) and the verification step (0.93),
about 0.86, rounded to 0.85. Verification is the bottleneck, because lint-docs and complexity gates can surprise.
Entropy is the sum of the step entropies: `1.8 + 0.8 + 0.4 = 3.0`. Impact is 70 because calibration feeds every future
planner EV estimate, and the bug currently inverts the sign of EV on every flow that resolves a merge conflict (three
flows on 2026-11-20). Cost is the sum of the step costs: `5.0 + 2.0 + 1.0 = 8.0`.

`EV = P(success) * Impact + mu * LearningValue - lambda * Delta_S_intent - Cost`

`EV = 0.85 * 70.0 + 0.5 * 4.0 - 0.3 * 3.0 - 8.0 = 59.50 + 2.00 - 0.90 - 8.00 = 52.60`

Strong assumption: a row's `created_at` reflects flow order. Stage 3 and Stage 4 rows are written sequentially by one
host flow, so this holds. When two rows share the same instant, `ledger_revision` breaks the tie. If the instant and
revision are both equal, the original ledger line order breaks it: Python's sort is stable and the parsed rows keep file
order.

### Intent & Git Integration

  from being scored as a failure.
- **Git branch:** I-1795161177-calibration-final-row-by-time/P-1795161194-CLA-CO5.5/\_ (execution branch under it)
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. In `calibration_ev.py`, add a private `_created_at_instant(record)` helper that returns a timezone-aware UTC
   datetime:
   - Take `str(record.get("created_at", "")).strip()`, replace a trailing `Z` with `+00:00`, then parse it with
     `datetime.fromisoformat`.
   - If the parsed value is naive, give it UTC.
   - On an empty value or `ValueError`, return `datetime.min` with UTC tzinfo.
   - Import `UTC` and `datetime` from `datetime`.
2. Add a public `summary_row_order_key(record)` that returns `(instant, ledger_revision)`, where
   `ledger_revision = int(record.get("ledger_revision") or 1)`. Guard `TypeError` and `ValueError` and fall back to 1.
   Add `latest_summary_row(records)`, which returns `sorted(records, key=summary_row_order_key)[-1]` for a non-empty
   list and `None` otherwise. Use a stable sort, not `max`, so the last ledger line wins when instant and revision are
   both equal.
3. In `evaluate_dual_ev_outcomes`, delete the inner `sort_key` and build `sorted_records` with
   `sorted(matching, key=summary_row_order_key)`. Keep `final_record = sorted_records[-1]`. The clean-EV logic does not
   change.
4. Add the module constant `SYNC_CONFLICT_STATUS = "sync_conflict"` with a comment saying it mirrors the Stage 3 status.
   Use a literal, not an entrypoint import.
5. Add `_is_superseded_sync_conflict(record, later_records)`. It returns True when the record's status is
   `sync_conflict` and any later row (by the order above) is converged according to `is_converged_record` with
   `_record_exit_code == 0`.
6. Add `_counts_as_failure(record)`, which reproduces the current test: status `failed`, or `_record_exit_code != 0`.
   Then rewrite `has_failure` as: any row at index `i` in `sorted_records` that counts as a failure and is not a
   superseded `sync_conflict` given `sorted_records[i + 1:]`. Split this into a small `_has_unresolved_failure` function
   so `evaluate_dual_ev_outcomes` stays within C901 and PLR0912.
7. When the final row is itself a `sync_conflict`, nothing supersedes it. The clean score then gives `p = 0` because the
   row is not converged, and the observed score fails as well:
   - The row's status is not `failed`, and the copied failure row's `exit_code` may be 0.
   - The existing path already gives the right answer: when the final row is not converged, `p_bugs` and `imp_bugs`
     follow `p_clean = 0`.
   - Also make it explicit: `_has_unresolved_failure` returns True when the final row is a `sync_conflict`. The
     "unresolved conflict scores as failed" test then pins the behaviour.
8. Update the module docstring with one sentence on the ordering rule (time first, revision as the tie-break).
