## Plan Description & Strategy

Build `holon intent-check <intent.json>` as three new source modules and two new test modules, matching the intent's
scope exactly:

- `intent_scope_graph.py` (at most 200 lines): pure read-only helpers. A Python import scanner built on `ast` that maps
  repository-relative `.py` paths to dotted module names (stripping everything up to and including a `src/` segment),
  resolves absolute and relative imports, and answers "which files import module X" and "which modules does file Y
  import"; a package re-export finder for the sibling `__init__.py`; and a co-change counter over
  `git log -n 200 --no-merges --name-only` output.

  marker), and builds an `IntentScopeReport` dataclass with `missing`, `proposed` (each with a reason, for example
  `test imports listed module` or `co-changed 4x with <path>`) and `warnings`, plus `render_text` and `to_json`.
- `cli/commands/intent_check.py` (thin, roughly 50 lines): `ORDER`, `register` (positional `intent_file`, the shared
  `--target-worktree` option, `--json`), and `run` which returns `1` when `proposed` is non-empty and `0` otherwise. It
  is picked up by `discover()` because it exposes `register` and `run`; no existing command module is edited.

The tests build a hermetic `tmp_path` git repository per case (the session-wide test git config in `tests/conftest.py`
already isolates identity and global config) and drive the logic module directly plus the CLI through
`sandbox_executor.cli.main`.

## Step 2: Add `intent_scope_graph.py` with import-graph and co-change helpers

- **Sub‑intent recommendation:** NO
- **Reasoning:** One new module of at most 200 lines with pure functions; the risk is heuristic correctness, which the
  Step 5 tests pin down.
- **Step Type:** IMPLEMENTATION
- **Exploration level:** EXPLOIT

### Intent & Git Integration

- **Step Intent:** Provide read-only helpers that find test importers, imported source modules, re-exporting package
  `__init__.py` files and co-changed partners for a listed file.
- **Git branch:** same execution branch as Step 1
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. `module_name(path)`: for a repository-relative `.py` path, drop the leading segments up to and including the last
   `src` segment if present; otherwise use the path as is. Strip `.py`, map `/` to `.`, and drop a trailing `.__init__`.
   Return `None` for non-Python paths.
2. `python_files(worktree)`: list tracked `.py` files with `run_git(["ls-files", "-z", "--", "*.py"], cwd=worktree)`;
   `ls-files` is read-only. Fall back to an empty list when the directory is not a git repository.
3. `imported_modules(worktree, path)`: parse the file with `ast.parse` (catch `SyntaxError`, `OSError`,
   `UnicodeDecodeError` and return an empty set). Collect `Import` names, and for `ImportFrom` resolve relative imports
   against the file's own module (respecting `level`, and treating `__init__.py` as its package), then add both `module`
   and `module.name` for each alias so `from pkg import mod` resolves to `pkg.mod`.
4. `build_module_index(worktree)`: a dict from dotted module name to path for every tracked `.py` file, computed once
   per check.
5. `test_importers(index, imports_by_path, listed_module)`: test files (`test_*.py` or `*_test.py`, or under a `tests/`
   segment) whose imports contain the listed module name or a name under it.
6. `imported_sources(index, imports, listed_test)`: map each imported dotted name (and its parents, longest first) to a
   tracked non-test path through the index; external packages are ignored because they are not in the index.
7. `reexporting_init(worktree, path)`: the sibling `__init__.py` of the listed module, returned only when it exists and
   its imports (from step 3) include the listed module's dotted name.
8. `co_changed(worktree, listed, limit=200, threshold=3)`: run
   `run_git(["log", "-n", str(limit), "--no-merges", "--no-renames", "--name-only", "--format=%x1e"], cwd=worktree)`
   (read-only, no `--follow`, no index or ref writes), split commits on the record separator, and count, for each listed
   path, partner paths sharing a commit. Return partners whose count is at least `threshold`, excluding listed paths,
   `is_metadata_path` paths and files that no longer exist in the worktree. Return a mapping partner to
   `(count, listed_path)` keeping the highest count.
9. Keep every function under the ruff limits (`C901 <= 10`, `PLR0912 <= 12`) by splitting the relative-import resolver
   and the commit parser into small private helpers; add module and public-function docstrings per the ruleset; no
   inline `# noqa`.
10. Do not import from `cli`, `flow` or `entrypoint`; the module depends only on `ast`, `pathlib`,
    `sandbox_executor.git`.

## Step 3: Add `intent_scope_check.py` with the report model and rules

- **Sub‑intent recommendation:** NO

  sections.

- **Step Intent:** Turn an intent JSON file into an `IntentScopeReport` with `missing`, `proposed` and `warnings`, and
  render it as plain text or JSON.
- **Git branch:** same execution branch
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. `load_intent(path)`: read the JSON with UTF-8; raise `ValueError` with a clear message when the file is unreadable,
   not an object, or has no `scope` list. Read `acceptance_criteria` as a list of strings (missing means empty).
2. `ScopeEntry`: frozen dataclass with `path` and `marked_new`. Parsing strips whitespace, a leading `./`, a trailing
   ` (new)` and a leading `new:`; `marked_new` is true when a marker was present. Document the convention in the module
   docstring and the command help.
3. `IntentScopeReport`: frozen dataclass with `missing: list[str]`, `proposed: list[Proposal]` and
   `warnings: list[str]`; `Proposal` holds `path`, `reason` and `source` (the listed file that caused it). A
   `has_proposals` property drives the exit code.
4. `check_intent_scope(intent, worktree)`:
   - missing: listed paths, not marked new, for which `(worktree / path).exists()` is false;
   - proposed, for each existing listed `.py` file: test importers of a listed source module, source modules imported by
     a listed test, the re-exporting `__init__.py`; then co-change partners for every listed path. Drop proposals
     already in the scope, de-duplicate by path keeping the first reason, sort by path for stable output;
   - warnings: for each listed file, warn when the joined acceptance-criteria text contains none of: the full path, the
     file name, the stem, or the dotted module name. Text is a warning only and never a proposal.
5. `render_text(report)`: three headed sections (`Missing`, `Proposed companions`, `Warnings`), each with `none` when
   empty, and a closing line stating the number of proposals.
6. `to_json(report)`: a dict with exactly the keys `missing`, `proposed` (list of objects with `path`, `reason`,
   `source`) and `warnings`.
7. Keep the module at most 200 lines; no file writes anywhere (no `open(..., "w")`, no temp files, no caches).

### Strategy Rationale

The intent is well specified, cheap and squarely aimed at a measured cost (touch-set escapes costing about half an hour
each), so it is accepted as is and executed as one plan with no sub-intents. The touch set equals the intent's scope:
the command self-registers through `discover()`, so no existing module, README or package `__init__.py` needs to change,
which is exactly the escape class the tool targets. Reusing `sandbox_executor.git.run_git` and `is_metadata_path` keeps
the new code small and consistent with how the flow already classifies bookkeeping paths.

Aggregation: overall entropy is the sum of step entropies, `0.3 + 1.6 + 1.4 + 0.5 + 1.2 + 1.0 + 0.4 = 6.4`. Overall cost
is the sum of step costs, `0.5 + 3.5 + 2.5 + 1.0 + 2.5 + 1.5 + 0.5 = 12.0`. Overall success is driven by the bottleneck
chain Steps 2, 3, 4 and 7 with correlated failure modes (a heuristic bug found in Step 5 is fixed in Step 2 within the
same run), so it is set qualitatively at `0.82`, above the naive product of the bottleneck steps
(`0.88 * 0.90 * 0.95 * 0.92 = 0.69`) because fix-forward inside one execution branch is normal. Impact `70.0` reflects a
pre-launch tool that removes a recurring Stage 3 to Stage 2 round trip but is advisory (nothing in the flow calls it
yet). Learning value `4.0` is the evidence of how well import-graph plus co-change heuristics predict real touch sets,
observable from the Step 7 smoke run.
`EV = 0.82 * 70.0 + 0.5 * 4.0 - 0.3 * 6.4 - 12.0 = 57.40 + 2.00 - 1.92 - 12.0 = 45.48`.

Strong assumptions: `cli.main` honours the integer returned by a command's `run` (otherwise `sys.exit` in `run`, as
`intent.py` does); test files outside `GOVERNED_MODULES_BY_PACKAGE` in `test_self_doc_modules.py` are not governed, so
the new modules need no registry entry there.
