### Strategy Rationale

The intent asks for a single owner of token reduction. The production code depends on the local copy in exactly three
places (CA generation, readiness probe plus timeout, the mounted addon), and everything else that imports
`sandbox_executor.token_reduction` is either the copy itself, tests of the copy, the A/B measurement script, or docs.
The plan therefore (1) snapshots a test inventory as a coverage baseline, (2) re-homes the two pieces of host-side logic
this repository genuinely owns (readiness probe, Root CA) into `launcher/` with their tests, (3) repoints the sidecar at
the holon-coherence image, (4) migrates every test that exercises launcher/cli/coherence behaviour out of
`test_token_reduction.py` and the other mixed files into launcher-named test modules, (5) deletes the package and
everything that exists only for it, and (6) validates.

Ordering matters: re-homes come before deletion so every intermediate commit compiles and the suite stays green; test
migration comes before deletion of `test_token_reduction.py` so no keep-worthy test is lost in between.

Root CA as a launcher function rather than `holon-coherence init-ca`: the host CLI is not installed by `uv sync`
(holon-coherence is only a git submodule, excluded from ruff, not a `[tool.uv.sources]` member), so shelling out would
add a new host prerequisite and break the `--token-reduce` path on hosts that only have this repository. The ported
generator keeps the same on-disk layout (`~/.holon/certs/holon-root-ca.crt`/`.key`, `mitmproxy-ca*.pem`) as
holon-coherence's own `ca_generator.py`, so a CA created by either tool is reused by the other.

Aggregation: entropy is the sum of step entropies (`0.5 + 1.0 + 2.0 + 3.0 + 2.5 + 2.0 + 0.5 = 11.5`). p_success is a
qualitative bottleneck judgement rather than a naive product (the naive product `≈ 0.37` treats correlated, retryable
steps as independent): Step 4 (sidecar repoint, `p = 0.75`) is the bottleneck, Step 5 (test migration, `p = 0.80`) is
the next-largest risk, and the remaining steps are near-certain and recoverable within the same execution, giving
`p ≈ 0.72`. Impact 80 (removes ~2,900 lines of diverged production code plus ~4,500 lines of tests/docs/scripts and a
whole drift class). Cost is the sum of step costs (`2 + 2 + 4 + 5 + 6 + 4 + 3 = 26`). Learning value 4 (the image
runtime contract and the test-inventory coverage technique are reusable).

`EV = P(success) * Impact + mu * LearningValue - lambda * Delta_S_intent - Cost`

`EV = 0.72 * 80.0 + 0.5 * 4.0 - 0.3 * 11.5 - 26.0 = 57.60 + 2.00 - 3.45 - 26.00 = 30.15`

Strong assumptions: the holon-coherence image honours `HOLON_IN_CONTAINER=1`, `WIRE_LOG_DIR`, `CACHE_DIR` and
`HOLON_PASSIVE_MONITORING` (verified by reading the pinned submodule source: `commands/start.py` `is_in_container`,
`mitm_addon.py` env reads); and no CI job runs a real Docker sidecar (the sidecar is exercised through `FakeDocker` in
