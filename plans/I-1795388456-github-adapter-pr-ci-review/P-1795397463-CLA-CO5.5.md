### Strategy

The single biggest failure mode is a silent seam break: if `loop.py` starts calling an adapter method while 170 tests
still patch `loop.probe_ci_checks`, the patches intercept nothing and the tests either hit the write guard, take the
`which("gh") is None` path and assert on the wrong branch, or pass vacuously. Doing the whole intent in one change
couples that test migration with the module surgery and puts roughly 35 files in one diff, so the work is split into
three children, each of which leaves the suite green and behaviour identical at its own merge point:

1. **Pure decisions first, behind re-exports.** Move the decision logic into I/O-free modules
   (`flow/github/ci_policy.py`, `flow/github/mergeability_policy.py`, `flow/github/review_policy.py`,
   `flow/github/pr_metadata.py`). The old modules re-import the moved names so every existing import and patch target
   keeps resolving. This child changes no seam and so carries the least risk; it also shrinks `pr.py` and
   `review_post.py` enough for child 2 to work inside the frozen budgets.
2. **Adapter and fake, inside `flow/github`.** Add `flow/github/adapter.py` with `GitHubAdapter` (repository-scoped:
   `repo_dir`, `proxy_env`, injectable `run` and `which`) exposing `open_or_update`, `ci_checks`, `mergeability`,
   `post_review` (plus the narrow `post_comment`, `pr_view`, `default_branch` and `merge` primitives that the existing
   functions need), all returning plain dataclasses or dicts with redacted text. The public functions
   (`create_or_update_pr`, `probe_ci_checks`, `check_pr_mergeability`, `post_pr_review_consensus`) become thin
   orchestrators with an optional keyword `github: GitHubAdapter | None = None` that defaults to
   `GitHubAdapter(repo_dir, proxy_env)`. Their names and signatures stay the same, so the 170 loop-level patches keep
   working unchanged. Add `tests/flow/github/fake_github.py` (`FakeGitHub`, an in-memory adapter-shaped double that
   records calls) and convert `tests/flow/github/test_pr.py`, `test_ci.py`, `test_review_post.py` and `test_merge.py` to
   it. A dedicated `tests/flow/github/test_adapter.py` pins the exact `gh` argv, env, timeouts and redaction using an
   injected fake `run` (never real `gh`).
3. **Call sites and review-loop tests.** `stages/review.py` (via `_run_engine_review_loop`) and `loop.py` accept an
   injected `github` adapter (default built from `repo_dir` and `proxy_env`) and pass it to the orchestrators;
   `ci_wait.py` receives a probe bound to the adapter and `ci_final_head.py` gets its `gh pr view headRefOid` and
   `gh run rerun` through the adapter too. The loop-level tests move from `patch("...loop.probe_ci_checks")` to
   injecting `FakeGitHub` through a shared fixture in `tests/review_loop_stubs.py`. A guard test asserts that no file in
   `flow/` other than `flow/github/adapter.py` contains the `gh` argv for the in-scope verbs (`pr create`, `pr edit`,
   `pr checks`, `pr review`, `pr view` for mergeability, `pr comment` from review posting).

Behaviour identity is enforced by characterisation: before each child's change, its executor records the exact argv, env
keys, `cwd`, `timeout`, and returned dict for the existing paths (already covered by the tests under
`tests/flow/github/` and `tests/test_review_loop.py`) and the converted tests assert the same values against
`FakeGitHub.calls`.

Test discipline per child: run the affected tests first with `uv run pytest <paths>`, then the full suite once with
`uv run task test`, then `uv run task lint` (ruff complexity, module budgets, prettier). No repeated runs: this intent
has no performance or timing target.

### Strategy Rationale

The intent is accepted in substance and split for risk, not for budget: the summed step entropy
(`4.0 + 5.5 + 5.0 = 14.5`) sits just under the 15.0 budget, but as a single plan it would be one diff over roughly 35
files whose dominant failure mode (silently dead patches) is invisible until the full suite runs. Three children, each
merging green into the root intent branch, contain that risk and give the reviewers a reviewable diff each time. The
order is forced by dependencies: the pure modules free the frozen line budgets and remove `noqa` debt that the adapter
work needs, and the adapter and `FakeGitHub` must exist before the loop tests can switch to them.

The intent's declared scope omits about 20 test files that patch the loop-level GitHub names; meeting acceptance
criteria 1 and 3 while keeping "existing behaviour tests still pass" requires editing them, so the touch set is widened
explicitly here (ruleset section 3 requires test changes to be declared in the plan). Out of scope and left untouched:
`gh` calls for run logs (`ci_failure_detail.py`, `ci_slowest_tests.py`) and approval-invalidation comments
(`approval_invalidation.py`); they are good follow-up candidates for the same adapter.

Aggregation: overall `p_success` is not the naive product (`0.85 * 0.72 * 0.68 = 0.42`) because each child runs through
its own review loop with a resolver and failures are correlated (the same skills apply to all three); a qualitative
uplift to 0.58 is used. Entropy is the sum of the steps (14.5). Impact is 75 (higher than the sum of step impacts
because the full benefit, no subprocess patching and one `gh` boundary, only arrives when all three land). Cost is the
sum of the steps plus about 0 for orchestration (24). Learning value 8 (adapter-level fakes as a reusable pattern for
the remaining `gh` callers). `EV = 0.58 * 75.0 + 0.5 * 8.0 - 0.3 * 14.5 - 24.0 = 43.5 + 4.0 - 4.35 - 24.0 = 19.15`,
rounded to 19.2. The bottleneck is Step 3 (lowest `p_success`, largest breadth).

## Safety & Constraint Alignment

- **Key world ruleset constraints that affect this plan:**
  - `holon-config/world/constraints.md` section 1: children run on their own branches and merge into the root intent
    branch only; nothing merges to `main` without a human.
  - `holon-config/world/ruleset.md` sections 2 and 3: typed, documented public API; test changes declared in the plan.
  - `docs/safety.md`: PR merge stays in `flow/github/merge.py` with the existing method selection and

  - `holon-config/hygiene/module_budgets.json` (frozen) and `tests/test_complexity_gate.py` (identity snapshot of
    complexity `noqa`).
- **Potential violations or edge cases:**
  - A converted test reaches real `gh` because a seam was missed.
  - Redaction applied to JSON `stdout` breaks parsing, or redaction is skipped on a new error path.
  - A moved function keeps a complexity `noqa` under a new path and fails the ratchet.
  - `loop.py`, `pr.py`, `merge.py` or `ci_final_head.py` grows past its frozen budget.
- **Mitigations built into the plan:**
  - Adapter spawns through `subprocess.run`, so `tests/gh_write_guard.py` still blocks unmocked writes; a dedicated test
    proves it. `FakeGitHub` raises on unscripted calls.
  - `test_adapter.py` pins argv, env, timeouts and redaction; an AST boundary test enforces the single `gh` boundary.
  - Re-exports in step 1 and optional `github` keywords in step 2 keep every existing seam working until step 3 migrates
    its callers.
  - Line counts checked after each edit; new helpers go to new focused modules.
- **Residual risk accepted (and why):** The out-of-scope `gh` callers (`ci_failure_detail.py`, `ci_slowest_tests.py`,
  `approval_invalidation.py`) keep their own spawns; the intent explicitly limits the adapter to PR create/update, CI
  checks, mergeability and review posting, and widening further would push entropy past budget.
