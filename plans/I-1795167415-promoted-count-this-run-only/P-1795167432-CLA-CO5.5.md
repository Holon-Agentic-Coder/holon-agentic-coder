## Plan Description & Strategy

**Root cause (confirmed by reading the code).** `promote_pending_candidates` in
`apps/sandbox-executor/src/sandbox_executor/knowledge/wisdom.py` selects every row of `action_signatures` that has
`success_count + failure_count >= min_trials`. For each row it runs `evaluate_action_promotion`, queries
`action_records`, and builds a failure, pattern or heuristic item. When the target JSON file already exists, it does not
rewrite the file. It does still attach `persisted_path` and append the item to the returned list. Stage 5
(`flow/stages/calibrate.py`) logs `len(...)` of that list, so the logged number is the cumulative count of qualifying
candidates (576 → 640 on 2026-11-20). It is not the number promoted by this run. On goal 2: files are already
write-idempotent (`persist_kb_fact` / `persist_wb_rule` return early, and `test_wisdom.py` checks byte and mtime
identity). The evaluation work and the returned items are still repeated on every flow.

**Fix.**

1. `promote_pending_candidates` returns only the items it **newly** promotes in this call. In a dry run, it returns only
   the items it **would** newly write. It skips evaluation for candidates whose terminal artefacts already exist:
   - a `KB-failure-<fp8>.json` exists, or
   - both `KB-pattern-<fp8>.json` and `WB-heuristic-<fp8>.json` exist.

   A candidate that has only a pattern file is still evaluated, because it can still be promoted to a `proven-success`
   heuristic. In that case only the new heuristic is returned. A second run therefore returns `[]` and calls
   `evaluate_action_promotion` for no terminal candidate.

2. Stage 5 logs `Stage 5 promoted M new knowledge/wisdom candidate(s) this run.`, or
   `Stage 5 promoted no new knowledge/wisdom candidates this run.` when M is 0. The optional running total is
   deliberately left out. It would need a richer return type, and that would widen the change to the CLI and the
   `cli`/`knowledge` re-exports for low value.
3. **Regression guard (found during planning).** Today the commit helper runs whenever the cumulative list is non-empty.
   In practice that is always, so it also sweeps up artefacts that an earlier flow wrote but could not commit after a
   failed calibration. Once the count is per-run, M can be 0 while such stragglers sit in the worktree. Stage 5 will
   therefore call the commit helper whenever calibration succeeded and the run is not a dry run. The helper already does
   nothing on a clean `git status --porcelain`. It logs the "unchanged" message only when M > 0, so a quiet run adds no
   new log noise.
4. **Line budgets.** `flow/stages/calibrate.py` is at exactly 349/349, so any added line fails `uv run task lint`.
   `_commit_stage5_promoted_artifacts` (about 58 lines) moves into a new focused module, `flow/calibrate_promotion.py`.
   It sits next to the existing `calibrate_rerun.py`, `calibrate_sync.py` and `calibrate_rebuild.py`, and it gets the
   default limit of 200 lines. `calibrate.py` imports the helper back, so `flow/__init__.py` (562/562) keeps importing
   it from `flow.stages.calibrate` and stays byte-identical. The `promote_pending_candidates` call stays in
   `calibrate.py`, so the existing patch target `sandbox_executor.flow.stages.calibrate.promote_pending_candidates` in
   the tests keeps working. `holon-config/hygiene/module_budgets.json` is never touched. `knowledge/wisdom.py` is
   outside the budgeted packages (386 lines); the plan keeps it under about 400 lines (see Step 2's contingency).
5. The CLI `holon promote --pending` labels its count as newly promoted (`Newly promoted knowledge items: N`, and the
   dry-run variant to match), so the operator surface matches the new meaning.

**Known trade-off.** Once a failure-mode file exists for a fingerprint, that fingerprint is no longer re-evaluated for
success promotion. This matches the immutable, append-only KB policy (I-1793960332), and a veto is lifted with
`lift_veto`, not by promotion. The trade-off is documented in the docstring and pinned by a test.
