### Strategy Rationale

**Why accept as is.** On 2026-11-20 an overlap wait was followed by a Stage 4 conflict on five files that had to be
merged by hand. Waiting has no value unless the flow then builds on the change it waited for, so a fix has a large
effect. Most of the mechanism already exists:

- `github/merge.py::merge_into_branch` merges `origin/<source>` into `<target>` on origin with `--no-ff`, in a temporary
  detached worktree (the operator's checkout is never touched). It never force-pushes, refuses protected targets, does
  nothing when the source is already an ancestor, resolves ledger-only conflicts with
  `ledger_interleave.resolve_ledger_only_conflicts` (interleaves by `created_at` above an untouched merge-base prefix)
  and aborts on any other conflict.
- `admission.py::admission_stage_failure` already runs before dispatch and owns the admission object.
- `git_refs.py::_append_ledger_row` appends a host-side ledger row to the plan branch, and `admission_record.py` shows
  the once-per-plan pattern.
- `stages/sync_conflict.py` and `_stage_failure(..., dispatched=False)` show how to stop Stage 3 resumably.

**Issues found in the current code that the plan must handle:**

1. **The blocked history is lost on admission.** `record_admission` replaces the blocked record with
   `admitted_record()`, which drops `blocked_since`. If the refresh then hits a conflict and the operator resumes, the
   next admission looks like a "first check" and the refresh would be skipped. The plan has the admitted record carry
   `waited_since` (from the earlier `blocked_since`) and later `refreshed_to`. A refresh is due when `waited_since` is
   set and `refreshed_to` is not, so a resume after a refresh conflict retries the refresh. A flow admitted on its first
   check has no `waited_since` and is never touched.
2. **The merge failure message names no files.** `_merge_in_worktree` returns a generic message. Goal 3 needs the
   conflicting files named, so the unmerged paths are read before `merge --abort` and returned in a structured way.
3. **Partial-work resume would break.** `entrypoint/partial_resume.py::plan_lineage_refusal` accepts a moved plan tip
   only when the plan branch changed nothing but ledger files after the fork point. A refresh merge brings in non-ledger
   changes from main, so a flow that was blocked on a Stage 3 retry after a failed execution would lose its partial
   work. Step 5 extends the rule so first-parent merge commits whose second parent is the recorded refresh commit count
   as engine-owned. The executor's `merge_plan_tip` then brings main into the resumed branch.
4. **Recording in the executions ledger.** The executor container writes the execution summary row, so the host cannot
   stamp it before dispatch without changing the executor. The plan appends one host-side `plan_refresh` row
   (`kind`/`entry_type` `plan_refresh`, `plan_id`, `plan_branch`, `refreshed_to`, `merge_commit`, `waited_since`,
   `created_at`) to the plan branch's `executions.jsonl`. Because the row is on the plan branch before the execution
   branch is cut, every execution branch carries it, and calibration can join it on `plan_id`/`plan_branch`.
   `refreshed_to` also goes into the checkpoint's admission object and the Stage 3 payload (which is checkpointed in
   `stage_results`).

**Rejected alternatives.**

- Rebasing the plan branch: the intent forbids it, it rewrites ledger history, and it needs a force-push.
- Refreshing inside the executor container: the host owns every remote operation (`host_remote.py`).
- Growing `execute.py`: it is at its line budget; a one-call hook plus a new module follows the repository's "one module

## Step 5: Let a resumed execution's partial work survive a refresh merge on the plan branch

- **Sub‑intent recommendation:** NO
- **Reasoning:** This is a correctness edge (a flow blocked on a Stage 3 retry after a failed execution). It is
  contained to one helper in `partial_resume.py` and has a safe fallback. It is the plan's single exploratory step.
- **Step Type:** IMPLEMENTATION
- **Exploration level:** BALANCED

- **Hypothesis being tested:** `plan_lineage_refusal` can accept a plan branch that moved by refresh merges
  (first-parent merge commits with the refresh message prefix whose first-parent diff is the target branch's content)
  without admitting arbitrary non-ledger plan edits. The executor's existing `merge_plan_tip` then brings main into the
  resumed branch cleanly.
- **Learning target:** Whether the lineage rule can tell "engine-owned non-ledger change" (a refresh) apart from "plan
  edited", and whether resume-then-merge produces conflicts in practice.
- **Maximum acceptable cost for this learning:** 2.5 cost units (about one focused session). Beyond that, take the
  fallback.

### Intent & Git Integration

- **Step Intent:** Keep goal 1 compatible with the resumetip guarantees (#208), so a refresh never throws away partial
  work.
- **Git branch:** the execution branch of this plan
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. In `entrypoint/partial_resume.py`, extend `_changes_only_engine_owned` (or the walk in `plan_lineage_refusal`) as
   follows:
   - Walk the plan branch's first-parent commits between the fork point and the plan tip.
   - A commit counts as engine-owned when either (a) it changes only `holon-knowledge/ledger/*.jsonl` against its first
     parent (today's rule), or (b) it is a merge commit whose subject starts with the refresh prefix defined in Step 3
     and whose tree equals what merging its second parent into its first parent would produce, ledger files excepted.
   - Checking (b) cheaply: the diff from its first parent, restricted to non-ledger paths, equals the diff from
     `merge-base(first, second)` to `second` on those paths. Use `git diff --quiet` comparisons with pathspec excludes.
   - The prefix constant lives in a shared non-flow module (`sandbox_executor/ref_names.py` or `plan_paths.py`), so
     neither package imports the other's stage module. If neither fits, the constant is duplicated, with a test
     asserting both copies are equal.
2. Keep the helper within the complexity limits. Add a private `_is_refresh_merge(repo, commit)`.
3. Update the partial_resume module docstring.
4. **Fallback (if the hypothesis fails or exceeds its cost):** leave the lineage rule unchanged. Have
   `plan_refresh_stage_failure` log that a resumable partial branch forked before the refresh will restart from the
   refreshed plan tip, and document this in `docs/git_flow.md`. This trades lost partial work for correctness in a rare
   case.

- **Is Bottleneck:** NO

  discipline.
- **Potential failure modes for this step:**
