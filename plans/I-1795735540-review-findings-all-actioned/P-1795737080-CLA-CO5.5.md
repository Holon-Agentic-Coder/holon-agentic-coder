## Plan Description & Strategy

Re-apply the previously built and verified Stage 4 finding-outcome gate on this plan's execution branch, with a touch
set that covers all of its fallout. The gate design:

1. `review_finding_outcomes.py` (new, about 43 lines) contains pure functions:
   - `REQUIRED_VERDICTS = 3`.
   - `is_disposed`: applied needs a non-empty `commit_sha`; rejected needs `has_stated_reason(rejection_reason)`.
   - `undisposed_finding_ids`: matches findings to dispositions by `finding_signature` and lists each undisposed id
     once.
   - `returned_verdict_count`: counts COMPLETED reviewers.
   - `verdict_count_ok`.
   - `with_commit`: stamps the pushed head SHA on applied dispositions.
2. `flow/review/verdict.py` turns these into consensus blockers through `_verdict_count_blocker` and
   `_finding_outcome_blockers`. The blocker text names the verdict count, or the finding ids.
3. `flow/review/approval_gates.py` `record_iteration_gates` adds the verdict-count blocker to the diff gate, so a
   consensus that is not exactly three verdicts records no approved diff gate.
4. `flow/review/loop.py`:
   - After `reviewer_objected`, it adds the outcome blockers. It passes the merged findings
     (`merge_findings(iter_findings, carried_rows)`) and every recorded disposition (all, pending, and the rejected
     history).
   - When recording applied fixes, it stamps them with the resolver's pushed head SHA.
5. Tests:
   - Unit tests cover the new module, including a fake loop that leaves a nit and a surviving mutant without an outcome.
   - Consensus-integrity tests cover two verdicts, four verdicts, one unresolved finding, and a complete three-verdict
     approval.
   - Approval-gate tests cover a blocked consensus.
   - Loop tests cover an undisposed finding.
   - Existing loop and approval tests move to three-reviewer ensembles (`review_fakes.with_clean_peers`).
   - The self-doc module registry gets the new module and its count goes from 146 to 147.
