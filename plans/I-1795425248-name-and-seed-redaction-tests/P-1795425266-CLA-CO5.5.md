## Step 2: Add `seeded_secrets.py`, the seeded fake-credential generator

- **Sub‑intent recommendation:** NO
- **Reasoning:** One new test-support module of about 60 to 90 lines, no product code; low risk, reusable by both files.
- **Step Type:** IMPLEMENTATION
- **Exploration level:** EXPLOIT

### Intent & Git Integration

- **Step Intent:** Give both test files one reproducible source of fake credentials and fake temp names, with a fixed
  default seed, an environment override and a stress mode, and a standard way to name the seed in failure messages.
- **Git branch:** same execution branch as Step 1
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. Create `apps/sandbox-executor/tests/seeded_secrets.py` with a module docstring that states the contract: a fixed
   default seed (a named constant, for example `DEFAULT_SEED = 0`), override through the `CREDENTIAL_TEST_SEED`
   environment variable (an integer), and stress mode when that variable is `random`, which draws a fresh seed from
   `secrets.randbits(32)` once per process and still reports it. Explain why `random.Random`, not `secrets`, is used:
   these are fake values whose only requirement is reproducibility.
2. Provide `resolve_seed()` returning the integer seed (raising a clear `ValueError` naming the variable on a
   non-integer value other than `random`), memoised per process so every test in a worker sees the same seed in stress
   mode.
3. Provide `generator(label)` returning a fresh `random.Random` derived from the resolved seed and a stable label string
   (for example the test or matrix name), so each test's draws are independent of collection order and of which xdist
   worker runs it. Derive with a stable hash of `f"{seed}:{label}"` (for example `hashlib.sha256`), never the salted
   built-in `hash`.
4. Provide `seed_note()` returning a short string such as `seed=<n> (set CREDENTIAL_TEST_SEED=<n> to reproduce)`, to be
   appended to every assertion message that names a failing case id, so a failure prints the seed and the case id.
5. Provide `name_sequence(rng)` returning an infinite iterator of 8-character names over tempfile's own alphabet
   (`abcdefghijklmnopqrstuvwxyz0123456789_`) drawn from the given generator, as the seeded replacement for
   `tempfile._RandomNameSequence()` in `_colliding_temp_names`.
6. Keep public functions typed and docstringed (world ruleset §2), and every function far inside the ruff complexity
   limits; no `# noqa`.
7. Do not add a conftest hook; the seed is reported through the assertion messages, which keeps `conftest.py` out of the
   touch set.

- **Is Bottleneck:** YES (Steps 3 to 7 use it), but p_success is high.

- **Potential failure modes for this step:** per-test derivation accidentally depends on collection order, so a seed

- **Guardrails and early‑abort checks:** a quick local check that two processes with the same seed and label produce the

### Strategy Rationale

The intent is accepted as written. Its three parts are ordered by dependency: seeding must come before the reproduction
sweep (an unseeded sweep cannot name a reproducing seed), and the reproduction must come before the fix (the fix must
target the cause, and the pull request must quote the seed). Two clarifications keep the plan sound without reframing
it:

1. **The seed must cover the temp-name fallback, not only the credentials.** The flaky test forces a colliding first
   temp name, then falls back to an unseeded `tempfile._RandomNameSequence()`; because 2,480 cases share one `HOME`, the
   fallback is used constantly. Seeding only `secrets.choice` would leave the failure unreproducible.
2. **The seed variable is `CREDENTIAL_TEST_SEED`, not `HOLON_*`.** A `HOLON_*` name read from tests would still be a
   project name operators can mistake for product configuration, and if a workflow ever set it, the
   `test_environment_reference.py` drift guard would require a registry and docs entry; a neutral name keeps the touch
   set to the five scoped files.

Aggregation: entropy is the sum of the steps, `0.4 + 1.2 + 2.0 + 1.6 + 1.0 + 1.8 + 0.6 + 0.8 = 9.4`. Cost is the sum,
`1.0 + 2.0 + 3.0 + 3.0 + 1.5 + 2.0 + 2.5 + 1.5 = 16.5`, dominated by the two sweeps (about 1.5 hours of wall time
together). p_success is not the plain product of the steps (`about 0.36`), because Steps 4 and 5 have fallbacks (the
analytic, environment-driven route) that keep the plan alive when the Linux sweep does not reproduce; it is set near the
bottleneck chain Step 5 to Step 6 to Step 7, `0.78`. Impact 72 reflects removing a recurring cause of red CI on
unrelated pull requests (three so far, and merged-head CI can withdraw approvals) plus self-describing security test
names. Learning value 7 comes mostly from Steps 4 and 5. Overall:
`EV = 0.78 * 72.0 + 0.5 * 7.0 - 0.3 * 9.4 - 16.5 = 56.16 + 3.50 - 2.82 - 16.50 = 40.34`.

The macOS timing-ceiling overrun on #254 (674 s against 600 s) is noted but not targeted: the intent attributes it to a
slowdown spread across tests, and this plan only guarantees it adds no cost (seeded `random.Random` is cheaper than
`secrets.choice`, and no test is added to the hot doctor matrix). Splitting the 900-line URL file was considered and
rejected: test files are outside the module budget, and a split would bury the rename in a larger diff.

No sub-intents: the work is one coherent change to five test files at entropy 9.4, below the 15.0 budget, and its steps
share a single branch's state.
