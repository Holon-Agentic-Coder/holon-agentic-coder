### Strategy Rationale

Each self-explaining violation today costs one CI run plus one review iteration; six of six recent PRs hit it. Running
the same checker in the executor container before the branch is recorded converts that loss into a Stage 3 failure row
that names `path:line`, which the resume path and the agent can act on immediately, and the new prompt sentence tells
the agent the gate exists so it runs the check itself during its turn (the cheapest fix point).

Aggregation: `p_success` is the product of the two independent-ish implementation steps times the verification step,
`0.90 * 0.97 * 0.96 = 0.84`; the bottleneck is Step 1 (subprocess wiring, false positives from untracked files, ledger
row semantics). Entropy is the sum of step entropies `1.6 + 0.4 + 0.9 + 0.3 = 3.2`, far under the 15.0 budget. Impact is
judged qualitatively at 72 (recurring per-PR churn removed, but CI already catches the defect so it is a cost, not a
correctness, win). Cost is the sum of step costs `4.5 + 0.8 + 2.5 + 1.2 = 9.0`.
`EV = P * Impact + mu * LV - lambda * Delta_S - Cost = 0.84 * 72.0 + 0.5 * 3.0 - 0.3 * 3.2 - 9.0 = 60.48 + 1.50 - 0.96 - 9.0 = 52.02`,
rounded down to 51.0 for the untested host-resume interaction.

Strong assumptions: the mounted worktree carries `origin/main` (the pre-push sync already relies on `origin/<target>`),
and the repository being executed on ships `scripts/check_self_explaining.py` (when it does not, the gate is skipped
with a notice so non-holon target repositories keep working).

Deferred follow-up (not in scope, recorded for a later intent): feed the violation output to the existing `FixRunner`

## Plan Description & Strategy

Wire the existing self-explaining checker into Stage 3 publishing:

1. `pre_push.py` gains a module-level function that runs `scripts/check_self_explaining.py --root <repo_dir>` with
   `sys.executable` in `repo_dir`, and a `PrePushSteps.self_explaining_gate()` step that `record_branch` calls after the
   attribution check and before `pre_push_sync`. A violation prints the checker's `path:line` lines to stderr, appends a
   superseding `failure` row whose summary lists the violations, commits that row on the execution branch, sets the
   in-memory execution status to failure, and returns `False`, so the branch is not recorded, not synced and not pushed.
2. One sentence is added to rule 10 of `holon-config/prompts/executor.template.md` telling the executor that Stage 3
   runs the check before the push.
3. A new test module drives the step against real temporary git repositories (bare origin plus clone, the real checker
   scripts copied in) for the docstring, `# why:`-only and prompt-render cases.
4. Run the affected tests, then the full suite once, then lint, all in the foreground.

No environment variables, cwd defaults or git config are set, overlaid or removed for any child process: the checker
child inherits the executor's environment unchanged and runs with `cwd=repo_dir`, which is the same cwd every other
pre-push git child already uses. The Environment Overlay Discipline therefore does not apply; the test in Step 3 still
runs the real checker child (and its `git` grandchildren) so its behaviour under the executor environment is exercised.

- **Git branch:** `I-1795741002-self-explaining-gate-pre-push` (execution branch of this plan)

### Implementation Details (No code blocks, only logic/steps)

1. In `pre_push.py` add constants for the checker path relative to the repo (`scripts/check_self_explaining.py`), the
   violation exit code (1), a timeout (reuse a generous value such as 600 seconds, since the checker may fetch
   `origin/main` with its own 300-second timeout) and a cap on how many violation lines go into the ledger summary (for
   example 20).
2. Add `run_self_explaining_check(repo_dir) -> tuple[bool, str]`:
   - Script absent under `repo_dir`: print a notice and return `(True, notice)`.
   - Run `[sys.executable, <script>, "--root", repo_dir]` via `subprocess.run` with `cwd=repo_dir`,
     `capture_output=True`, `text=True`, `check=False`, the timeout; no `env=` argument (inherit unchanged).
   - Exit 0: return `(True, stdout)`.
   - Exit 1: keep only violation lines (`<path>:<line>: added ...`) whose path is tracked in `HEAD`
     (`self.repo`/`GitRepository` `ls-files` or `git ls-files` via `_get_repo(repo_dir).run`); if none remain, print a
     notice that only untracked files were flagged and return `(True, ...)`; otherwise return `(False, joined lines)`.
   - Any other exit code, `OSError` or `subprocess.TimeoutExpired`: print a warning naming the exit code (redacted with
     `redact_agent_secrets`) and return `(True, warning)`. Add a `# why:` comment stating CI is the fail-closed gate and
     a container without `origin/main` must not block every push.
   - Extract the tracked-path filter into its own small function (for example `violations_on_tracked_paths`) to keep
     every function under ruff complexity limits.
3. Add `PrePushSteps.self_explaining_gate(self) -> bool`:
   - Return `True` without running when `self.exec_entry.get("status") != "success"` (salvaged partial work must stay
     publishable for resume).
   - Call the module function through the facade-free module name (tests patch nothing here; they drive it for real).
   - On failure: print `Error: Self-explaining check failed before push:` followed by each violation line to stderr,
     append `superseding_failure_row(self.exec_entry, summary)` (import from
     `sandbox_executor.entrypoint.sync_conflict`) with a summary such as "Pre-push self-explaining check refused the
     branch: <capped violation lines>. Remove the added docstrings and comments, or turn a needed reason into a '# why:'
     comment.", add `failure_reason` `self_explaining_violation`, write it with `atomic_ledger_append` to
     `executions.jsonl` under `self.ledger_dir`, stage it with `ledger_commit_paths` and commit with message
     `execute: record self-explaining refusal for <exec_id>` (`check=False`), mirroring `record_sync_failure`. If that
     helper body grows past ~15 lines, put the row writing in a separate function `record_self_explaining_refusal(...)`
     in `pre_push.py`.
   - Set `self.exec_status = "failure"` so `_exit_with_status` prints the stage as failed; return `False`.
4. In `record_branch`, after the attribution check and before `self.pre_push_sync()`, add
   `if can_record: can_record = self.self_explaining_gate()`. Keep the existing refusal message.
5. Before finishing, read `sandbox_executor/flow/execution_publish.py` and the Stage 3 failure handling to confirm a
   branch whose tip carries a superseding `failure` row is treated as a failed Stage 3 run (the same way a sync failure
   is). If it is not, record the gap in the execution notes rather than widening the touch set.
6. Write no docstrings and no comments other than the one `# why:` line.
