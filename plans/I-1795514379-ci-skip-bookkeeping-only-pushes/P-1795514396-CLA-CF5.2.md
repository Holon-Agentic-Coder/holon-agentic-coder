### Current behaviour (read on `main` at `601297f4`)

Six workflows run on every `pull_request` event of type `opened`, `synchronize`, `reopened`, `labeled` and `unlabeled`,
on pushes to `main` and on manual dispatch: `test-unit.yml` (job `unit`, Ubuntu and macOS), `test-integration.yml` (job
`integration`), `test-hygiene.yml` (job `hygiene`), `test-stress.yml` (job id `workspace-survival`, name
`Workspace survival`), `make.yml` (job `build`, Ubuntu and macOS) and `docker-build.yml` (job `build`). None of them
looks at which files changed. One composite action exists, `.github/actions/ci-timing-gate/action.yml`; it shows the
house style (inputs passed through `env`, `shell: bash`, a call to a script under `scripts/` with `python3`).

### Target behaviour

In every job the order of steps becomes: the existing "Record job start time" step where the job has one, then the
checkout, then the new step `Bookkeeping gate` (`id: bookkeeping`), then the existing steps, then the new last step
`Full run completed`. The gate step writes one output, `skip`, which is `true` or `false`.

The gate says "skip" only when all of the following hold. The rule name in brackets is what the gate prints when the
check decides for a full run.

1. The event is `pull_request` (`event-not-pull-request`), and it is the first attempt of the run (`rerun-attempt`).
2. The action is `synchronize`, `labeled` or `unlabeled` (`action-not-eligible`).
3. For a label event, the label is not result-affecting (`result-affecting-label`). For `synchronize`, the payload names
   a previous head that is not empty and not all zeros (`missing-previous-head`). The payload also names the head SHA
   and the head branch, and the environment names the workflow file and the run number (`incomplete-event`).
4. For `synchronize`, the compare answer for `before...head` has the status `ahead` (`force-push-or-diverged`), lists
   fewer than 300 files (`diff-too-large`), and every listed path, including the old name of a rename, lies under
   `plans/`, `executions/` or `holon-knowledge/` (`non-bookkeeping-change`, with the first offending path). A path lies
   under a root only when its first whole component is the root and something follows it, so `plans_helper.py`,
   `src/holon-knowledge-tool.py` and a file named `plans` are not bookkeeping.
5. The walk through earlier runs of the same workflow on the same branch finds a real success of the same job. The walk
   starts at the newest earlier run. That run must be on the previous head (for a label event: on the current head),
   otherwise `previous-run-missing`. Each run visited must be finished (`previous-run-not-finished`), must hold exactly
   one job that matches (`previous-run-missing`), and that job must have concluded `success`
   (`previous-run-not-successful`, with the conclusion, for example `failure` or `cancelled`). A matching job with a
   successful marker step ends the walk. A matching job whose marker step was skipped sends the walk to the next older
   run. A matching job without a marker step ends in `previous-run-unverified`. More than 20 hops end in
   `chain-too-long`; a list that ends first ends in `previous-run-missing`.
6. When the real success is on another commit than the one already compared in point 4, one more compare call for
   `real-success-head...head` must pass the same three checks of point 4.

Any exception on the way prints `api-error` with the exception's class name and runs the full job. The two "skip" rules
are named `bookkeeping-only` (for `synchronize`) and `label-not-result-affecting` (for label events). The gate prints
one line, for example `bookkeeping-gate: decision=RUN rule=non-bookkeeping-change detail=scripts/x.py`, and adds the
same line to the step summary.

A job is matched by name, not by position. The workflow passes its job's base name (`unit`, `integration`, `hygiene`,
`Workspace survival`, `build`) and, for a matrix job, the runner label. A job of an earlier run matches when its name
equals the base name, or starts with the base name followed by a space and an opening bracket and, when a runner label
was passed, holds that label as one of the comma-separated values inside the brackets. This accepts both
`unit (ubuntu-latest)` and `unit (ubuntu-latest, 120)`, so the plan does not depend on how GitHub prints matrix values
that an `include` entry adds.

On a skip, every step after the gate is skipped except the cheap ones on a short allow-list, and the job ends green in
seconds. The hygiene job is the exception the intent asks for: on a skip it still sets up Node.js and runs
`make lint-json` (jq over every JSON and JSONL file) and `make lint-md` (Prettier over every markdown file). Both cover
the whole repository, so they cover the changed bookkeeping files without a list of changed files.

### Implementation Details (No code blocks, only logic/steps)

- Conventions for both modules (the same as `scripts/ci_durations_api.py`): a module docstring that states the contract,

  no language feature newer than the ones `scripts/ci_timing_gate.py` already uses (no `match`, no

- Create `scripts/ci_bookkeeping_api.py`:
  - `GateClient`, a frozen dataclass with `repo`, `token` (hidden from `repr`) and `opener` (default `default_opener`).
    Its method `get_json(path)` requests `{API_ROOT}/repos/{repo}/{path}` through `build_request` and returns the
    decoded JSON object. It raises `ValueError` when the answer is not a JSON object.
  - `Comparison`, a frozen dataclass with `status`, `paths` (a tuple of strings) and `truncated`. The function
    `compare(client, base, head)` calls `compare/{base}...{head}`. `paths` holds each file's `filename` and, when
    present, its `previous_filename`. `truncated` is true when the list holds `COMPARE_FILE_CAP` (300) entries or more.
    A `files` value that is not a list, or an entry without a text `filename`, raises `ValueError`.
  - `RunRef`, a frozen dataclass with `run_id`, `run_number`, `head_sha` and `status`. The function
    `list_earlier_runs(client, workflow_file, branch, before_run_number)` calls `actions/workflows/{workflow_file}/runs`
    with `event=pull_request`, the branch (URL-quoted with no safe characters, because branch names here contain `/`)
    and `per_page=100`. It keeps the runs whose `run_number` is below `before_run_number` and returns them sorted by
    `run_number`, highest first. It reads one page only.
  - `list_jobs(client, run_id)` calls `actions/runs/{run_id}/jobs?per_page=100` and returns the `jobs` list (the latest
    attempt of each job, which is the API default). A value that is not a list raises `ValueError`.
- Create `scripts/ci_bookkeeping_chain.py`:
  - Constants `FULL_RUN_STEP = "Full run completed"` and `MAX_CHAIN_HOPS = 20`. Each rule name of this module is a
    module-level constant, and the tuple `CHAIN_RULES` lists them all, so that the README test of Step 4 can read them.
  - `JobQuery`, a frozen dataclass with `workflow_file`, `branch`, `job_name`, `os_name`, `run_number` (of the current
    run) and `target_sha` (the commit the newest earlier run must be on).
  - `match_job(jobs, job_name, os_name)` returns the one job whose name equals `job_name`, or starts with `job_name`
    plus a space and an opening bracket and ends with a closing bracket and, when `os_name` is not empty, holds
    `os_name` among the comma-separated values inside the brackets. It returns `None` for no match and for more than one
    match.
  - `classify_job(job)` returns one of four words. `not-successful` when the job's `status` is not `completed` or its
    `conclusion` is not `success`. Otherwise it looks at the steps named `FULL_RUN_STEP`: none gives `unverified`; a
    step with the conclusion `success` gives `real-success`; a step with the conclusion `skipped` gives `gate-skipped`;
    anything else gives `not-successful`.
  - `ChainResult`, a frozen dataclass with `real_sha` (text or `None`), `rule` and `detail`.
  - `find_real_success(client, query)` implements point 5 of the target behaviour and returns a `ChainResult`. Its rule
    names are exactly `previous-run-missing`, `previous-run-not-finished`, `previous-run-not-successful` (detail: the
    conclusion), `previous-run-unverified`, `chain-too-long` and, with `real_sha` set, `previous-run-succeeded`. It does
    not catch exceptions; the caller in Step 2 turns them into `api-error`. Keep the per-run decision in a helper so
    that no function has more than six `return` statements.
- Create the test helper `apps/sandbox-executor/tests/ci_bookkeeping_fakes.py` (new test file, declared here):
  - `FakeGitHub`: built from compare answers keyed by `(base, head)`, a list of runs and a mapping from run id to jobs.
    Calling it with a request returns the JSON bytes for the three URL shapes above. It records every requested URL,
    raises a configured exception for a configured URL part, and raises `AssertionError` for an unknown URL.

  chain's rule when no real success was found; the diff rule on `real_sha...head_sha` when `real_sha` is neither the
  commit already compared nor the head itself; and only then the "skip" `Decision` (`bookkeeping-only` or
  `label-not-result-affecting`, with the number of changed files and the real success commit as detail).
