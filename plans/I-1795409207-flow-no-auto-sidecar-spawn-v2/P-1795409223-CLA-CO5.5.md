### Findings from the planning read (verified against the current tree)

1. `launcher/coherence.py::detect_holon_coherence` checks tiers in this order: explicit opt-out, explicit opt-in
   (argument, `HOLON_TOKEN_REDUCE`, `HOLON_PASSIVE_MONITORING`), TCP port probe (`_proxy_port_reachable`), Docker image
   probe (`_coherence_image_present`, which runs `docker image inspect` on holon-coherence and
   `mitmproxy/mitmproxy:12.2.3`), and CLI binary probe (`_coherence_binary_present`).
2. `flow/context.py::FlowContext.__post_init__` (line ~184) sets `token_reduce = sidecar.detect_holon_coherence()`
   whenever `token_reduce is None`. `cli/commands/flow.py::_build_flow_context` (line ~269) calls
   `cli.detect_holon_coherence(bool(args.token_reduce or args.mitm_web))`, and `_update_flow_context` only ever flips
   `token_reduce` to True on resume.
3. `flow/dispatch.py` forwards `token_reduce=bool(context.token_reduce)` to `launcher/role_dispatch.py`, then
   `launcher/containers.py::ContainerLaunch.run`, then
   `launcher/sidecar.py::get_token_reduction_mounts_and_envs(token_reduce=…)`. In that function a truthy `token_reduce`
   always takes the `setup_token_reduction_proxy()` branch, which spawns the sidecar (`docker network create` plus
   `docker run`). Only an env-only opt-in (`HOLON_TOKEN_REDUCE=1` with the flag off) takes
   `proxy_attach._attach_external_proxy()`.
4. Consequence: on the flow path, every detection tier, including the port-probe tier the goal wants to keep, is turned
   into a sidecar spawn. Restricting detection to tiers 1–3 is therefore necessary but not sufficient. The flow needs a
   separate "attach only" signal that reaches the launcher.
5. The per-stage commands are strictly explicit (`cli/commands/intent.py:65` passes
   `token_reduce=bool(args.token_reduce)`). Their launcher path is the same `get_token_reduction_mounts_and_envs`.
   Adding an optional, default-False `proxy_attach` keyword leaves per-stage behaviour unchanged.
6. Out-of-scope inconsistency: `cli/commands/review.py:184` (the per-stage `review-loop` command) also calls the full
   `detect_holon_coherence`. The intent says to keep per-stage behaviour unchanged, so this plan does not touch it and
   records it as a follow-up.
7. Module budgets: `flow/context.py` is 264 lines against a frozen 280-line override, leaving 16 lines of headroom. All
   other touched source modules are outside the budgeted `flow` package (`launcher/*`, `cli/*`) or have large headroom
   (`flow/review/loop.py` 952, `flow/stages/review.py` 305, `flow/stages/children.py` 330). `flow/dispatch.py` (81
   lines) is under the 200 default.

### Strategy

- Add one flow-specific resolver in `launcher/coherence.py` that only ever evaluates tiers 1–3 and returns two separate
  booleans: `spawn_sidecar` (explicit CLI flag only, exactly like the per-stage commands) and `attach_running_proxy`
  (port probe hit, not opted out).
- Carry `attach_running_proxy` as a new `FlowContext.proxy_attach` field and dispatch it to the launcher as an optional
  `proxy_attach` keyword. The launcher may then only call `_attach_external_proxy()`, never
  `setup_token_reduction_proxy()`.
- `HOLON_TOKEN_REDUCE=0` forces both booleans False in the resolver, before any probe runs. The launcher already
  enforces it through `_token_reduce_opt_in`, which stays the second guard.
- The existing `detect_holon_coherence` stays unchanged for its non-flow caller (`review.py`), so no per-stage behaviour
  changes.
- Investigate the role-container connectivity failure in a time-boxed, read-mostly step and report the result in the
  execution report.

## Step 1: Investigate why a role container on the sidecar network cannot reach the sidecar after the host readiness probe passes

- **Sub‑intent recommendation:** NO
- **Reasoning:** This step only reads code and logs and produces a report. It changes no source, is capped in cost, and
  does not block the fix, so a separate branch or evaluation adds overhead without lowering risk.
- **Step Type:** INFO_GATHERING
- **Exploration level:** EXPLORATORY

- **Hypothesis being tested:** The host-side probe (`proxy_readiness.wait_for_proxy("127.0.0.1", <published port>)`
  through Docker's loopback publish) and the role container's path (Docker embedded DNS name `holon-proxy-<pid>-<uuid>`,
  port 8080, on network `holon-net-<pid>-<uuid>`) exercise different routes. One of these candidate causes breaks only
  the container route:
  - H1: the process or container that actually makes the failing request is not attached to `holon-net-*`. Examples: a
    nested or second container inherits the forwarded `HTTP(S)_PROXY` env, or a `--network` flag is overridden. This
    gives "Failed to connect" (or "Could not resolve proxy") for the sidecar host name.
  - H2: the sidecar is gone by the time the role container connects. Possible reasons:
    `_release`/`teardown_token_reduction_proxy` runs from another launch through the module-global `_sidecar_state`, the
    pipeline `finally` teardown, or an OOM under `--memory=256m`.
  - H3: the proxy URL host name given to the container does not match the sidecar's container name or network alias. For
    example, the error names `holon-proxy` without the per-run suffix, which points to a stale or default
    `HOLON_PROXY_URL` forwarded through the `HOLON_*` env file.
  - H4: Docker Desktop (linuxkit) specifics: the readiness probe goes through the host loopback publish, while
    container-to-container traffic is blocked or still pending on a freshly created user-defined bridge.
- **Learning target:** a CONFIRMED cause (code-path proof or reproduction) or a ranked, evidence-backed hypothesis, plus
  the minimal fix shape for a follow-up intent.
- **Maximum acceptable cost for this learning:** about 4 cost units (no more than 25 % of plan cost). Stop when reached
  and report whatever evidence exists.

### Strategy Rationale

- **Why reframe:** The intent's own diagnosis covers the image and binary tiers. The planning read showed a second,
  equally important defect: `FlowContext.token_reduce=True` is always dispatched as an explicit spawn request
  (`sidecar.get_token_reduction_mounts_and_envs` takes `setup_token_reduction_proxy` for any truthy `token_reduce`).
  Just dropping tiers 4–5 would leave the port-probe tier still spawning a sidecar, which breaks the goal
  "auto-detection may only attach … never spawn". A separate `proxy_attach` signal is the smallest change that satisfies
  both goals. Per-stage commands are unchanged because the new launcher keyword defaults to off.
- **Alternatives rejected:**
  - Setting `HOLON_TOKEN_REDUCE=1` in the process env on auto-detect: global mutation, which also leaks through the
    `HOLON_*` env-file forwarding into role containers.
  - Re-exporting the resolver via `cli/__init__`: grows the CLI facade for no benefit.
  - Changing `detect_holon_coherence` itself: it would silently change the per-stage `review-loop` command, which the
    intent says to keep unchanged.
- **Aggregation:**
  - Entropy is the sum of the step entropies: `0.5 + 1.2 + 2.0 + 2.0 + 1.0 + 0.3 = 7.0`.
  - Cost is the sum: `4.0 + 2.5 + 3.5 + 3.5 + 3.0 + 2.0 = 18.5`.
  - p_success is a qualitative judgement. The steps that matter for the deliverable are Steps 2–6. Their naive product
    `0.93 * 0.88 * 0.87 * 0.90 * 0.85 = 0.545` understates success because the failures are strongly correlated (one
    design, one test session) and each step has a re-plan path. Step 1 is excluded because its failure only lowers the
    score on the secondary goal. 0.78 was chosen.
  - Bottleneck: Step 4, because of the frozen 280-line budget for `context.py` and the resume semantics change.
  - Impact: 75, a qualitative total for the whole intent (fix, tests and root-cause report).
  - Learning value: 4.5, weighted toward Step 1.
  - EV: `EV = 0.78 * 75.0 + 0.5 * 4.5 - 0.3 * 7.0 - 18.5 = 58.50 + 2.25 - 2.10 - 18.50 = 40.15`.
- **Strong assumptions:**
  - No per-stage command passes `proxy_attach`, verified by grep: `dispatch_role_agent` callers are `flow/dispatch.py`
    and the per-stage commands, which pass only `token_reduce` and `mitm_web`.
  - The `flow/context.py` budget (280) has room for about 4 added lines.
  - The executor may lack a Docker daemon, which is accepted for Step 1.
