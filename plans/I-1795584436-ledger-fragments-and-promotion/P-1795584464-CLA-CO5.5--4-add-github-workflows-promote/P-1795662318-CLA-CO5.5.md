## Safety & Constraint Alignment

- **Key world ruleset constraints that affect this plan:**
  - `holon-config/world/constraints.md` §3 Ledger Immutability: only appends; the workflow runs `holon ledger promote`,
    which appends verbatim and deletes only pending fragments.
  - `holon-config/world/constraints.md` §1 Commit Boundaries: the agent commits only to this plan's branch; the
    workflow's push to `main` happens in GitHub Actions after a human merges the root intent.
  - `docs/safety.md` §5: governance changes need human approval; the bot token is maintainer-provided and its absence
    makes the workflow a green no-op.
  - Module budgets (`holon-config/hygiene/module_budgets.json`) are frozen and not touched; they apply only to the
    `flow` package, so `env_registry.py` growing by ~15 lines is fine.
- **Potential violations or edge cases:**
  - A promotion run rewriting something outside `holon-knowledge/ledger/` (e.g. a stray generated file) and pushing it
    to `main`.
  - An infinite loop: the bot's push to `main` re-triggering the workflow.
  - Two runs racing to push (`concurrency` prevents overlap within the repo, but a human merge can land between fetch
    and push).
  - The secret leaking into logs, or the input/secret interpolated into a shell script.
  - A rebase conflict on a canonical `.jsonl` during the retry.
- **Mitigations built into the plan:**
  - A path guard step lists every changed path (`git status --porcelain -uall`, including deletions and untracked) and
    fails the job if any path does not start with `holon-knowledge/ledger/`; only then is anything staged, and staging
    is limited to that pathspec.
  - The job is skipped when the triggering push's head commit carries the fixed promotion marker in its message, and the
    bot's commit always carries it.
  - `concurrency: {group: promote-ledger, cancel-in-progress: false}` serialises runs without killing a run mid-push.
  - Push retry: at most 3 attempts, each failure followed by `git fetch origin main` and `git rebase origin/main`; a
    rebase conflict aborts the rebase and fails the job loudly rather than resolving anything.
  - The token is passed only through `env:` and the checkout `token:` input, never echoed; secret presence is tested via
    an env variable comparison, never printed.
- **Residual risk accepted (and why):** The workflow cannot be run end to end in this sandbox (no GitHub runner); its
  first real run happens after merge. The structural test plus the no-op default (no secret configured means nothing is
  pushed) keep the blast radius at zero until a maintainer opts in.

### Implementation Details (No code blocks, only logic/steps)

1. `name: Promote Ledger`. Triggers (`on:`): `push` with `branches: [main]` only (keeps
   `test_push_trigger_stays_on_main` green), `schedule` with one daily cron (e.g. `"41 3 * * *"`, off the hour and away
   from `ci-durations.yml`'s `23 4`), and `workflow_dispatch` with an optional `force` boolean input (default false). No
   `pull_request` trigger, so `test_ci_bookkeeping_wiring` and `test_workflow_triggers` pull-request rules do not apply.
2. Top-level `permissions: contents: read` (the write happens through the bot token, not `GITHUB_TOKEN`), plus
   `actions: read` if the timing-gate composite action needs it (check `ci-durations.yml`, which uses the same gate with
   `actions: read`, `contents: read`; copy that).
3. `concurrency: group: promote-ledger`, `cancel-in-progress: false`.
4. One job `promote` on `ubuntu-latest`, `timeout-minutes: 15`, with a job-level
   `if: github.event_name != 'push' || !contains(github.event.head_commit.message, '[ledger-promote]')` so the bot's own
   promotion commit does not re-trigger a promotion. Job-level
   `env: HOLON_LEDGER_BOT_TOKEN: ${{ secrets.HOLON_LEDGER_BOT_TOKEN }}`.
5. Steps in order:
   - `Explain a missing bot token` with `if: env.HOLON_LEDGER_BOT_TOKEN == ''`: prints a `::notice::` line saying the
     `HOLON_LEDGER_BOT_TOKEN` secret is not configured, so promotion is skipped and the run stays green, and points at
     `.github/workflows/README.md`. Every later step carries `if: env.HOLON_LEDGER_BOT_TOKEN != ''`, so the job ends
     green without doing anything.
   - Checkout (`actions/checkout@v7`, same major as the other workflows) with `ref: main`, `fetch-depth: 0`,
     `token: ${{ secrets.HOLON_LEDGER_BOT_TOKEN }}`.
   - `CI Timing Gate (Start)` via `./.github/actions/ci-timing-gate` (keeps the README's "every job of every workflow
     ends with the CI timing regression gate" true); runs unconditionally after checkout is available — if the gate
     needs the checkout, gate it on the token too and keep the final check `if: always()` only when the token is set.
     Mirror `ci-durations.yml` exactly.
   - Install uv with `astral-sh/setup-uv@v8.3.0` (the pinned version in `test-unit.yml`) and `uv sync --locked`.
   - `Promote pending ledger fragments`: `uv run holon ledger promote` plus `--force` when the dispatch input is true;
     the input reaches the shell through `env:` (`FORCE: ${{ inputs.force || false }}`), never interpolated into the
     script (same pattern and comment as `ci-durations.yml`).
   - `Fail on changes outside holon-knowledge/ledger/`: collects `git status --porcelain=v1 -uall` paths (handle rename
     `->` by taking both sides), prints each offending path and exits 1 if any does not start with
     `holon-knowledge/ledger/`; sets a step output `changed=true|false`.
   - `Commit and push the promotion` (`if:` token set and `changed == 'true'`): sets a bot git identity
     (`holon-ledger-bot`), `git add -A -- holon-knowledge/ledger`, commits with the message
     `chore(ledger): promote pending fragments [ledger-promote]`, then a bounded loop of 3 attempts:
     `git push origin HEAD:main` succeeds → exit 0; on failure `git fetch origin main` and `git rebase origin/main` (on
     rebase failure: `git rebase --abort`, print an error, exit 1), sleep a few seconds, retry. After the third failure
     exit 1.
   - `CI Timing Gate (Check <= 10 min)` with `if: always()` and the token condition, mirroring `ci-durations.yml`.
6. Write the marker `[ledger-promote]` and the bot name as YAML values once each so the Step 4 test can compare the job
   `if:` marker with the commit message marker.
7. Use only `HOLON_LEDGER_BOT_TOKEN` as a `HOLON_*` name in the file (no `HOLON_LEDGER_PROMOTE_EVERY` override; the
   command's default threshold applies), so Step 2 registers exactly one new name.
