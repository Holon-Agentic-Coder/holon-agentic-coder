### Strategy Rationale

The bug is behavioural drift. `holon calibrate` calls `run_calibrate` only. The flow's `_calibrate_execution_branch`
also reconciles and promotes inline, in one function that carries `# noqa: C901, PLR0912, PLR0915`. The fix extracts
these three steps into one Stage 5 core module (`flow/stage5.py`), and both entry points call it:

- `run_stage5(context, steps, verdict, report_only)` returns a `Stage5Outcome`.
- `Stage5Outcome` holds the report dict, the reconciliation status and verdict, and the newly promoted candidates.
- The step callables come from `Stage5Steps`. The function that builds them, `stage5_steps()`, lives in
  `flow/stages/calibrate.py`.

The flow already knows the execution verdict from its Stage 3 result. The CLI has no stage results, so a small sibling
module (`flow/stage5_verdict.py`) reads the verdict from the execution's latest summary row in `executions.jsonl`. It
returns None when there is no row, and the core then skips reconciliation and promotion rather than guess.

The core makes re-runs idempotent by checking for an existing `reconciliation` event for the execution branch before it
appends one. `promote_pending_candidates` already promotes only new candidates.

The previous attempt shows that `flow/__init__.py` must register the new modules' public names in `_LAZY_EXPORTS` and
`__all__`. Existing package-export tests require this. The file has a module budget of 562 lines (currently 477), so
adding about 10 lines stays within it.

Aggregation: overall `p_success` is set by the bottleneck, Step 2 (flow-stage refactor, 0.88), discounted for the
residual touch-set risk, giving 0.85. Entropy is the sum of the step entropies: `1.8 + 2.0 + 1.6 + 2.2 + 1.2 = 8.8`.
Cost is the sum of the step costs: `3 + 3.5 + 2 + 4 + 1.5 = 14.0`. Impact is the intent-level value (70) and is not

### Implementation Details (No code blocks, only logic/steps)

1. Create `flow/stage5.py` with the following:
   - A frozen dataclass `Stage5Steps` holding these step callables:
     - `calibrate`
     - `reconcile`
     - `promote`
     - `commit_reconciliation`
     - `commit_promoted`
     - `warn_ledger_failure`
     - an optional `on_calibrate_error`. The flow passes its fallback-report builder here. When it is None, the
       exception re-raises, so the CLI fails loudly.
   - A dataclass `Stage5Outcome` with these fields:
     - `report_dict`
     - `calibration_succeeded`
     - `report_only`
     - `reconciliation`, a dict of `status`, `verdict` and `rows_appended`
     - `promoted_candidates`

     It also has a `newly_promoted_count` property and a `to_json_dict()` method that returns `mode`, `reconciliation`
     and `newly_promoted_count`.

   - `run_stage5(context, steps, verdict, report_only=False)`:
     - It calls `steps.calibrate` with `skip_commit=context.dry_run`.
     - `LedgerRewriteError` and `CalibrationFormatError` always propagate.
     - With `report_only`, it returns `skipped_report_only` straight after the report.
     - Otherwise it reconciles, then promotes, and on any non-rewrite exception it routes to `warn_ledger_failure`.
   - The private helpers `_reconcile_execution` and `_promote_candidates` keep the current flow semantics:
     - `max_age_days=14` and `min_trials=2`.
     - The same ledger paths, `LEDGER_EXECUTIONS_REL` and `holon-knowledge/.index/action_index.db`.
     - The same log lines.
     - Commits happen only when calibration succeeded.
   - Reconciliation returns one of these statuses:
     - `skipped_no_commit` on a dry run or `--no-commit`
     - `skipped_no_ledger`
     - `skipped_no_verdict`
     - `already_recorded`
     - `recorded`
     - `left_uncommitted`
   - Promotion is skipped when the verdict is None.
   - `standalone_context(execution_branch, target_worktree, no_commit)` builds the minimal `FlowContext` the CLI uses.

2. Add idempotence with `_already_reconciled(ledger_path, execution_branch)`. It scans `executions.jsonl` for a row with
   `event_type == "reconciliation"` and `parent_action_id == execution_branch`, and parses each line defensively. Before
   writing this, confirm the actual field names that `reconcile_records` writes, in `knowledge/`. Match on those names
   if they differ.
3. Create `flow/stage5_verdict.py` with `resolve_execution_verdict(repo_dir, execution_branch)`:
   - It reads the ledger at the execution branch with `read_git_file`, then falls back to the copy on disk.
   - It filters summary rows with `is_matching_record`, takes the row from `latest_summary_row`, and maps
     converged-with-exit-0 to `success` and anything else to `failure`.
   - It returns None when there is no summary row.
4. In `flow/__init__.py`, add these registrations:
   - `_LAZY_EXPORTS` entries for `sandbox_executor.flow.stage5`
     (`Stage5Outcome Stage5Steps run_stage5 standalone_context`) and for `sandbox_executor.flow.stage5_verdict`
     (`resolve_execution_verdict`).
   - `stage5_steps` appended to the `flow.stages.calibrate` entry.
   - The matching `__all__` names, in sorted order.

   Do not change anything else in that file.

5. Keep every function within the ruff limits (`C901 <= 10`, `PLR0913 <= 5`). The core takes 4 positional parameters.
   Keep each new module under 200 lines.
