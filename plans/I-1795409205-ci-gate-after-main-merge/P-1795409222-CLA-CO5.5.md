### Strategy Rationale

The defect is a missing gate between two existing pieces: `_stage5_conflict_gate` (`flow/review/conflict_gate.py`)
merges `origin/<target>` into the execution branch and then returns `None`, so `run_calibrate_stage`
(`flow/stages/calibrate.py`) goes straight into `_calibrate_execution_branch`, which pushes calibration commits and only
afterwards checks CI on the final head (`check_final_head_ci`). The same gap exists when the head simply moved after
approval. The strategy is:

1. Put a pre-calibration "merged-head CI gate" in a new focused module that waits on the exact head SHA, treats
   cancelled/stale/superseded/skipped-required runs as not passed, re-triggers a cancelled run once per run id, and
   returns a record naming the SHA, run ids and conclusions.
2. Put "withdraw consensus" (append-only ledger row + once-per-head PR comment + reset of the Stage 4 counters) in a
   second new module, reusing the comment adapters of `flow/github/approval_invalidation.py`.
3. Wire both through `run_calibrate_stage` (which has headroom: 267 of 349 lines) and let the pipeline loop Stage 4 →
   Stage 5 through a third small module, because `pipeline.py` (427/431), `review/loop.py` (943/952), `ci_final_head.py`
   (342/344) and `conflict_gate.py` (194/200) are at their frozen module budgets and must not grow beyond a couple of

## Plan Description & Strategy

Execution order: probe (Step 1) → exact-SHA CI gate module (Step 2) → consensus withdrawal module (Step 3) → Stage 5
wiring in `calibrate.py` with the no-merge fast path (Step 4) → pipeline restart of Stage 4 (Step 5) → tests (Step 6) →
full verification (Step 7).

Behaviour after the change:

- Stage 4 approves head `A` (CI already waited for on `A` inside the loop).
- Stage 5 starts; `_stage5_conflict_gate` may merge `origin/main` and push merged head `M`.
- New: `run_calibrate_stage` resolves the current execution head. If it equals the approved head `A` (no merge, no move)
  the gate logs that it relies on the Stage 4 CI record of `A` and Stage 5 runs immediately as today. Otherwise it waits
  for every check run on exactly `M` to complete; on all-passed it logs `M`, run ids and conclusions and Stage 5
  continues (calibration commits pushed afterwards, then the existing final-head check runs on the calibrated head as
  today). On any failure it withdraws the consensus (ledger row + PR comment + counter reset) and returns a Stage 5
  result flagged `review_restart`, pushing nothing. On pending-at-budget-end or exhausted re-triggers it fails Stage 5
  closed without pushing.
- The pipeline sees `review_restart`, logs it, re-enters Stage 4 at iteration 1 for `M` with a fresh ensemble, and on a
  new approval re-enters Stage 5, up to the restart cap.

## Step 2: Add an exact-SHA CI check module and the merged-head CI gate

  completed and passed, with run ids and conclusions, treating cancelled or superseded runs as not passed.
- **Git branch:** execution branch of this plan

### Implementation Details (No code blocks, only logic/steps)

1. New module `flow/github/ci_head_checks.py` (target under 200 lines):
   - `probe_head_checks(repo_dir, sha, proxy_env)`: runs
     `gh api --paginate repos/{owner}/{repo}/commits/<sha>/check-runs` through `subprocess` with the same env, timeout
     and redaction pattern as `_gh_rerun` in `ci_final_head.py`; returns a list of plain dicts
     `{check_run_id, name, status, conclusion, head_sha, run_id}` where `run_id` comes from `parse_run_id(details_url)`;
     returns None on any error (fail-closed).
   - Drops every check run whose `head_sha` is not the requested SHA (superseded runs cannot leak in).
   - Keeps only the newest check run per check name (highest `check_run_id`), so a re-triggered run replaces the
     cancelled one rather than being masked by it.
   - `classify_head_checks(checks)`: returns `passed` only when the list is non-empty, every run has
     `status == completed`, and every conclusion is `success`, `neutral` or `skipped`; `pending` when any run is queued
     or in progress; `cancelled` when the only non-passing conclusions are `cancelled` or `stale`; otherwise `failed`
     (`failure`, `timed_out`, `action_required`, `startup_failure` and any unknown conclusion).
   - `rerun_cancelled(repo_dir, run_ids, proxy_env)`: dispatches `gh run rerun <run_id>` (whole run, not `--failed`,
     because a cancelled run has no failed jobs); False on any error.
2. New module `flow/review/merged_head_gate.py` (target under 200 lines):
   - `MergedHeadSeams` frozen dataclass of optional collaborators (probe, rerun dispatcher, policy, head reader),
     mirroring `FinalHeadSeams`, so arguments stay within `PLR0913 <= 5`.
   - `gate_merged_head_ci(context, repo_dir, head_sha, seams)`: polls `probe_head_checks` with the existing
     `CiWaitPolicy` clock/sleep on the review CI wait budget (`resolve_review_ci_wait_seconds`) plus the CI registration
     timeout for the first appearance of checks; an empty list after registration timeout is `unknown` (not passed).
   - On `cancelled`, re-triggers each cancelled run id once per head (tracked in a local set), then keeps polling; a
     second cancellation of the same run id yields `failed_closed` with reason "cancelled twice".
   - Returns a record
     `{state: passed|failed|pending|unknown|failed_closed|skipped, head_sha, runs: [{run_id, check_run_id, name, conclusion}], reruns: [...], reason}`;
     `state == failed` only for genuine check failures (this is the state that withdraws consensus; pending/unknown fail
     Stage 5 closed without withdrawing).
   - Never raises: exceptions become `unknown` with a redacted, bounded reason (`MAX_REASON_CHARS`).
   - `format_merged_head_ci(record)`: one log line naming the full head SHA, each run id and conclusion (acceptance
     criterion 5).
3. Do not modify `ci_final_head.py` (342/344 lines); reuse its helpers only by import where they are public
   (`parse_run_id`, `describe_failure`, `CredentialRedactor`).
