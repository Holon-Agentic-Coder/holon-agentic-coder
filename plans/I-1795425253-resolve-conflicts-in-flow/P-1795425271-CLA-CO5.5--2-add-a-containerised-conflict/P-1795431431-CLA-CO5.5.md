## Plan Description & Strategy

The conflict resolver is one callable built by `conflict_code_resolver(context)` that satisfies the `CodeResolver`
protocol. For each call (one in-progress merge, a list of `CODE` paths, the `TargetProbe`):

1. Work out the tier ladder of the configured runner, cheapest first (for `claude`: haiku, sonnet, opus, from
   `agent_defaults.get_model_capabilities`).
2. Snapshot the merge state: index entries, untracked files, `HEAD`, `MERGE_HEAD`.
3. For each tier: write the role input file (conflict paths, merge base, ours and theirs SHAs, intent JSON, plan path,
   tier model), dispatch the `conflict-resolver` role container through `flow/dispatch._dispatch_role`, and read the
   result file. The container renders `holon-config/prompts/conflict_resolver.template.md`, runs one agent turn, then
   runs `uv run task lint` and `uv run task test` in the foreground and writes a verdict: `resolved`, `cannot_decide`,
   `lint_failed`, `tests_failed` or `agent_failed`, plus the failing tests.
4. On the host, the attempt guard checks: no index, `HEAD` or `MERGE_HEAD` change (tampering is fatal); worktree changes
   only within the conflict set; no new untracked files; no conflict markers left in the conflict set. Only a `resolved`
   verdict that passes every check stages the paths and returns
   `CodeResolution(resolved=True, tier, attempts, test_result)`.
5. Otherwise, save the attempt diff as an artefact, restore the conflicted files to their merge state
   (`git checkout -m -- <paths>`), revert out-of-set edits, and move up one tier.
6. When the top tier fails, return `CodeResolution(resolved=False, ...)`. `merge_target` already aborts the merge,
   appends one blocked `target_sync` row naming the paths, tier, attempts and failing tests, commits that row locally
   and pushes nothing.

Wiring the factory into flow boundaries is the parent plan's Step 3 (the next child intent). This plan proves the
factory end to end through `sync_with_target` with a fake dispatcher on real git fixtures.

## Step 3: Add the host-side attempt guard (conflict-set check, tamper check, reset)

- **Sub‑intent recommendation:** NO
- **Reasoning:** This is the safety core of the intent ("rejects edits outside the conflict set"). It is small and
  testable on local git fixtures, and its correctness is easiest to judge next to the loop that uses it.
- **Step Type:** IMPLEMENTATION
- **Exploration level:** BALANCED

- **Hypothesis being tested:** During a merge with unmerged index entries, comparing a snapshot of `git ls-files -s`
  (stage entries), `git ls-files -o --exclude-standard`, `HEAD` and `MERGE_HEAD` before and after an attempt, together
  with `git diff --name-only` (worktree against index), detects every out-of-set edit and every git write by the agent.
  After that, `git checkout -m -- <paths>` restores the conflicted files to their marker state.
- **Learning target:** Whether `git checkout -m` reliably recreates the marker state for all conflict kinds the
  classifier sends to `CODE` (content conflicts, add/add, modify/delete), or whether some kinds need a restore from the
  stage blobs instead.
- **Maximum acceptable cost for this learning:** Fixture tests only (about 1 cost unit). If a conflict kind cannot be
  restored, that kind fails closed after its first failed attempt instead of escalating.

### Intent & Git Integration

- **Step Intent:** No attempt can land an edit outside the conflict set, and a failed attempt leaves the merge exactly
  as the next tier needs it.
- **Git branch:** `I-1795425253-resolve-conflicts-in-flow/P-1795425271-CLA-CO5.5--2-add-a-containerised-conflict/_`
  (execution branch of this plan)
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. New module `flow/conflict_resolver_attempt.py`.
2. `MergeSnapshot` (frozen): the stage entries from `git ls-files -s -z` excluding the conflict paths, the untracked set
   from `git ls-files -o --exclude-standard -z`, `HEAD` SHA and `MERGE_HEAD` SHA. `snapshot_merge(worktree, paths)`
   builds it through `git.run_git` with `check=False`.
3. `AttemptCheck` (frozen): `ok`, `tampered`, `out_of_set` (paths), `markers` (paths) and `reason`.
   `check_attempt(worktree, paths, before)` returns:
   - tampered when the snapshot's stage entries, `HEAD` or `MERGE_HEAD` changed, or when the merge is no longer in
     progress (`target_sync_merge.merge_in_progress`);
   - out-of-set paths: `git diff --name-only -z` paths not in the conflict set, plus untracked files new since the
     snapshot;
   - marker paths: conflict paths still holding lines that start with the marker prefixes. The check is a small local
     helper, because `target_sync_merge._has_markers` is private and that module is at 199 of 200 lines, so it is not
     touched.
4. `stage_resolution(worktree, paths)`: `git add -A -- <paths>` (which also records deletions), then
   `target_sync_merge.merge_verification_error(worktree, paths)` as a final check. A non-empty result counts as
   tampering, so it fails closed.
5. `reset_attempt(worktree, paths, check)`: revert out-of-set tracked edits with `git checkout -- <path>`, delete only
   the new untracked files the check listed (never a broader clean), and restore the conflict paths with
   `git checkout -m -- <paths>`. Afterwards it confirms that the paths are unmerged again
   (`target_sync_merge.unmerged_paths`); if not, it reports that the restore failed, and the loop fails closed.
6. `save_attempt_diff(worktree, paths, artefact_dir, label)`: writes `git diff -- <paths>` (worktree against index) to
   `<artefact_dir>/conflict-resolver/<label>.diff` before any reset. The artefact directory is the flow's existing
   git-ignored temporary directory (`tmp/` under the target worktree, as the review loop uses); if none exists, it is
   created under `tmp/conflict-resolver/`.
7. Path handling: the conflict-set comparison uses repository-relative POSIX paths exactly as git reports them. Renamed
   or case-changed paths count as out of set.
8. The module budget file needs no special case here: when it is in the conflict set, Step 4 blocks before any dispatch;
   when it is not, any edit to it is already out of set.
9. Tests in `tests/flow/test_conflict_resolver_attempt.py`, using real temporary git repositories with a two-branch
   content conflict:
   - an in-set resolution passes and stages;
   - an edit to another tracked file is out of set and is reverted;
   - an edit to a test file outside the set is out of set;
   - a new untracked file is out of set and is removed, while untracked files that existed before are kept;
   - `git add` of another file, a commit, and `git merge --abort` are each detected as tampering;
   - markers left behind are detected;
   - `reset_attempt` restores the marker state for content, add/add and modify/delete conflicts;
   - the diff artefact is written.
10. Run `uv run pytest tests/flow/test_conflict_resolver_attempt.py` in the foreground.

## Step 4: Add the escalation loop and the `conflict_code_resolver(context)` factory with fail-closed exhaustion

- **Sub‑intent recommendation:** NO
- **Reasoning:** This step ties Steps 1-3 together into the `CodeResolver` the merged `sync_with_target` already
  accepts. It is the end-to-end proof of the intent and cannot be split from its parts usefully.
- **Step Type:** IMPLEMENTATION
- **Exploration level:** EXPLOIT

### Intent & Git Integration

- **Step Intent:** Code conflicts are resolved on the cheapest tier first. The resolver escalates exactly one tier after
  a failed lint, failed tests, cannot-decide, agent failure or a rejected edit, and fails closed after the top tier.
- **Git branch:** `I-1795425253-resolve-conflicts-in-flow/P-1795425271-CLA-CO5.5--2-add-a-containerised-conflict/_`
  (execution branch of this plan)
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. New module `flow/conflict_resolver_role.py` with `conflict_code_resolver(context: FlowContext) -> CodeResolver`. It
   returns a closure, or a small frozen callable class if that reads better, with the protocol signature
   `(worktree, code_paths, probe) -> CodeResolution`.
2. Pre-dispatch block: if `holon-config/hygiene/module_budgets.json` is among `code_paths` and the intent lacks
   `module_budget_change`, return
   `CodeResolution(resolved=False, tier="none", attempts=0, test_result="module budget file in conflict set")` without
   dispatching.
3. Build the ladder with `tier_ladder(context.agent, context.model)` (Step 1) and take a `snapshot_merge` (Step 3).
4. Per tier, with helpers kept under the complexity limits (`_run_attempt`, `_write_role_input`, `_read_verdict`):
   1. Write the role input JSON to a `tempfile.mkstemp` file under the worktree's git-ignored `tmp/`: paths,
      `probe.merge_base`, `probe.head_sha`, `probe.target_sha`, `probe.target_ref`, `context.intent_data`, the plan path
      if known from the context, and the tier.
   2. Create the result file the same way.
   3. Call `_dispatch_role(context, CONFLICT_RESOLVER_ROLE, [input_path, context.agent, tier], result_file=...)`.
   4. Read the verdict. A dispatch exception, a non-zero exit or an empty or unreadable result counts as `agent_failed`.
   5. Run `check_attempt`. Tampering, or a failed restore later, returns a fail-closed `CodeResolution` at once, with no
      further tiers.
   6. `resolved` with a clean check: call `stage_resolution` and return
      `CodeResolution(resolved=True, tier=tier, attempts=n, test_result="passed")`.
   7. Anything else: `save_attempt_diff`, `reset_attempt`, log the reason through `context.log` (redacted), and take
      `next_tier`.
   8. Always remove the temporary input and result files.
5. Exhaustion returns
   `CodeResolution(resolved=False, tier=<last tier>, attempts=n, test_result=<last verdict and failing tests, bounded>)`.
   `merge_target` then aborts the merge, appends the blocked `target_sync` row (with the tier, attempts and test result)
   and commits it locally without pushing. No new abort or push code is added.
6. The `CodeResolution.test_result` text is bounded (for example 500 characters) and redacted, because it goes into the
   ledger row.
7. `SyncRequest.code_resolver` keeps its `fail_closed_code_resolver` default. Callers opt in by passing
   `conflict_code_resolver(context)`. Wiring at flow boundaries belongs to the parent plan's Step 3.
8. Tests in `tests/flow/test_conflict_resolver_role.py`, with a fake `context.dispatcher` that edits files in the
   mounted worktree and writes a scripted verdict, on real git fixtures through `sync_with_target`:
   - the first tier succeeds: one dispatch, tier is haiku, merged result, and the row records tier and attempts 1;
   - lint failure, then success: two dispatches, haiku then sonnet;
   - tests failure, then cannot-decide, then success: three dispatches in ladder order;
   - no escalation after a success;
   - an out-of-set edit on tier 1 is reverted, and tier 2 sees clean marker files;
   - tampering (a fake that commits) gives one dispatch only and a blocked result;
   - exhaustion gives three dispatches, a blocked result with `code conflicts unresolved`, a worktree with no
     `MERGE_HEAD`, an unchanged `HEAD` apart from the local blocked-row commit, no push call (patched
     `host_remote.push_commit`), and saved diff artefacts;
   - the module budget file in the set gives no dispatch and a blocked result;
   - a one-tier ladder fails closed after one attempt.
9. Run
   `uv run pytest tests/flow/test_conflict_resolver_role.py tests/flow/test_conflict_resolver_attempt.py tests/flow/test_conflict_resolver_tiers.py tests/flow/test_target_sync.py tests/flow/test_module_budgets.py`
   in the foreground.

### Dependencies & Criticality

- **Depends on:** Step 1, Step 2, Step 3
- **Is Bottleneck:** YES

### Safety & Constraint Considerations

- **Relevant rules:** `docs/safety.md` "Rebase conflict" (bounded attempts, then a human);

- **Potential failure modes for this step:**
