### Target behaviour

- The stored-credential tier is the OS secret store and nothing else. On macOS the lookup is
  `security find-generic-password -s holon -a claude-oauth-token -w`; on Linux it is
  `secret-tool lookup service holon account claude-oauth-token`. Any other platform has no store. The source name of the
  tier becomes `"keychain"`. No discovery code reads the plaintext file.
- A lookup has three results: found, no entry, or no usable store (tool missing, time-out, locked keychain, no secret
  service). Discovery treats the last two alike (no credential); pre-flight words them differently.
- Pre-flight for the claude runner first runs the one-time migration, then checks the credential. With no credential it
  fails closed with `not_logged_in`. The output and the hint name the store one-liner for the current platform and
  `claude setup-token`.
- Migration, in this order:
  - no file: nothing happens, nothing is printed, and no platform tool is started;
  - file unreadable or without a usable token: the file is kept and one line says so;
  - no usable store: the file is kept and one line says so;
  - the keychain already holds the identical token: the file is deleted and one line says so;
  - the keychain holds a different token: nothing is overwritten, the file is kept and one line says so;
  - otherwise the token is stored through standard input and read back; when the read-back matches, the file is deleted
    and one line states the file, the store, the service and the account; when it does not match, the file is kept.
- The lines go to standard error and never contain the token. While the file still exists, the pre-flight
  `not_logged_in` output adds that the plaintext file was not imported, was left untouched and is no longer read.
- Operator store commands, which prompt for the token so that it is neither an argument nor in the shell history:
  - macOS: `security add-generic-password -U -s holon -a claude-oauth-token -w`
  - Linux: `secret-tool store --label="Holon claude credential" service holon account claude-oauth-token`

### Considered and rejected

- **Keep the file as a fallback.** Rejected by the maintainer's decision in the intent.
- **Remove the explicit environment route for claude as well.** Rejected: role containers receive the credential only
  through the environment, so this would break every containerised run, including nested ones.
- **Pass the token to `security add-generic-password -w <token>` as an argument.** Rejected: the intent forbids a token
  on a command line. `security -i` with the command on standard input is used instead.
- **Use the `keyring` package.** Rejected: no new Python dependency is allowed.
- **Run the migration inside discovery.** Rejected: a read path that deletes a file is surprising, and it would import
  the migration module from `claude_credential.py` and create a cycle. Pre-flight is the place the intent names.
- **Trust the exit code of the store command.** Rejected: an interactive tool can exit 0 after a failed command. The
  read-back is the proof.
- **Cache the looked-up token in the process.** Rejected: it adds state for a call of a few tens of milliseconds and
  would make tests order-dependent.
- **Refuse a `HOLON_AGENT_OAUTH_TOKEN_FILE` reference that names the retired path, or retire that variable (DEFER).**
  Not done here: `config_env_secrets.py`, its tests and its documentation are outside the scope, and removing a
  documented variable is a decision for the maintainer. The plan stops recommending it and the migration output names
  the stale line.

### Implementation Details (No code blocks, only logic/steps)

- Create `apps/sandbox-executor/src/sandbox_executor/claude_keychain.py`. The module docstring states the contract in
  one paragraph: service `holon`, account `claude-oauth-token`, the token reaches a tool only on standard input, and no
  tool output is ever printed or logged. The module imports only the standard library.
- Constants: `SERVICE`, `ACCOUNT`, a lookup time-out and a store time-out (between 10 and 15 seconds; plain constants,
  no environment variable), and the two operator one-liners from `### Target behaviour`, keyed by platform.
- `LookupStatus`: an enum with `FOUND`, `MISSING` (the store answered and has no entry) and `UNAVAILABLE` (no usable
  store). `KeychainLookup`: a frozen dataclass with `status` and `token` (empty unless found). Its `repr` must not show
  the token (declare the field with `repr=False`).
- `current_platform()`: returns `"darwin"`, `"linux"` or `"unsupported"` from `sys.platform`. Tests patch this function,
  never `sys.platform`.
- `run_keychain_tool(argv, stdin_text=None)`: the only function in the code base that starts `security` or
  `secret-tool`. It calls `subprocess.run` with the argument list, no shell, captured text output, `check=False` and a
  time-out. With `stdin_text` it passes the text as input; without it, standard input is `subprocess.DEVNULL`, so a tool
  can never wait for the terminal. It returns the completed process, or `None` when the binary is missing, the call
  times out or the operating system refuses it. It never formats or logs the exception, the output or the input.
- `lookup_token()`: returns a `KeychainLookup`.
  - macOS: runs `security find-generic-password -s holon -a claude-oauth-token -w`. Exit 0 with non-empty trimmed output
    is `FOUND`; exit 0 with empty output and exit 44 are `MISSING`; everything else, including `None` from the seam, is
    `UNAVAILABLE`.
  - Linux: runs `secret-tool lookup service holon account claude-oauth-token`. Exit 0 with non-empty trimmed output is
    `FOUND`; exit 0 with empty output, and exit 1 with nothing on standard error, are `MISSING`; everything else is
    `UNAVAILABLE`.
  - Unsupported platform: `UNAVAILABLE` without starting anything.
- `store_token(token)`: returns `True` only when the token is in the store afterwards.
  - It first checks the token against an allow-list (ASCII letters, digits and the characters `.`, `_`, `~`, `+`, `/`,
    `=`, `-`; not empty). A token outside the list returns `False` and starts no tool.
  - macOS: the argument list is exactly `security`, `-i`. Standard input is one line:
    `add-generic-password -U -s holon -a claude-oauth-token -w` followed by the token and a line break.
  - Linux: the argument list is `secret-tool`, `store`, `--label=Holon claude credential`, `service`, `holon`,
    `account`, `claude-oauth-token`. Standard input is the token with no line break.
  - A `None` result or a non-zero exit returns `False`. Otherwise the function calls `lookup_token()` and returns `True`
    only when the status is `FOUND` and the token is identical.
- Wording helpers, all free of secrets: `store_name()` ("the macOS keychain", "the Secret Service keyring"),
  `store_command()` (the one-liner of the current platform) and `store_commands_text()` (both one-liners with their
  platform names, for the in-container message and for an unsupported platform).
- Every function has a docstring and type annotations, takes at most 5 arguments and stays inside the ruff limits. Split
  the per-platform parts into small private functions instead of one long branch. No `# noqa`.
- Test file change declared: create `apps/sandbox-executor/tests/fake_keychain.py` with a class `FakeKeychain`. It holds
  one optional entry in memory and the switches `platform` (default `"linux"`), `available`, `write_fails` and
  `write_is_silent_noop` (the store command exits 0 and stores nothing). Its `run(argv, stdin_text=None)` method
  emulates the four command lines above for both platforms with the exit codes of the contract, records every call as a
  pair of argument list and standard input in `calls`, and raises `AssertionError` for any other argument list. A
  function `install(monkeypatch)` creates a fake, patches `claude_keychain.run_keychain_tool` and
  `claude_keychain.current_platform`, and returns the fake.
- Test file change declared: in `apps/sandbox-executor/tests/conftest.py` add one autouse fixture `fake_keychain` that
  calls `install` and returns the fake, next to `isolated_claude_secrets_file` (which is not changed in this step). The
  fixture is about 8 lines; the logic lives in the helper so that `conftest.py` (411 lines) barely grows.
- Test file change declared: create `apps/sandbox-executor/tests/test_claude_keychain.py`. Fake tokens are built at run
  time (`"sk-ant-" + "oat" + make_probe(...)`). Tests:
  - lookup returns the token on macOS and on Linux, trimmed, with exactly the documented argument list and no standard
    input;
  - lookup reports `MISSING` for an empty store and `UNAVAILABLE` for a missing tool, a time-out, an unexpected exit
    code, a Linux failure with text on standard error, and an unsupported platform (where nothing is started);
  - store sends the token only on standard input: `assert_no_leak` finds the token in no recorded argument list, the
    macOS argument list is exactly `security`, `-i`, and the read-back happens;
  - store returns `False` when the write fails, when the write is a silent no-op, and when the read-back differs;
  - the allow-list refuses an empty token and tokens with a space, a quote, a backslash or a line break, with zero
    calls;
  - the real seam, with `subprocess.run` replaced by a recorder: no shell, `check` false, a time-out, `DEVNULL` as
    standard input for a lookup, the text as input for a store; `FileNotFoundError`, `subprocess.TimeoutExpired` and
    `OSError` give `None`;
  - the `repr` of a found lookup and the three wording helpers contain no token fragment;
  - the two one-liners start with `security add-generic-password -U` and `secret-tool store` and end without a secret.
- Run `command -v security secret-tool` once and note the result for the execution report. Do not run either tool.
