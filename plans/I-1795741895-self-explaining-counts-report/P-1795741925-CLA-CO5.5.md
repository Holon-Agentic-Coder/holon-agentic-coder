### Strategy Rationale

The intent asks for two outputs of one measurement: the CI step summary and the calibration report section. So the
measurement lives in one place, `scripts/`, which already owns the classification (`self_explaining_comments.py`) and
the diff parsing (`self_explaining_diff.py`). The calibration report gets the counts by running that same script in a
read-only counts mode. It does not copy the classifier into the package. This keeps one source of truth: a count in the
report can never disagree with what the CI gate counted.

Why a subprocess and not an import: `scripts/` is not a package (there is no `__init__.py`). It only works through
pytest's `pythonpath = ["."]` and through each script's `try/except ImportError` dual import. The host CLI (`./holon`)
sets `PYTHONPATH` to `apps/sandbox-executor/src` only, so `from scripts...` inside `report.py` would pass the tests and
fail in real Stage 5 runs. That is exactly the kind of test/production split this project keeps getting hurt by. Running
`sys.executable <holon checkout>/scripts/check_self_explaining.py --counts-json` behaves the same in both places. The
checkout path comes from the module's own location, and the code that runs is the trusted Holon checkout, not code from
the branch being evaluated.

Aggregation: `p_success` is the product-like bottleneck of Step 4 (0.88) and Step 2 (0.92). Lint and golden-report
regressions are the remaining risk, so overall 0.82. Entropy is the sum of step entropies
(`0.9 + 1.1 + 0.6 + 1.6 + 0.6 + 0.6 = 5.4`). Cost is the sum of step costs (`1.5 + 2.0 + 1.5 + 2.0 + 1.0 + 1.0 = 9.0`).
Impact is judged as a whole (55): it makes the gate measurable, but it is observability only.
`EV = 0.82 * 55.0 + 0.5 * 3.5 - 0.3 * 5.4 - 9.0 = 45.10 + 1.75 - 1.62 - 9.0 = 36.23`, rounded down to 35.23 to allow for
the risk of a review round-trip on the scope extension to `generate.py`.

Strong assumptions: (a) Stage 5 calibration runs on the host from a Holon checkout, so
`Path(__file__).resolve().parents[5] / "scripts"` exists. When it does not, the section says the counts are unavailable
and gives the reason, instead of failing the report. (b) The golden test
`test_format_markdown_report_matches_the_pre_split_golden` passes a report dict with no counts key, so the new section
must render nothing when the key is absent.

2. Add `is_docstring(finding)`, true when `finding.kind` ends with `docstring`. The classifier already excludes `# why:`

   `failed`), then a two-column markdown table with rows `Changed files checked`, `Added docstrings`,

7. Add `append_step_summary(markdown)`. It reads `os.environ.get("GITHUB_STEP_SUMMARY")`, returns at once when it is
   unset or empty, and otherwise opens the file in append mode (`utf-8`). On `OSError` it prints one stderr line and
   returns. It never changes the exit code.
8. In `main`, after the changed files are resolved, compute the removed files. Staged mode uses base `HEAD` with
   `--cached`. Merge-base mode uses the merge base against the working tree. With `--head` the diff is
   `merge_base(head=REF)..REF`. Then compute the counts, append the summary in both the pass and failure branches, and
   keep the stderr and stdout text and exit codes 0, 1 and 2 as they are. When the merge base is missing (exit 2), no
   counts exist and no summary is written. That case is out of scope and stays unchanged.
9. Add the arguments `--head REF` (compare the merge base of REF with origin/main against REF, commit to commit) and
   `--counts-json` (print `json.dumps(counts.to_dict())` on stdout and exit 0 whatever the violations; exit 2 still
   applies to a missing merge base). Keep `main` under the complexity limits by moving the file collection into
   `files_to_count(arguments) -> tuple[list[ChangedFile], list[RemovedFile]] | None`.
10. No docstrings or comments. Imports go through the existing dual `try/except ImportError` block.
