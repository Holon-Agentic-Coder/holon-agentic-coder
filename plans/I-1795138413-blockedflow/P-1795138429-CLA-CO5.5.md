## Plan Description & Strategy

Current behaviour (verified in the code): `admission.check_admission` reads the plan's touch set, calls
`in_flight.discover_in_flight_flows` (open flow pull requests plus `local_in_flight_flows`, which globs
`<worktree>/.holon/flow/checkpoint-*.json` in every other worktree and keeps any checkpoint whose `current_stage` is
execute or review), and returns an `AdmissionDecision`. A refusal becomes a failed Stage 3 result; the pipeline then
saves the checkpoint, whose `current_stage` is computed as execute (intent and plan completed, execute not), so the
refused flow looks in flight to everyone else. Two refused flows that overlap therefore list each other forever. There
is no lock, so two retries in the same window can both see "nothing in flight" and both be admitted.

Strategy, in dependency order:

1. **Admission record in the checkpoint** (new `flow/admission_state.py`, plus a `FlowContext.admission` field and a
   top-level `admission` key in the checkpoint JSON). Old checkpoints load with `admission = None`.
2. **Per-repository admission lock** (new `flow/admission_lock.py`): an exclusive `fcntl.flock` on
   `<git rev-parse --git-common-dir>/holon-admission.lock`, bounded wait, fail-closed on timeout.
3. **Discovery skips blocked flows** (`in_flight.py`): a checkpoint whose admission state is `blocked` is not in flight;
   flows carry the structured reference (`kind`, pull-request number and head branch, or plan branch and worktree)
   needed for `blocked_by` entries; a separate read lists blocked waiters for the ordering rule. An open pull request
   remains in flight regardless of any checkpoint (pull requests are discovered independently).
4. **Ordered, atomic admission** (`admission.py`): under the lock, discover, compute conflicts, apply the oldest-waiter
   rule, write the admission record into the checkpoint, release. Refusal records `blocked` (keeping the first
   `blocked_since`, replacing `blocked_by`); admission records `admitted` (with `override: true` and the conflicts under
   `--allow-overlap`). Dry runs only log and never write.
5. **Hermetic tests** covering every acceptance criterion.
6. **Budgets and docs.**
7. **Verification** with the affected tests, then the full suite once, then lint and lint-docs.

Why no cycle can form: `blocked_by` only references (a) open pull requests, (b) admitted local flows, or (c) an older
blocked waiter. Blocked flows are not in flight, so (a) and (b) never point at a blocked flow; (c) edges always point to
a strictly older `(blocked_since, plan_branch)` key, a total order, so the waits-for graph is acyclic. Because the lock
is held from discovery to the checkpoint write, the first holder after a merge either is admitted (and becomes visible
as admitted to the next holder) or records itself blocked; two overlapping flows on one host cannot both pass.

## Step 2: Add the per-repository admission lock

- **Sub‑intent recommendation:** NO
- **Reasoning:** One small new module with a single responsibility; reusable, but too small to justify its own branch
  and evaluation.
- **Step Type:** IMPLEMENTATION
- **Exploration level:** EXPLOIT

### Intent & Git Integration

- **Step Intent:** Serialise admission checks of every worktree of one repository on the same host.
- **Git branch:** the plan's single execution branch
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. Create `flow/admission_lock.py` with:
   - `admission_lock_path(repo_dir, run_git)`: runs `git rev-parse --git-common-dir` through the injected `GitRunner`,
     resolves a relative result against `repo_dir`, and returns `<common-dir>/holon-admission.lock`; returns an
     `AdmissionUnavailable` (imported from `in_flight.py`) when git fails;
   - a context manager
     `admission_lock(repo_dir, run_git=None, timeout_seconds=ADMISSION_LOCK_TIMEOUT_SECONDS, poll_seconds=...)` that
     opens the file (`O_CREAT`), takes `fcntl.flock(LOCK_EX | LOCK_NB)` in a bounded poll loop, yields, and always
     unlocks and closes in `finally`;
   - an `AdmissionLockTimeout` exception (or an `AdmissionUnavailable` value) raised when the wait exceeds the timeout,
     so the caller refuses fail-closed with a clear reason.
2. Default timeout around 120 seconds: discovery makes at most ~50 `gh pr diff` calls, so a holder normally finishes
   well inside it; the value is a module constant.
3. The poll sleep goes through `time.sleep` imported as a module attribute so the repository's sleep-patch guard in
   tests applies (check `tests/flow/sleep_patch.py` conventions and follow them).
4. Locks are advisory and released by the kernel when a process dies, so a crashed holder never wedges admission.

## Step 4: Run admission under the lock with the oldest-waiter rule and record the state

- **Sub‑intent recommendation:** NO
- **Reasoning:** It is the riskiest step but tightly coupled to Steps 1 to 3 and only testable together with them; a
  separate sub-intent would merge an inert half-feature. Kept in-plan with an explicit hypothesis and discard rule.
- **Step Type:** IMPLEMENTATION
- **Exploration level:** BALANCED

- **Hypothesis being tested:** Holding one file lock from discovery to the checkpoint write, plus "defer to an older
  overlapping waiter whose blockers are all clear", admits exactly one of any set of mutually overlapping flows per
  window, in `blocked_since` order, without creating a new deadlock or starving the oldest waiter.
- **Learning target:** whether the clear-blocker test can be decided from recorded `blocked_by` plus current discovery
  alone (no recursive re-evaluation of the waiter's touch set), and how an abandoned blocked waiter affects newer flows.
- **Maximum acceptable cost for this learning:** 1.5x this step's cost (about 9 units); beyond that, ship without the
  ordering rule only after re-planning with the reviewer, never silently.

### Intent & Git Integration

- **Step Intent:** Make Stage 3 admission atomic per repository, ordered by first refusal, and recorded in the
  checkpoint.
- **Git branch:** the plan's single execution branch
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. Ordering logic goes in `admission_state.py` (or a sibling `flow/admission_order.py` if `admission_state.py` would
   exceed ~200 lines):
   - `blocker_is_clear(entry, flows, waiters)`: a `pull_request` entry is clear when its number is no longer among the
     open flow pull requests; a `local_flow` entry is clear when its plan branch is neither in flight nor a blocked
     waiter (a blocked waiter that blocks another waiter keeps it waiting, preserving order along the chain);
   - `older_ready_waiter(own_plan_branch, own_record, own_touch_set, flows, waiters)`: among waiters whose declared
     touch set overlaps this plan's (same `overlapping_entries` rule as admission), whose sort key
     `(blocked_since, plan_branch)` is strictly smaller than this flow's (a never-blocked flow uses "now", so every
     existing waiter is older), and whose blockers are all clear, return the oldest; else `None`.
2. `admission.py` `check_admission`:
   - read the plan touch set as today (refusal without a touch set or on discovery failure keeps the fail-closed reason;
     these are not overlap refusals and record no `blocked` state, matching the intent's "refusal for a touch-set
     overlap");
   - inside `admission_lock(context.target_worktree)`, discover flows and waiters, compute conflicts, and, when there
     are no conflicts, apply `older_ready_waiter`; a hit becomes one `local_flow` conflict naming the waiter, its
     worktree and the overlapping entries;
   - build `blocked_by` entries from each conflicting `InFlightFlow` (kind and reference fields plus files) and carry
     them on `AdmissionDecision` (new field), alongside the existing `conflicts` payload, which stays unchanged for
     backwards compatibility of the Stage 3 payload and ledger rows;
   - still inside the lock, call a new `record_admission(context, decision)` that sets `context.admission` to
     `blocked_record(...)` (refused, no override), `admitted_record()` (admitted) or `admitted_record(conflicts)`
     (`--allow-overlap` override) and writes the checkpoint with `save_checkpoint(context)` at its default path, which
     is the path other worktrees' discovery globs. Lock acquisition timeout or a checkpoint write failure refuses
     fail-closed with the reason.
   - Keep `check_admission`'s injected `run_gh`/`run_git` parameters and thread `run_git` into the lock path lookup so
     tests stay hermetic; split helpers so each function stays within `C901 <= 10`, `PLR0913 <= 5`.
3. `admission_stage_failure`: a dry run never writes (pass a `record=False` path or check `context.dry_run` before
   recording, and never take the lock in a dry run beyond what discovery needs). The override row to `executions.jsonl`
   is unchanged; the checkpoint additionally notes the override.
4. `format_refusal`: when a conflict comes from the ordering rule, its label says "an older waiting flow ... (blocked
   since ...)" so operators see why a seemingly clear plan waits.
5. `stages/execute.py`: no logic change expected (it already calls `admission_stage_failure` before dispatch); touch it
   only if the dry-run call needs the explicit no-record flag.

### Strategy Rationale

The intent is accepted as is: it fixes a real, silent deadlock in a safety gate and closes an admission race, with
precise states and acceptance tests, so its EV is clearly positive and no reframing beats it. The plan keeps one
execution branch because the total predicted entropy (11.0) fits the 15.0 budget and the steps are tightly coupled (the
blocked state is useless without discovery skipping it, and the ordering rule is untestable without both). Code
placement follows the module-ownership rule: every scoped module is already exactly at its line budget, so the new model
and the lock go in new focused modules and the scoped modules only gain call sites.

Aggregation: entropy is the sum of step entropies, `2.0 + 1.5 + 2.0 + 2.5 + 1.5 + 1.0 + 0.5 = 11.0`; cost is the sum,
`3.0 + 2.5 + 3.0 + 6.0 + 4.0 + 1.5 + 2.0 = 22.0`. Overall p_success is a qualitative judgement anchored on the
bottleneck Step 4 (0.78) and lowered for the coupled risks of Steps 1 to 3 and the race test's determinism, giving 0.72
(a straight product, `0.90 * 0.88 * 0.87 * 0.78 * 0.82 * 0.92 * 0.85`, is about 0.34 but over-counts: the steps share
fixtures and failures are mostly recoverable within the execution). Impact 80 reflects that admission gates every
concurrent flow. Learning value 6.0 is the maximum single-step value plus the evidence on lock-based ordering.
`EV = 0.72 * 80.0 + 0.5 * 6.0 - 0.3 * 11.0 - 22.0 = 35.3`.

Strong assumptions: all flows that can overlap run on one host (the intent scopes atomicity to "the same host";
cross-host races remain possible and are mitigated only by the pull-request diff comparison), and Stage 3 always re-runs
admission before dispatch on resume (verified in `stages/execute.py`).
