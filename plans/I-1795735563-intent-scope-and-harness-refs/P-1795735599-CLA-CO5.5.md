### Strategy Rationale

The intent is small, well scoped and already lists every file. The work is one dependency chain: a stdlib-only pattern
module, a pure payload-rules module that uses it, then three thin consumers (the `intent-check` CLI through
`intent_scope_check.py`, Stage 1 through `flow/intent_questions.py`, and the CI script). Building the pure modules first
means each consumer step is a few lines plus tests.

Aggregation: `entropy_pred` is the sum of step entropies (`0.5 + 1.0 + 1.5 + 1.5 + 1.5 + 2.0 + 0.5 = 8.5`). `cost_pred`
is the sum of step costs (`1.5 + 1.5 + 2.5 + 2.5 + 2.0 + 3.0 + 1.0 = 14.0`). `p_success_pred` is a judgement below the
weakest step (Step 6, 0.80) and above the raw product (about 0.37), because the steps are correlated: they share one
author, one small codebase and one verification run, and a failure in one is normally fixed in place rather than sinking
the plan. Bottleneck: Step 6 (CI workflow), because an existing test
(`tests/test_ci_bookkeeping_wiring.py::test_every_workflow_that_runs_on_a_pull_request_is_wired`) fails for any new
workflow whose text contains a block-form `pull_request:` key, and that test is outside the scope. The plan avoids it
with the flow-scalar trigger form, which `tests/test_workflow_triggers.py` already accepts.

`EV = P(success) * Impact + mu * LearningValue - lambda * Delta_S_intent - Cost`, with `lambda = 0.3` and `mu = 0.5`
from `holon-config/metrics/ev_config.json`:
`EV = 0.78 * 70.0 + 0.5 * 4.0 - 0.3 * 8.5 - 14.0 = 54.60 + 2.00 - 2.55 - 14.0 = 40.05`.

Strong assumptions: the harness names can be confirmed from earlier plans in `plans/` (they are not repeated in this
file, because this file is itself added by the pull request the new scan checks); `python` 3.13 on the CI runner is
enough to run a stdlib-only script; no existing fixture passes a glob or trailing-slash scope through Stage 1 (a grep of

Design decisions:

- Module ownership: `harness_reference_patterns.py` owns the patterns (stdlib `re` only, no package imports, so the CI
  script can load it without installing the package). `intent_payload_rules.py` owns the intent-file rules and imports
  only the pattern module and stdlib, so `flow/intent_questions.py` gains no dependency on git-running code and no
  import cycle appears (`tests/test_import_cycle.py` stays green).
- Exit codes of `holon intent-check`: 2 for a rule violation (same code as invalid input, as the intent asks), else the
  existing 1 for proposals and 0 otherwise.
- The JSON report keeps exactly `missing`, `proposed` and `warnings` for an intent with no violation (so the existing
  key-set tests stay valid) and adds a `violations` list only when there is one. Hub-file warnings join the existing
  `warnings` list, so they never change the exit code.
- CI script exit codes: 0 clean, 1 reference found, 2 diff unreadable (fail closed).

   `sandbox_executor.harness_reference_patterns`.
2. Define a frozen dataclass `PayloadFindings` with `violations: list[str]` and `warnings: list[str]` and a property
   `refused` (true when there is a violation).
3. Scope entry handling: strip the new-file marker the same way `intent_scope_check.ScopeEntry.parse` does (trailing

   that contains any of `*`, `?`, `[`, `]`, `{`, `}`, and (only when `worktree` is given) one that is an existing

   glob widens the touch set and blocks every other flow at Stage 3 admission"). If the entry itself matches a harness
   pattern, refer to it as "scope entry N" instead of echoing it.
5. `hub_file_warnings(entries)`: warn on `flow/lazy_exports.py` (path ends with it), any basename `conftest.py`, any
   `.md` file whose parent directory is named `docs`, and `scripts/pre_commit_check.py`. Warnings only.
6. `intent_texts(payload)`: yield `(field, text)` for `goal`, `description`, `rationale` (strings) and each item of
   `scope` and `acceptance_criteria` (lists; non-list values are read as one string).
7. `harness_reference_violations(payload)`: for each field with a match, a message naming the field and the pattern
   labels and saying the intent text is copied into the append-only intents ledger; never the matched text.
8. `check_intent_payload(payload, worktree=None) -> PayloadFindings` combines the three (scope violations first, then
   harness violations; warnings from the hub check).
9. Keep each function under the ruff complexity limits; no docstrings, no comments except `# why:`; at or under 200
   lines.
10. Create `apps/sandbox-executor/tests/test_intent_payload_rules.py` with: a real directory entry in a `tmp_path`

    the message contains neither the sample text nor any match; a clean intent (copied shape of this intent's own
