## Plan Description & Strategy

### Current behaviour (read on `main` at `fe2b040d`)

- The engine saves the checkpoint only after a stage returns (`PipelineEngine._record_stage` in `flow/pipeline.py`).
  Stage 2 (`flow/stages/plan.py`) dispatches the planner, pushes, fetches and adopts inside one stage call, so a kill
  anywhere in that call leaves a checkpoint that still says "plan next" and names no plan branch.
- The planner container creates its plan branch in the mounted worktree when it starts and commits the plan file and the
  `plans.jsonl` row only at the end (`entrypoint/planner.py`); the host pushes after the container returns.
- `PlanStage.prepare` snapshots the plan branches **on origin** only (`_snapshot_child_branches`).
  `publish_new_child_branches` (`flow/host_remote.py`) then pushes every **local** plan branch absent from that
  snapshot, and `_discover_child_branch` (`flow/git_refs.py`) adopts the single new origin branch or refuses with
  "ambiguous P-branches ... refusing to guess".

That gives three kill windows, each with its own symptom on a resume from plan:

| window | state left by the kill                                      | resume today                                      |
| ------ | ----------------------------------------------------------- | ------------------------------------------------- |
| W1     | local plan branch, no plan commit yet (planner was running) | both branches pushed, "ambiguous P-branches"      |
| W2     | local plan branch with the plan committed, not pushed       | both branches pushed, "ambiguous P-branches"      |
| W3     | plan branch pushed, checkpoint not advanced                 | a second plan branch is created and silently used |

W1 and W2 match the PR #239 report (refusal, stale branch on origin). W3 is the case the intent text describes. Step 1
confirms this table with tests.

### Target behaviour

1. **Adopt instead of planning again.** On entry to Stage 2 (not in a dry run, and not when the engine re-plans with
   `replan_feedback`), the stage lists the `P-.../_` branches directly under the intent prefix on origin and in the
   local worktree. A branch is **complete** when a `plans.jsonl` row of that plan and the plan file it records exist at
   the branch ref. With at least one complete branch the stage adopts the **newest complete** one (largest plan-id
   timestamp, ties broken by branch name), pushes it first when it exists only locally (fast-forward only), logs every
   candidate, the incomplete ones with the reason, and the choice, and continues to `read_plan` without dispatching the
   planner. With no complete branch it plans exactly as before.
2. **Never publish a stale local branch.** The pre-dispatch snapshot becomes origin plus the plan branches already in
   the local worktree, so a dispatch publishes and counts only the branch it created. This removes the path to the
   "ambiguous P-branches" refusal on a resume (W1).
3. **Record before the push.** After the planner returns and before the host pushes, Stage 2 saves the checkpoint with
   the new plan branch as `plan_branch` and the plan stage marked `running`, so a kill at or after the push leaves a
   checkpoint that names the branch and still resumes at Stage 2, where rule 1 verifies, publishes and adopts it.
4. **Say how to choose.** The existing ambiguity refusal (two branches appearing during one dispatch) gains one sentence
   that names the way forward: resume from plan, which adopts the newest complete branch. No path needs a hand-edited
   checkpoint.

Why both mechanisms: the record alone does not help a kill before the planner returns (W1, W2 before the record), a
checkpoint written by an older version, or a repository already holding two plan branches. Adoption alone satisfies
those but not acceptance criterion 2, and during an engine re-plan the checkpoint would still point at the refused plan.

One rule decides the branch (newest complete). The checkpoint's recorded branch is used for the log line only; in every
kill window it is the newest branch anyway, and a single rule keeps the choice deterministic and easy to explain.

### Implementation Details (No code blocks, only logic/steps)

- In `plan_resume.py` (or in `flow/stages/plan_branch_record.py` when `plan_resume.py` would pass 200 lines), add two
  public functions and register them in `flow/lazy_exports.py` and `flow/__init__.py`.
- `record_plan_branch(context, plan_branch)`: returns `None` or an error text. It follows the shape of `save_admission`
  in `flow/checkpoint.py`:
  - remember the live values of `context.plan_branch`, the `plan` entry of `context.stage_results` (or its absence) and
    the `replan_feedback` entry of `context.intent_data` (or its absence);
  - set `context.plan_branch` to the new branch; set the `plan` stage result to a `StageResult` with status `RUNNING`,
    so the saved `current_stage` is `plan` even during an engine re-plan, where the earlier plan result is still
    `SUCCESS`; remove `replan_feedback`, which must never reach a checkpoint;
  - call `save_checkpoint(context, context.checkpoint_path)`; an `OSError` becomes the error text, which names the
    checkpoint path and the branch;
  - in a `finally` block restore all three live values. The stage therefore continues, succeeds or fails exactly as
    today (for example `context.plan_branch` stays unset after a failed Stage 2), and the engine's normal save after the
    stage overwrites the record.
- `publish_planned_branches(context, intent_prefix, before, suffix)`: returns `None` or an error text.
  - Find the plan branches this dispatch created: `new_local_child_branches` against `before`, kept when
    `_matches_dispatch_suffix` accepts them.
  - With exactly one, call `record_plan_branch`; on an error return it without pushing (the branch stays local; a resume
    publishes and adopts it). With none or several there is nothing unambiguous to record; continue, and the existing
    checks of `adopt_plan_branch` report the situation.
  - Then publish as today: `remote_error` around `publish_new_child_branches` with the same arguments, and return its
    result.
- In `PlanStage.dispatch_planner`, replace the direct publish call with
  `publish_planned_branches(context, self.intent_prefix, self.existing_plans, self.preferred_suffix)`. The order of the
  two existing checks stays: a non-zero planner exit is reported first, then the publish or record error. Drop the
  import that is no longer used. Net line change in `plan.py`: about zero.
- Why the record uses `RUNNING` and not `SUCCESS`: the branch is not yet on origin and not yet verified. A resume
  re-enters Stage 2, where `adopt_existing_plan` checks completeness, publishes if needed and adopts. A `SUCCESS` record
  would let a resume start Stage 3 on a branch that may not exist on origin.
- Test file change declared: extend `apps/sandbox-executor/tests/flow/stages/test_plan_resume_adopts_branch.py`:
  - in the W3 test of Step 1, assert on the checkpoint file as left by the kill: `load_checkpoint` succeeds, its
    `current_stage` is `plan`, its context's `plan_branch` is the single plan branch on origin, and the `plan` stage is
    not among the completed stages;
  - order: with the push made to fail (unreachable push URL), the checkpoint file already names the local plan branch;
  - a save error (patch `save_checkpoint` where the record looks it up, raising `OSError`) fails Stage 2 with a message
    naming the checkpoint path and the branch; nothing was pushed to origin; a following Stage 2 run publishes and
    adopts the branch without dispatching the planner;
  - during a re-plan (`replan_feedback` set) the saved checkpoint does not contain `replan_feedback`, and the live
    `intent_data` still does after the record;
  - after a successful Stage 2 the live context equals what the stage sets today (`plan_branch`, a `SUCCESS` plan
    result).
- Run in the foreground, once:
