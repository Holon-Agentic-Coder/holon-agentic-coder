## Plan Description & Strategy

Findings from the current tree (`apps/sandbox-executor/src/sandbox_executor/knowledge/wisdom.py`, 353 lines, budget
400):

- `persist_kb_fact` writes `created_ts` (caller value or `datetime.now`) and `updated_ts` (always `datetime.now`), plus
  the caller's `evidence` dict verbatim.
- `persist_wb_rule` writes `created_ts` (caller value or wall clock) and the caller's `ascension_evidence` verbatim.
- The promotion builders feed run-varying data into those dicts: `_promote_success_candidate` puts `ledger_refs` (most
  recent 5 record ids), `success_count`, `failure_count`, `wilson_lower`, `posterior_mean` and `ladder_state` into KB
  `evidence` and `eval_res.advisory_text` (embeds `21/21`, `0.85`) into `payload.description`;
  `_build_wisdom_heuristic_item` puts `total_executions`, `wilson_lower` into `ascension_evidence` and the advisory into
  `payload.advisory`; `_promote_failure_candidate` puts `ledger_refs` and counters into `evidence` and `failure_count`
  into `payload.description`.
- Nothing in `src/` reads `evidence`, `ascension_evidence`, `updated_ts`, `payload.description` or `payload.advisory`
  back from disk; `load_index` reads only `kb_id/wb_id`, `kb_type/wb_type`, `status`, `created_ts`, `tags`.
  `flow/conflict_classes.py` only names the timestamp keys. The in-memory items returned by `promote_pending_candidates`
  are consumed by Stage 5 / calibrate counts and by tests (`test_promotion_idempotence.py:124` reads
  `first[0]["evidence"]["ladder_state"]`, `test_failure_promotion_review_chatter.py:86` reads in-memory `ledger_refs`
  and on-disk `payload.action`, `name`, `symptoms`).

Strategy: separate the **in-memory promotion item** (keeps every counter, unchanged for callers and reports) from the
**persisted envelope** (deterministic). The persisted envelope is built by a new small module
`knowledge/stable_envelope.py` so `wisdom.py` shrinks rather than grows:

1. Timestamps: `created_ts` = caller-supplied value if present (existing tests and callers that pass an explicit value
   keep it), otherwise the fixed constant `STABLE_CREATED_TS = "1970-01-01T00:00:00+00:00"`; KB `updated_ts` = the same
   value as `created_ts`. No wall clock is read. Both keys stay so `load_index`, the schema docs and `conflict_classes`
   keep working; `load_index` sorting by `(created_ts, id)` still yields a total, stable order.
2. Evidence: the writer filters `evidence` / `ascension_evidence` through an allowlist of stable keys (KB: none, so
   `{}`; WB: `project_count`, `provenance`). Counters, Wilson bounds, posterior means, ladder states and ledger refs
   stay in the action index database and ledgers where they already live, and in the in-memory item.
3. Advisory text: the builders put a counter-free, non-imperative text into the persisted payload (`payload.description`
   for KB pattern and failure, `payload.advisory` for WB) via `stable_advisory_text(...)`; `payload.name`,
   `payload.action`, `payload.symptoms` and `tags` are unchanged (they are derived from the context, not counters, and
   an out-of-scope test asserts them).
4. Write-once: the writer opens the target with exclusive-create mode and returns the path on `FileExistsError`, so an
   existing file (including legacy files on main) is never rewritten, even under a race between the `exists` check and
   the write. The JSON format stays `json.dump(..., indent=2)` with the existing key order so new files look like the
   old ones minus the varying values.

The plan does not migrate or rewrite the existing files under `holon-knowledge/` (forbidden by the intent); they remain
readable because nothing about the reader changes. Already-diverged legacy files can still conflict once more if two
flows both happen to add a path that is absent on main — after this change both sides write identical bytes, so git sees
an identical add/add and does not conflict.
