Strategy: three small, independent deliverables, each in its own new module with its own hermetic tests, then thin
wiring and one validation pass.

1. `flow/github/token_scopes.py` (pure logic plus one injectable HTTP GET): resolve the token, classify its type from
   its prefix without echoing it, read `X-OAuth-Scopes` from `GET https://api.github.com/user`, decide whether a set of
   paths needs the `workflow` scope, and produce a verdict (`ok`, `missing`, `unverifiable`).
2. `flow/stages/token_scope_guard.py`: the Stage 3 step that combines the plan touch set and the intent scope, calls the
   verdict, and returns a failed `StageResult` (with `dispatched=False`) naming
   `gh auth refresh -h github.com -s workflow` when the scope is missing. Wired into `ExecuteStage.steps()` right after
   `preflight` (so after the dry-run and `skip_push` exits and before admission, plan refresh and dispatch).
3. `flow/execution_recovery.py`: when the host push is refused, pin every new execution branch's tip under
   `refs/holon/recovery/<execution id>` and try a best-effort remote push to `holon-recovery/<execution id>`; the stage
   error names the ref(s) and, when the refusal text mentions the workflow scope, the same refresh command.
4. Doctor: one value-free report line (`github_token=<type> scopes=<list|unverifiable|none> source=<env name|gh>`) plus
   a `WARNING:` line when `workflow` is missing, added to the doctor environment section.

The guard is conservative: a touch-set glob that could match `.github/workflows/<file>` (for example `.github/**` or
`**`) counts as touching workflows. Fine-grained (`github_pat_`) and app (`ghs_`) tokens, and a classic token whose
response carries no `X-OAuth-Scopes` header, are reported as unverifiable and pass with a logged note, as the goal
requires. A network or HTTP failure of the scope request is also unverifiable (logged, not fatal), so an offline GitHub
API never blocks a flow that could otherwise run; only a positive "scopes header present and lacks workflow" fails fast.
No token, when a workflow path is touched, fails fast with a message naming `gh auth login`.

### Implementation Details (No code blocks, only logic/steps)

1. Create `apps/sandbox-executor/src/sandbox_executor/flow/github/token_scopes.py` with a module docstring explaining
   the classic versus fine-grained distinction and the "never print the value" rule. Import only from the standard
   library, `sandbox_executor.touch_set` and `sandbox_executor.redaction`; nothing from `cli` or `entrypoint`.
2. Constants: `WORKFLOW_SCOPE = "workflow"`, `WORKFLOW_DIR = ".github/workflows/"`,
   `USER_API_URL = "https://api.github.com/user"`, `REFRESH_COMMAND = "gh auth refresh -h github.com -s workflow"`, a
   default timeout of 10 seconds.
3. `resolve_github_token(environ=None, run=None) -> tuple[str | None, str]`: returns the token and its source label
   (`GITHUB_TOKEN`, `GH_TOKEN`, `gh` or `none`), checking the environment first and then `gh auth token` through an
   injectable runner (default `subprocess.run` with `capture_output`, `text`, a timeout, and `shutil.which("gh")`
   guard). Same order as today's `cli.find_github_token`.
4. `token_type(token) -> str` from the documented prefixes only: `ghp_` classic, `gho_` oauth (gh CLI; carries classic
   scopes), `github_pat_` fine-grained, `ghs_` app, `ghu_` user-to-server, otherwise `unknown`. Only the label leaves
   the function.
5. A frozen dataclass `TokenScopeReport(token_type, source, scopes: tuple[str, ...] | None, detail)` where
   `scopes is None` means unverifiable; properties `has_workflow` and `verifiable`, and `format_line()` producing the
   value-free doctor line.
6. `fetch_scopes(token, fetch=None, timeout=...) -> tuple[str, ...] | None`: one GET to `USER_API_URL` with headers
   `Authorization: Bearer <token>`, `Accept: application/vnd.github+json`, `User-Agent: holon`. The default fetcher uses
   `urllib.request` and returns `(status, headers)`; the fetcher is a parameter so tests inject a fake. Parse
   `X-OAuth-Scopes` by splitting on commas and stripping; a missing header returns None; an empty header returns an
   empty tuple (a classic token with no scopes). Any `OSError`/`URLError`/HTTP error status returns None with a short,
   redacted reason kept on the report (pass every message through `redact_agent_secrets` and also replace the literal
   token if present, as a belt-and-braces guard).
7. `scope_report(environ=None, run=None, fetch=None) -> TokenScopeReport` composes 3 to 6; fine-grained and app tokens
   skip the request entirely and are reported unverifiable ("fine-grained tokens carry no scopes header").
8. `touches_workflows(paths: Iterable[str]) -> list[str]`: returns the declared entries that are or may match a file
   under `.github/workflows/`: a literal path starting with `WORKFLOW_DIR` (after `normalise_touch_path`), or a glob
   entry for which `entry_matches(TouchSetEntry(path=entry), ".github/workflows/ci.yml")` (and the `.yaml` variant) is
   true. Accept plain strings so it serves both touch-set entries and intent `scope` strings.
9. `workflow_scope_error(report, workflow_paths) -> str | None`: None when no workflow path is touched, the report is
   unverifiable, or it has `workflow`; otherwise a message naming up to 5 of the paths, the token type and source (never
   the value), the scopes found, and the exact `REFRESH_COMMAND` (plus a note that an environment token must be
   regenerated with the `workflow` scope). With no token at all and workflow paths touched, name
   `gh auth login -h github.com -s workflow`.
10. Keep every function within `C901 <= 10`, `PLR0913 <= 5`; keep the module well under 200 lines.
11. Tests in `apps/sandbox-executor/tests/flow/github/test_token_scopes.py` (no network: every test injects a fake
    fetcher that records calls and returns a status plus a headers mapping):
    - header `repo, read:org` against `[".github/workflows/ci.yml"]` gives an error containing
      `gh auth refresh -h github.com -s workflow`;
    - the same token against `["apps/x.py"]` gives None;
    - header `repo, workflow` against a workflow path gives None;
    - `github_pat_` token: fetcher is never called and the verdict is unverifiable (None error);
    - classic token with no header: unverifiable;
    - fetcher raising `URLError`: unverifiable, the reason carries no token;
    - `touches_workflows` truth table: literal workflow path, `.github/**`, `.github/workflows/*.yml`,
      `.github/CODEOWNERS` (not workflows), `apps/**` (not workflows);
    - a sentinel token value never appears in `format_line()`, the error text, `repr(report)` or captured logs;
    - `resolve_github_token` order with a fake environment and a fake `gh` runner.

### Strategy Rationale

The intent is accepted with a grounded reframe of two details rather than its substance. First, because Stage 3 pushes
from the host and GitHub's workflow-scope refusal is about the commits' content, "push them to a recovery ref" cannot be
relied on to succeed remotely for the very failure that motivated the intent; a host-local
`refs/holon/recovery/<execution id>` ref guarantees the "commits are kept and named" criterion, and the remote push is
attempted as a bonus whose success is recorded (the plan's one exploratory element). Second, the token resolver is moved
into the flow-owned module because the flow may not import from the CLI. Splitting into sub-intents was rejected: the
predicted entropy (9.0) is well inside the 15.0 budget, the three deliverables share one small module, and three child
pipelines would roughly triple review and CI cost for about 400 lines of change.

Aggregation: entropy is the sum of step entropies, `2.0 + 2.0 + 2.5 + 1.5 + 0.5 + 0.5 = 9.0`. Cost is the sum,
`3.0 + 2.5 + 3.0 + 1.5 + 0.5 + 1.5 = 12.0`. Impact is the plan-level judgement (70.0) rather than the step sum (120),
since the steps overlap in value. Probability is a qualitative judgement anchored on the bottleneck Step 2 (0.85, frozen
line budget) and Step 3 (0.80): the naive product of all steps (about 0.46) understates success because the steps are
independent modules with repair loops inside one execution and the final gate retries cheap fixes; 0.76 is used.
Learning value is the sum, `1.0 + 0.5 + 2.0 + 0.5 = 4.0`. Overall
`EV = 0.76 * 70.0 + 0.5 * 4.0 - 0.3 * 9.0 - 12.0 = 53.2 + 2.0 - 2.7 - 12.0 = 40.5`.

Strong assumptions: `read_plan_touch_set` returns the plan's `## Touch Set` for the plan branch in the flow worktree (as
`touch_set_guard.py` already relies on); the Stage 3 test fixtures can run `ExecuteStage.run()` with patched
collaborators (as `test_execute_steps.py` does); GitHub keeps returning `X-OAuth-Scopes` for classic and gh OAuth
tokens.
