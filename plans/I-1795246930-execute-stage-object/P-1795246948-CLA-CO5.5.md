### Strategy Rationale

The function is a long chain of guard clauses, each returning `_stage_failure(...)` or a terminal `StageResult`. It can
be broken up naturally as an ordered list of step methods. Each step returns `StageResult | None`, and `None` means
"continue". `ExecuteStage.run()` walks that list and returns the first non-None result, so no single method needs more
than a handful of returns or branches. The state the guards share (`start_time`, `plan_prefix`, `repo_dir`,
`preferred_suffix`, `precheck`, `existing_executions`, `executor_args`, `exit_code`, `push_error`, `exec_branch`,
`exec_id`, `exec_ref`, `summary_row`, `container_status`, `base_payload`, `changed`) moves into one `ExecuteState`
dataclass held by the stage object. That removes the long argument lists.

Two constraints shape the design and were checked in the repository:

1. **Test patch targets.** More than 20 existing tests patch names _on the execute module_, for example
   `sandbox_executor.flow.stages.execute._dispatch_role`, `.check_and_resolve_stage_conflicts`, `.fetch_base`,
   `.publish_new_child_branches`, `._snapshot_child_branches`, `._fetch_branch_prefix_error`, `._discover_child_branch`,
   `._track_local_branch`, `._read_ledger_rows`, `._resolve_branch_ref`, `.changed_paths`, `._plan_budget_decision`,
   `._run_decomposed_plan`, `.touch_set_violation_result` and `.salvage_for_resume`. These tests are in
   `tests/flow/test_pipeline.py`, `test_resume_tip.py`, `test_partial_salvage.py`, `tests/flow/test_plan_refresh.py`,
   `tests/flow/test_dispatch.py`, `tests/flow/test_git_refs.py` and `tests/flow/stages/test_plan_decision.py`. So every
   method that calls one of those names **must stay in `stages/execute.py`** and look the name up through module
   globals. That rules out moving the class itself to another module.
2. **Line budget.** `stages/execute.py` is at 403 of a frozen 431 lines, and `partial_salvage.py` is at 226 of 226.
   Turning the function into a class adds roughly 40 to 60 lines (dataclass fields, method headers and docstrings). To
   stay under budget, logic that calls no patched name moves to new focused modules: the deterministic failure-veto
   lookup (about 33 lines, touches only the action index) and the empty-diff outcome builder (the superseding-row
   decision and its three message variants, about 40 lines, which calls only `superseding_failure_row` and
   `_append_superseding_execution_row`, neither patched through `execute`). Nothing is added to `partial_salvage.py`.

Aggregation: entropy is the **sum** of the step entropies (`1.2 + 1.8 + 3.5 + 1.2 + 0.8 = 8.5`), well inside the 15.0
budget. Cost is the sum (`2.5 + 2.5 + 5.0 + 2.5 + 2.0 = 14.5`). Impact is a qualitative 80: the intent is a readability
and testability refactor of the most-edited stage, and the steps' impacts overlap rather than add up. P(success) is
driven by the **bottleneck**, Step 3 (0.80). The naive chained product (`0.92 * 0.90 * 0.80 * 0.88 * 0.90 = 0.52`)
understates it, because Steps 1, 2, 4 and 5 are cheap, can be retried within the same execution, and fail visibly rather
than silently. So the overall value is 0.78. Learning value is about the per-step maximum plus the characterisation
insight (4.5).

`EV = P * Impact + mu * LV - lambda * Entropy - Cost = 0.78 * 80.0 + 0.5 * 4.5 - 0.3 * 8.5 - 14.5 = 62.40 + 2.25 - 2.55 - 14.50 = 47.60`

Strong assumptions: ruff's PLR0913 counts `self`, so methods keep at most four other parameters (most take none).
`tests/test_complexity_gate.py` treats removing a baseline noqa entry as an allowed ratchet-down, so that test needs no
change.

## Plan Description & Strategy

Five sequential steps on one execution branch:

1. **Characterise** the current `run_execute_stage` behaviour. Fill the gaps in the existing tests so every exit
   (failure message, `exit_code`, payload keys, superseding-row decision, success payload) is pinned. These tests must
   pass on the _unchanged_ code.
2. **Extract** the two self-contained chunks that call no patched name into new focused modules, so the class conversion
   has line-budget headroom: the deterministic failure-veto lookup (`flow/stages/execute_veto.py`) and the empty-diff
   outcome builder (`flow/stages/empty_diff_outcome.py`). `run_execute_stage` calls them; behaviour does not change.
3. **Convert** the function into `ExecuteState` plus an `ExecuteStage` class with named step methods. Turn
   `run_execute_stage` into a thin wrapper and drop the `# noqa: C901, PLR0911, PLR0912, PLR0915`.
4. **Test each step in isolation** in a new `tests/flow/stages/test_execute_steps.py`. Build an `ExecuteStage` with a
   prepared `ExecuteState`, stub only that step's collaborators and assert the step's return value and state changes.
5. **Validate**: affected tests, then `uv run task test`, `uv run task lint` (ruff plus module budgets) and
   `uv run task lint-docs`. Also confirm with `git diff` that `module_budgets.json` is unchanged.

Step-method mapping (run order) in `ExecuteStage.steps()`:

- `preflight`: plan-branch presence, ticker or model suffix, veto check, dry run (success result), skip-push refusal.
- `admit_and_refresh_plan`: stage-conflict resolution, budget precheck (invalid, over budget, over-deep decomposition),
  then admission and plan refresh.
- `resume_point`: snapshot the existing execution branches, fetch the base, and seed `executor_args`.
- `salvage_partial`: when `resume_partial` is set, run `salvage_for_resume`, then `_resumable_partial_branch`, append
  the partial branch to `executor_args` and log either the resume line or the no-partial-work line.
- `dispatch_executor`: `_dispatch_role`, hold unrecorded branches, publish, held failure, exit-code and push-error
  checks.
- `adopt_execution_branch`: fetch the prefix, discover the branch (ambiguity or missing), track it locally, read the
  summary row, build `base_payload`.
- `check_container_outcome`: container over budget, non-zero exit, decomposed (handled in a `_decomposed_outcome` helper
  method to keep returns at 6 or fewer), sync conflict.
- `guard_empty_diff`: resolve `plan_ref`, `changed_paths`, then the empty-diff failure through the Step 2 outcome
  builder.
- `record_execution`: missing summary row, non-success status, touch-set violation, success `StageResult` stored in
  `context.stage_results["execute"]`.
