### Intent & Git Integration

- **Step Intent:** Turn re-run evidence into one of `introduced | flaky | environment | pre-existing` deterministically,
  and build the scrubbed environment used for the environment check.
- **Git branch:** same execution branch
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. A `StrEnum` named `FailureClass` with the values `INTRODUCED`, `FLAKY`, `ENVIRONMENT` and `PRE_EXISTING`. A
   `RerunResult` dataclass holds `passed: bool`, `failing_ids`, `ran: bool` (false when the run could not start or the
   ids were absent) and `output`. A `Diagnosis` dataclass holds `classification`, `same_env`, `scrubbed`, `base`,
   `base_check` (`passed | failed | absent | unavailable | not_run`) and `environment_suspects`.
2. `IDENTITY_PREFIXES = ("GIT_AUTHOR_", "GIT_COMMITTER_")`. `scrubbed_environment(env, home, tmpdir)` returns a new
   mapping without those keys. It sets `HOME` and `TMPDIR` to the given fresh directories, which the loop creates under
   `tempfile.mkdtemp`. It keeps `UV_CACHE_DIR`, resolved from the original environment or `<original HOME>/.cache/uv`,
   and keeps `UV_PROJECT_ENVIRONMENT`. `# why:` a clean HOME must not force uv to re-download into an empty cache inside
   the network-isolated container. The input is never mutated. `identity_suspects(env)` returns the sorted removed
   names.
3. `classify(same_env, scrubbed, base)` implements the table in "Plan Description & Strategy" as early returns, with
   complexity well under the limits:
   - `same_env.passed` → `FLAKY`.
   - `scrubbed.passed` → `ENVIRONMENT`.
   - `base` ran and failed on the same ids → `PRE_EXISTING`.
   - Anything else → `INTRODUCED`. Here `base_check` records `passed`, `absent` (exit code 4 or 5, or "not found") or
     `unavailable`.
4. `diagnose(failing_ids, rerun, base_rerun, env)` is the only function with effects, and they are injected. `rerun` is
   a callable taking ids and an environment and returning a `RerunResult`; `base_rerun` is a callable taking ids and
   returning a `RerunResult`. It runs the same-env re-run and stops at flaky. Otherwise it runs the scrubbed re-run and
   stops at environment. Otherwise it runs the base re-run. Each re-run runs only the failing ids, so the cost grows
   with the number of failures, not the suite size.
5. Tests in `apps/sandbox-executor/tests/test_test_failure_classify.py`, using a fake rerun that returns scripted
   `RerunResult`s:
   - One test per table row.
   - A leaked-identity scenario: the fake fails when `GIT_AUTHOR_NAME` is in the environment and passes without it →
     `ENVIRONMENT`, with `environment_suspects` listing the leaked names, in one `diagnose` call (acceptance criterion
     4).
   - Base ids absent → `INTRODUCED` with `base_check == "absent"`.
   - Base unavailable → `INTRODUCED` with `base_check == "unavailable"`.
   - `scrubbed_environment` leaves its input unchanged and keeps `UV_CACHE_DIR`.
   - Each run order is checked by counting calls, so the base is never run after a flaky or environment verdict.

### Dependencies & Criticality

### Intent & Git Integration

- **Step Intent:** One entry point that both call sites use to turn a failed measurement into a pass, a flaky record or
  a blocked stop with the trail.
- **Git branch:** same execution branch
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. Constants: `MAX_FLAKY_RERUNS = 2` and `MAX_FIX_TURNS = 4`. `# why:` each full selection can take up to the 900 s test
   timeout, so the loop must stay inside the execute stage budget.
2. `LoopOutcome` dataclass:
   - `status` ∈ `passed | flaky_passed | blocked | exhausted`.
   - `classification`.
   - `measurement`: the last `TestMeasurement`.
   - `rows`: the recorded ledger rows, which form the trail.
   - `blocked_reason`.
   - `final_tier`.
   - `evidence_text`: a short human-readable summary of the classification, ids, first excerpts and row ids, for logs
     and errors.
3. `TestFailureLoop` dataclass holding the injected collaborators. The constructor takes one `LoopPorts` dataclass to
   keep `PLR0913` within limits. Its fields:
   - `run_selection`: a callable returning `(TestMeasurement, raw_output)`.
   - `rerun_ids` and `base_rerun`: see Step 3.
   - `fix_turn`: an optional callable taking a `FixRequest` and returning a bool.
   - `record`: a partial of `record_test_failure` with the ledger path, branch and execution id bound.
   - `ladder`: a tuple of models.
   - `start_tier`.
   - `remaining_seconds`: a callable; defaults to infinite.
   - `stage` and `head_sha`: callables.
4. `ShortSummaryRunner`: a small helper the call sites use to run `TEST_COMMAND` with
   `review_failure_detail.with_short_summary(frozen_env(cwd))`, so ids are parseable. It keeps the full raw output for
   the record before `TestMeasurement` cuts it to 2000 characters. It conforms to `test_measurement.Runner`, so it is
   passed as `run_test_task(workspace, runner=...)` and `test_measurement.py` is not edited. It runs the command in a
   new session, and on timeout kills the process group (`os.killpg`), matching `_run_in_process_group`.
5. `rerun_ids_command(ids)` builds `uv run --no-sync python -m pytest -p no:cacheprovider -q -rfE --tb=short <ids>`.
   This targeted diagnosis run on a handful of ids does not use `-n`. `# why:` xdist start-up dominates for a handful of
   ids, and serial order keeps the per-test excerpt readable. `BaseCheckout` is a context manager:
   - It runs `git merge-base HEAD <target ref>`, with the target ref injected.
   - It adds a detached worktree under `tempfile.mkdtemp(prefix="holon-test-base-")`.
   - It runs the ids there with `PYTHONPATH` set to the base `apps/*/src` and `UV_PROJECT_ENVIRONMENT` set to the
     workspace virtual environment (per the H3 outcome of Step 1).
   - It always removes the worktree in `finally`.
   - When merge-base or the worktree add fails, it returns `RerunResult(ran=False)`, which maps to `unavailable`.
6. `run(first_measurement, first_output)` algorithm, with each phase as its own short method so complexity stays low:
   1. If the first measurement passed, return `passed` (the common path costs nothing).
   2. If it is unmeasured (`rate is None`, a timeout or a missing tool), record one row with classification
      `environment` and the `run_error`, and return `blocked`. This is an honest "could not measure" result, not a bare
      halt.
   3. Diagnose: extract ids, call `diagnose`, and record row iteration 0 with the classification.
   4. `FLAKY`: re-run the ids up to `MAX_FLAKY_RERUNS` times, recording one row per re-run. If all pass, run the full
      selection once. A pass gives `flaky_passed`. If it still fails, re-enter diagnosis once with the new output; a
      second flaky verdict gives `blocked` with reason `persistent flakiness`.
   5. `ENVIRONMENT` or `PRE_EXISTING`: return `blocked`, with the reason naming the class, the ids and (for environment)
      the suspects.
   6. `INTRODUCED`: with no `fix_turn`, return `blocked` (`no fix runner available`). Otherwise loop while the fix turns
      used are below `MAX_FIX_TURNS` and `remaining_seconds() > 0`:
      - Build a `FixRequest` (classification, ids, excerpts, signature, tier, iteration). Call
        `fix_turn(request, tier)`.
      - Run the full selection.
      - A pass gives `passed`, recorded as a final success row.
      - Otherwise compute the new signature and record a row. If the signature equals the previous one, step to
        `next_tier(ladder, tier)` (copied semantics; the ladder tuple is passed in so the loop imports nothing from
        `flow`). When `next_tier` returns `None`, return `exhausted` with the full trail.
      - A new, different signature re-enters diagnosis on the new ids, because a fix can surface an environment or flaky
        class.
   7. When the bounds or time run out, return `exhausted`.
7. `fix_prompt(request)` renders a plain-text prompt:
   - The classification and the failing ids.
   - The redacted excerpts.
   - The instruction to fix the code so the listed tests pass, without weakening or deleting the tests unless the plan
     requires it.
   - That `uv run task lint` and `uv run pytest <ids>` must pass in the foreground.
   - That no command may be backgrounded.

   The text comes from a module-level template string, not a new prompt file, so no template outside the scope is
   needed.

8. Tests in `apps/sandbox-executor/tests/test_test_failure_loop.py`. They use a `FakeSuite` that plays back scripted
   outputs, a fake fix turn that records requests, and an in-memory `record`:
   - Passing first run: no re-runs.
   - Introduced → fix → pass: one fix turn, then `passed`, and the request carries the ids and excerpts (acceptance
     criterion 2).
   - Flaky → re-runs → `flaky_passed`, with recorded rows (acceptance criterion 3).
   - Environment → `blocked`, with evidence text naming `GIT_AUTHOR_NAME` (acceptance criteria 3 and 4).
   - Pre-existing → `blocked`.
   - Repeated signature → the tier steps from the start tier to the next ladder entry (acceptance criterion 5).
   - Repeated at the top tier → `exhausted`, with every row in `rows` (acceptance criterion 5).
   - A different signature after a fix → re-diagnosed.
   - `MAX_FIX_TURNS` honoured.
   - `remaining_seconds` reaching 0 stops the loop.
   - Unmeasured first run → `blocked`.
   - No fix turn → `blocked`.

   Also one `BaseCheckout` test against a real temporary git repository (git only, no uv). It uses the existing cheap
   repository fixtures (`repo_templates.py`, `worktree_fixtures.py`) with an injected runner stub in place of `uv`, and
   asserts the worktree is removed even when the runner raises.
