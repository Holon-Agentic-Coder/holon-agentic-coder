### Strategy Rationale

Single-plan, single-branch execution. The current code computes two predicates independently:

- approval: `status == APPROVED or (payload.halted_for_human and consensus.approved)`
- halt: `status == HALTED_FOR_HUMAN or payload.halted_for_human`

The gap is `status == HALTED_FOR_HUMAN`, `consensus.approved == True`, no payload flag: it fails approval and lands on
halt. The fix derives one shared `is_halt` value (status halted, or legacy payload flag) and defines approval as
`status == APPROVED or (is_halt and consensus approved)`; the `elif` then reuses `is_halt`. This keeps every existing
case identical (including the non-Mapping `consensus: True` case, which still prints `[SAFETY HALT]` because a
non-Mapping consensus is normalised to `{}`), and closes the gap.

Aggregation: overall `p_success` is the product of step successes, `0.97 * 0.97 * 0.99 ≈ 0.93`; entropy is the sum
`0.6 + 0.6 + 0.4 = 1.6`; cost is the sum `1.5 + 1.5 + 2.0 = 5.0`; impact is the intent-level impact (40: a user-facing
reporting correctness fix, not a behavioural pipeline fix); learning value is low (1.5). The bottleneck is Step 3
(full-suite and lint gates), only because it depends on unrelated suite health.

`EV = P(success) * Impact + mu * LearningValue - lambda * Delta_S - Cost`
`EV = 0.93 * 40.0 + 0.5 * 1.5 - 0.3 * 1.6 - 5.0 = 37.2 + 0.75 - 0.48 - 5.0 = 32.47 ≈ 32.5`

Strong assumptions: `StageStatus.from_str("halted_for_human")` and `StageStatus.APPROVED` remain the existing enum
