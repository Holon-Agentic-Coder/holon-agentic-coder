### Strategy Rationale

The intent is accepted as is. It is a provenance-safety fix with a clear incident history (56 uncommitted rows blocking
a Stage 4 conflict merge on 2026-11-20, and an earlier branch re-attach), and its acceptance criteria can be tested with
real git and a local bare `origin`. That infrastructure already exists in `tests/ledger_conflict_repos.py` and
`tests/review_loop_stubs.py`.

Design decisions:

1. **One owner module.** New module `flow/review/ledger_commit.py` owns "commit and push pending ledger rows". The three
   ledger paths are named once there (`intents.jsonl`, `plans.jsonl`, `executions.jsonl`, so exactly three append-only
   ledgers and no new ledger). `loop.py` (952/952 lines) and `records.py` (316/316) are at their frozen budgets, so the
   logic cannot go in either. `loop.py` gets only call sites, paid for by moving `_loop_status` out (Step 3).
   `records.py` is left untouched, although it is in the intent's scope list: nothing there needs to change.
2. **"End of each iteration" means every exit path of an iteration.** The while body has about 10 `break`s, so the loop
   commits the previous iteration's rows at the top of each pass and commits the last iteration's rows once after the
   loop. The post-loop commit goes after the final summary and action-event rows. This covers every break, including the
   resolver-failure break (acceptance criterion 3) and the no-convergence halt, without re-indenting the loop body.
3. **The ledger commit moves the reviewed head, so the loop follows it.** The resolver soft-resets to the head the host
   hands it (`pre_resolver_head`). If the host committed rows without advancing `resolved_target.head_sha`, that reset
   would leave the rows staged and fold them into the resolver's fix commit, and the next push would stop being a
   fast-forward. So after a ledger commit is pushed, `resolved_target.head_sha` advances to it. The no-convergence
   streak treats a ledger-only advance as "no diff change" (it carries `prev_head_sha` forward when the only new commit
   is the ledger commit).
4. **Gates commit first.** `_approved_post_gate` and `_stage5_conflict_gate` commit and push pending rows before probing
   and merging. `_merge_and_push` merges from `origin/<branch>` in a temporary worktree, so rows that are not pushed
   would otherwise be missing from the merge. After a merge is pushed, the flow worktree's local branch is
   fast-forwarded to the merged head, so the next ledger commit is still a fast-forward push.
5. **The stage exit is a backstop.** `run_review_stage`'s `finally` calls the same helper, so a raise, halt or failure
   never leaves ledger files modified. This is done line-neutrally because `stages/review.py` is also at its budget
   (305/305).

## Plan Description & Strategy

Add a focused `ledger_commit` module to the Stage 4 review package that commits only the three append-only ledger files
on the execution branch with the review-loop identity and no co-author trailer, then fast-forward pushes the commit
unless the run is a dry run or `skip_push`. Wire it in at four points:

1. The review loop's iteration boundaries: the top of each pass, then once after the loop and its final ledger rows.
2. The approved-post conflict gate, before the merge.
3. The Stage 5 conflict gate, before the probe.
4. The Stage 4 `finally`.

The loop follows the moved head so the resolver, the convergence streak and the CI wait stay consistent. After a
conflict-gate merge, the local branch is fast-forwarded to the merged head. Hermetic tests run real git against a local
bare `origin` and prove the three acceptance scenarios plus the helper's edge cases. The module budget file is never
touched.

     the tree is clean.
   - Log `[Review Loop] Committed N ledger file(s) at <sha8> (<reason>)`.
   - Return the SHA when the commit was pushed or `skip_push` is set, and None when nothing happened.
