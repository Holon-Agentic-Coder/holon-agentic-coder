### Step 2: Flow repositories from layered read-only templates and a fast history builder

- New `apps/sandbox-executor/tests/flow_repo_templates.py` (about 170 lines):
  - `build_flow_history(root, base_files, commits)` gives the state of `build_flow_repos` followed by one `commit_on`
    per `FlowCommit`, using five git processes (`init`, `clone`, one `fast-import` for every commit, `push --all`,
    `checkout`). The loop it replaces costs about 8 plus 7 per commit.
  - `flow_history_copy` serves that history, plus an optional git command such as a stopping merge, from a
    `shared_template` named by a hash of its content, and copies it with `copy_template`.
  - `derived_template` and `replace_with_copy` layer a fixture's fixed state over another template, here the flow
    conftest's `flow-template`.
- Deviation from the plan: it planned an explicit hermetic environment on every template git call. Every template here
  is instead requested from a function-scoped fixture or test body, so it is built under the session-autouse
  `hermetic_git_config` (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_NOSYSTEM`) and the autouse guards. That keeps the rule four
  of `repo_templates.py` without a second environment recipe. No template build runs production code.
- New `apps/sandbox-executor/tests/test_flow_repo_templates.py` (6 cases) proves the following:
  - The fast history equals `build_flow_repos` plus `commit_on` in refs, trees, upstreams, local config, `HEAD`,
    status and commit graph.
  - Bytes content round-trips, and a branch that origin lacks is refused.
  - A copy's origin names the copy, a push from the copy leaves another copy untouched, and the template is
    read-only.
  - A merge stopped in the template is copied with `MERGE_HEAD` and the conflicted index.
  - A derived template replaces an earlier copy.
- Converted:
  - `flow/test_conflict_resolver_attempt.py`: the `merging` factory fixture serves the whole conflicting
    `--no-commit` merge state from a template, one per distinct `ours`/`theirs` pair.
  - `flow/test_target_sync.py`: the `repos_with(*commits)` factory, used for the target move, code conflict,
    ledger-only conflict, marker file and sync-conflict row scenarios.
  - `flow/test_conflict_classes.py`: `_conflicted` and the non-UTF-8 case use `build_flow_history`. Each case is a
    distinct one-off repository, so a template would only add a repack.
  - `flow/test_conflict_resolver_role.py`: the `work_with(*commits)` factory, and `build_flow_history` for the one
    case with its own base.
  - `flow/test_target_sync_resume.py`: the `repos_with(*commits)` factory. The merge stays in each body, because the
    test interrupts it there.
  - `flow/test_admission.py`: the `own_plan_with(touch_set, before, after)` factory derives one template per plan
    shape from `flow-template`. The local flow's linked worktree stays per test.
  - `flow/test_ledger_worktree_cleanup.py`: the execution branch with its ledger row is a derived template.
  - `test_pre_push_sync_conflict.py` and `test_partial_salvage.py`: the fixture bodies became `shared_template`
    builders, unchanged otherwise.
- Checks: the nine files plus the new test passed `-p no:xdist` (168 passed in 31.65 s) and
  `-n auto --dist worksteal` (168 passed in 8.88 s). A git origin count over the 15 files went from 8,818 to 6,736.

### Step 3: Worktree-sandbox, default-branch and combined-base repositories from templates

  - `build_primary_with_remote`, for `test_host_worktree_sandbox.py`'s `repo`;
  - `build_seeded_primary`, for `flow/test_worktree_all_stages.py`'s `sandbox_repo`;

- `repo` keeps its `monkeypatch` lines (uid, gid, `GIT_CONFIG_GLOBAL`, identity), and the template is built after them
  under the same environment. `flow_worktree` and `sandbox_repo` keep their own `git worktree add` per test.
  `test_host_worktree_sandbox.py` shrank from 1,078 to 1,063 lines.
- Mode evidence for the write-preflight, ACL and rr-cache cases: an ad-hoc comparison (not committed) of a fresh
  `build_primary_with_remote` against a template copy found the same entries and the same mode on every path outside
  `objects/`, for example `repo` and `repo/.git` at `0o755` in both. Inside `objects/`, a copy's pack files carry the
  owner write bit, which no test reads. The preflight and ACL cases set the modes they assert with `chmod` themselves,
  and every one of them passes on copies. No case needed to keep a per-test build.
- `test_combined_base.py`: `_build_into` writes the whole history (base, plan, execution, main advance, child, merge
  or squash, integration merge, ledger row) with one `fast_import`, a generic `GraphCommit` graph writer added to
  `flow_repo_templates.py`, instead of about 30 git processes. The `build` factory fixture serves each distinct
  history from a template. An ad-hoc comparison (not committed) of the old and new builders for four argument shapes
  found these identical: tree per ref, origin refs, `HEAD`, the topological graph with subjects, authors and trees,
  status, the local config of seed and host, and the host's refs.
- `build_flow_history` now fast-imports straight into the bare `origin` and clones it on `FLOW_BRANCH` (three git
  processes, and no push for the network guard's `ls-remote --get-url` probe). Plain file edits then give the clone
  `build_flow_repos`'s refs and branch config. `test_flow_repo_templates.py` checks that equivalence.
- `test_resume_tip.py` and `test_executor_run_salvage.py` already used templates, and their remaining per-test
  commits are distinct scenarios that run after production calls, so they were left unchanged.
- `flow_repo_templates.py` ends at 214 lines, over the plan's soft target of 200. It is a test helper with no module

### Step 5: Shared read-only scenarios (exploratory) — not applied

From the base per-test git log, these groups of tests have identical call-phase production sequences:

- the mount and rr-cache tests in `test_host_worktree_sandbox.py` and `test_worktree_all_stages.py`, 10 processes each;
- two `test_executor_run_salvage.py` runs, 64 each;
- the killed-step cases;
- the Step 4 groups.

None of them is a read-only scenario that only differs in its final assertion:

- The mount tests build their own worktrees per test, and sharing them would need a module-scoped repository set up
  before the autouse guards.
- The two executor runs take different inputs (agent exit status 1 against a budget breach) and assert different exit
  codes.
- The killed-step cases are kill windows.
- The three SSH-origin pipeline tests in `test_worktree_all_stages.py` share a pipeline run, but two of them then
  mutate the state through a `FlowContext` that holds the dispatcher, so the run cannot be handed out as plain data.

No module-scoped fixture was added, so there is no order-dependence risk. Learning: in these files, a scenario worth
sharing is one that writes repositories, and that sits outside this step's read-only rule.
