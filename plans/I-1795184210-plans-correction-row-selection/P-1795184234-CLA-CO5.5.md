### Strategy Rationale

The defect is narrow and well located:

- `_parse_predicted_from_plans_ledger` in `apps/sandbox-executor/src/sandbox_executor/calibration.py` returns on the
  first `is_row_of_plan` match, so any superseding plans row is ignored. That includes a correction row and also the
  existing flow-written `decision_recorded_by: "flow"` row, which already uses `ledger_revision + 1`.
- `docs/ledger_schema.md` already documents superseding rows for executions (empty-diff, touch-set, interrupted) and for
  the flow's decomposition-decision plans row, but it defines no plans-row correction.

The fix reuses those conventions instead of inventing new ones:

1. A plans correction row is a full copy of the superseded row, with the corrected metric fields, `ledger_revision` set
   to the highest existing revision plus 1 (so at least 2), a fresh `created_at`, and provenance fields. The existing
   duplicate check in `ledger.py` keys on (intent, plan id, revision), so such a row already passes validation.
2. The reader picks the row with the highest `ledger_revision`, breaks ties by `created_at` instant, and on a full tie
   takes the last ledger line. This matches the intent's goal and the "readers take the newest matching row" wording in
   the schema.
3. A cross-check compares the selected row against the plan file's Overall Plan Metrics table and against the latest
   matching execution summary row's `predicted_metrics`. On a mismatch it logs a warning naming the metric and both
   values. The selected value is still used; the warning is only advisory, because the plan file or the execution row
   may itself be the wrong one.

**Aggregation:** `p_success` is the product-like bottleneck of Step 2 (0.88) and Step 4 (0.93), with the other steps
close to 1, rounded down to 0.85 to allow for lint and prettier churn. Entropy is the sum of step entropies
(`0.3 + 2.4 + 0.9 + 1.2 + 0.7 = 5.5`). Cost is the sum of step costs (`0.5 + 4.0 + 1.5 + 3.0 + 1.0 = 10.0`). Impact is a
qualitative judgement: calibration accuracy feeds every plan's priors, but the change is a reader fix plus a documented
convention, so 60. Learning value is mostly from Step 1's backlog measurement plus validating the correction convention.

`EV = P(success) * Impact + mu * LearningValue - lambda * Delta_S_intent - Cost`

`EV = 0.85 * 60.0 + 0.5 * 5.0 - 0.3 * 5.5 - 10.0 = 51.00 + 2.50 - 1.65 - 10.00 = 41.85`
