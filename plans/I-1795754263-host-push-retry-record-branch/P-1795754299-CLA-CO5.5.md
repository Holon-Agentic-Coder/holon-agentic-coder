## Plan Description & Strategy

The plan has three behavioural changes and one test module, executed as a single plan on one execution branch:

1. **Retry (host_remote.py).** Split the current one-shot push into `push_commit_once` (unchanged behaviour, still used
   for the best-effort recovery-branch pin) and a retrying `push_commit`. The retrying version:
   - makes up to `PUSH_ATTEMPTS` attempts, sleeping `PUSH_BACKOFF_SECONDS * 2 ** (attempt - 1)` between them;
   - logs every failure with its attempt number and the full redacted remote output through an optional `log` callable;
   - does not retry input-validation refusals, a missing workflow scope or a ref name that is too long.

   `publish_new_child_branches` passes the log through.

2. **Record before push (execute.py + execution_recovery.py).** After the executor container exits and the unrecorded
   branches are held, but before the host push, the stage records the new execution branch that carries a summary row.
   It sets `context.execution_branch` and saves the checkpoint at `context.checkpoint_path`, following the
   `save_admission` pattern. When the push still fails after retries, the failure payload also carries
   `execution_branch`.
3. **Resume reuse (execution_recovery.py + one ExecuteStage step).** On a Stage 3 resume where the recorded
   `execution_branch` sits under the current plan, is absent from origin and has a summary row, the stage re-pushes it.
   The source is `refs/heads/<branch>`, or the sha at `refs/holon/recovery/<exec_id>` when the local branch is gone. The
   stage then skips salvage and executor dispatch, and continues with the normal adopt, outcome, empty-diff and record
   steps. No second E-branch is ever cut.
4. **Tests (one new module).** One module covers:
   - a fake remote that rejects once and then accepts, and one that always rejects;
   - a resume that re-pushes without dispatching;
   - a real temporary bare remote whose pre-receive hook rejects the first push and accepts the second, with assertions
     on the logged remote output and attempt number.

Then the affected tests, the full suite once, and lint.
