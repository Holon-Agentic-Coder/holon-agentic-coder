### Strategy Rationale

The consensus decision already has one funnel: `consensus_blockers` / `decide_returned_consensus` in
`flow/review/verdict.py`, called once per iteration from `flow/review/loop.py` (line ~383 and ~407) and again from
`approval_gates.record_iteration_gates`, which recomputes the diff verdict from `IterationGates.blockers`. Any string in
`blockers` already downgrades APPROVED to CHANGES_REQUESTED and records `DiffGate.approved=False`. So the cheapest
correct gate is: a pure new module computes the two facts (undisposed finding ids, wrong verdict count), `verdict.py`
renders them as blocker strings, and `loop.py` appends them to `blockers` before the verdict and the gates are decided.

Planning facts that shaped the steps:

- `decide_consensus` (`review_ensemble.py:836`) already FAILs when the returned count differs from the configured
  `ensemble_size` and already refuses APPROVED while any reviewer reports any finding (a nit included). The new
  exact-three rule therefore only bites when `ensemble_size != 3`, and the new undisposed rule only bites on findings a
  previous resolver pass left open (or carried findings), never on the current reviewers' findings.
- Probe 1 (blocker appended inside `consensus_blockers`): 48 unit tests failed, because `blockers` also feeds
  `reviewer_objected` (loop line ~388), which switches the CI inspection fast path and makes dry runs (zero reviewers)
  look objected. Probe 2 (downgrade only an otherwise APPROVED verdict): 27 failed, all approvals on fewer than three
  reviewers. Hence the new blockers are appended **after** `reviewer_objected` is computed, so the CI path and dry runs
  are untouched and only approvals change.
- `flow/review/loop.py` is 940 lines against a frozen 950-line override in `holon-config/hygiene/module_budgets.json`.
  The loop change is capped at about 6 net lines; all logic lives in the new module and `verdict.py`.
- Host-side resolver dispositions carry no `commit_sha` (only the container entrypoint stamps it). "Applied with a
  commit" is made true by stamping `applied` dispositions with the resolver's pushed head in the loop; an applied fix
  that was never pushed stays undisposed and blocks approval, which is the honest outcome (the reviewed head lacks it).
- Rejections reuse `resolver_evidence.has_stated_reason`, so an empty or `unspecified` reason counts as no reason,
