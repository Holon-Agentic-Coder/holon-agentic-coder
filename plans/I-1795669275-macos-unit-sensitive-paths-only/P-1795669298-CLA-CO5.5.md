## Plan Description & Strategy

The macOS leg keeps its job and its check name `unit (macos-latest)` on every head; only its steps after a new "macOS
relevance gate" step are guarded, exactly as the bookkeeping gate guards them today. The gate is the
`.github/actions/macos-relevance-gate` composite action from PR #315, reworked from "skip when every path is neutral" to
"run when any changed file is platform-sensitive by path or by content".

Key design decisions:

1. **Changed files and their contents come from local git, not the compare API.** On `pull_request` the checkout is the
   merge commit `refs/pull/N/merge` (`GITHUB_SHA`). The action deepens that one commit to depth 2
   (`git fetch --no-tags --no-recurse-submodules --depth=2 origin "$GITHUB_SHA"`), and the script reads
   `git diff --name-status -z -M HEAD^1 HEAD`: exactly what the pull request changes on top of its base. New content is
   `git show HEAD:<new path>`, old content is `git show HEAD^1:<old path>` (rename and delete use the old path). This
   gives full contents, has no 300-file cap and needs no token. The same function judges a squash-merge commit `C`
   against `C^1`, so the replay over merged pull requests uses the same code. Any git error, a HEAD that is not
   `GITHUB_SHA`, a HEAD without two parents or an empty diff means "run".
2. **Rule order (first match decides, only the last rule skips):** `event-not-pull-request` (push to main,
   workflow_dispatch) → `rerun-attempt` (kept from #315: re-running the job forces the leg) → `force-label` (`ci-macos`)
   → `changed-files-unreadable` → `no-changed-files` → `sensitive-path` → `sensitive-content` → `internal-error` (any
   exception) → `all-neutral` (skip).
3. **Sensitive paths (regardless of content).** Matched against the new path and, for renames and deletions, the old
   path:
   - any `pyproject.toml` and any `uv.lock` at any depth;
   - every path under `.github/`;
   - the gate itself: `scripts/macos_relevance*.py` and `apps/sandbox-executor/tests/test_macos_relevance*.py`;
   - shell: `*.sh`, `*.bash`, the repository launcher `holon` (bash shebang), `Makefile`, and any file whose first line
     is a `#!` shebang naming `sh`, `bash` or `zsh`;
   - containers: `Dockerfile`, `Dockerfile.*`, `*.Dockerfile`, `docker-bake.hcl`;
   - launcher and keychain code: `apps/sandbox-executor/src/sandbox_executor/launcher/` (whole package),
     `apps/sandbox-executor/src/sandbox_executor/entrypoint/`, `apps/sandbox-executor/entrypoint/`, and any path whose
     file name contains `keychain`, `launcher` or `credential`;
   - test-wide configuration: every `conftest.py` (a fixture change reaches every test).
4. **Sensitive content (Python files only, `.py`; new content and old content are both scanned; tests use the same
   rule).** Patterns are regular expressions applied per line after stripping `#` comments; each one carries a short
   reason that is printed in the log:
   - process: `^\s*(import|from)\s+subprocess\b`, `\bsubprocess\.`,
     `\bos\.(system|popen|fork|exec\w*|spawn\w*|kill|killpg|getpgid|setsid|wait\w*)\(`, `\bpexpect\b`,
     `\basyncio\.create_subprocess_`;
   - platform checks: `\bsys\.platform\b`, `^\s*(import|from)\s+platform\b`, `\bplatform\.`, `\bos\.name\b`,
     `\bos\.uname\(`;
   - POSIX-only modules: `^\s*(import|from)\s+(signal|fcntl|termios|pty|tty|resource|pwd|grp|select)\b`, `\bsignal\.`;
   - home and environment: `\bHOME\b` on a line containing `environ` or `getenv`, `\bexpanduser\(`, `\bPath\.home\(`,
     `\bTMPDIR\b`, `^\s*(import|from)\s+tempfile\b`, `\bgettempdir\(`;
   - filesystem operations beyond joining (`os`, `os.path`, `shutil`, pathlib methods):
     `\bos\.path\.(realpath|abspath|samefile|islink|ismount|expanduser|getmtime|getctime|getatime)\(`,
     `\bos\.(chmod|chown|lchown|symlink|link|readlink|rename|replace|scandir|listdir|walk|stat|lstat|access|getcwd|chdir|umask|statvfs)\(`,
     `^\s*(import|from)\s+shutil\b`, `\bshutil\.`, and pathlib method calls
     `\.(resolve|absolute|samefile|is_symlink|symlink_to|hardlink_to|readlink|chmod|lchmod|stat|lstat|owner|group|iterdir|glob|rglob|walk|rename|replace|expanduser|cwd)\(`;
   - keychain and launcher names anywhere in the text: `\bkeychain\b` (case-insensitive),
     `\bsecurity\s+find-generic-password\b`, `\bsandbox_executor\.launcher\b`.
   - Neutral on purpose (documented as accepted risk): pure joining and naming (`os.path.join`, `basename`, `dirname`,
     `splitext`, `PurePath`, `/` operator, `.name`, `.suffix`, `.parent`), and plain content I/O (`open`, `read_text`,
     `write_text`, `read_bytes`, `write_bytes`, `mkdir`, `exists`, `is_file`, `is_dir`, `unlink`, `rmdir`, `touch`). A
     content file larger than 1 MiB or not UTF-8 decodable counts as sensitive.
5. **Every other file is neutral** (markdown, JSON/JSONL, YAML outside `.github/`, TOML other than `pyproject.toml`,
   templates, Python without a match). The log prints every judged path with `sensitive`/`neutral`, the side
   (`new`/`old`) and the matched reason, one line per path, plus a one-line summary and, on a skip, how to force the leg
   (`ci-macos` label or re-run).
6. **Timing:** the CI Timing Gate step and the "Full run completed" marker step are guarded by the relevance output, so
   a skipped leg produces neither a timing record nor a compare verdict; uploading a record happens only on push to
   main, where the leg always runs. `scripts/ci_timing_gate.py` needs no change unless a test shows otherwise.
7. **Bookkeeping gate:** `ci-macos` joins `RESULT_AFFECTING_LABELS` (from #315), so labelling or unlabelling a pull
   request always re-runs. The bookkeeping chain still requires the previous run's marker step; a relevance-skipped
   macOS leg has no marker, so a later bookkeeping-only push on that pull request runs the gate again (which then skips
   the macOS leg again by the same rule). The ubuntu leg, the bookkeeping gate's behaviour on ubuntu and the Workspace
   survival job are untouched.

Module layout (each below ~250 lines; `holon-config/hygiene/module_budgets.json` covers only the flow package and is
never touched):

- `scripts/macos_relevance_rules.py`: path rules, content patterns, `judge_change(change, read_blob) -> Verdict`.
- `scripts/macos_relevance_git.py`: `ChangedFile` (status, new path, old path), parsing of
  `git diff --name-status -z -M`, blob reading with a size cap, all through one injectable runner for tests.
- `scripts/macos_relevance.py`: event facts, rule order, log lines, `$GITHUB_OUTPUT`, `--replay-commit <sha>` and
  `--replay-range` CLI for the replay. Standard library only, Python 3.9 syntax (the macOS runner's own `python3`).

## Step 3: Read changed files from git and rewire the decision script

- **Sub‑intent recommendation:** NO

  "run on any error".
- **Step Type:** IMPLEMENTATION

### Intent & Git Integration

- **Step Intent:** Produce the list of changed files with old and new paths and contents for a pull-request merge commit
  (CI) or a squash-merge commit (replay), and decide with the rule order of Plan Description item 2.
- **Git branch:** same execution branch
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. Create `scripts/macos_relevance_git.py`: a `GitRunner` callable type (arguments in, stdout bytes out, raises on a
   non-zero exit), the default using `subprocess.run` with `check=True`, a timeout and `cwd` the workspace.
   `changed_files(runner, base, head)` parses `git diff --name-status -z -M --no-ext-diff base head` into
   `ChangedFile(status, path, old_path)` (status letters A, M, D, R, C, T; R/C carry the old path).
   `blob_text(runner, rev, path, cap)` uses `git cat-file -s` first and `git show rev:path` only under the cap.
   `merge_parents(runner, sha)` returns the parents of `sha` via `git rev-list --parents -n 1`.
2. Rework `scripts/macos_relevance.py`: keep `RelevanceFacts`, `facts_from`, `event_rule`, `_printable`, `main`'s
   "always exit 0 and write `skip=false` on any error" contract, and `write_step_summary`/`write_output`. Drop the
   `GateClient`/`compare` import and `RULE_DIFF_TOO_LARGE`. Add facts `sha` (from `GITHUB_SHA`). After the event rules:
   check HEAD equals `GITHUB_SHA` and has exactly two parents, else `changed-files-unreadable`; diff `HEAD^1 HEAD`;
   empty list gives `no-changed-files`; judge every file (no early exit, so the log lists every path); the first
   sensitive verdict gives `sensitive-path` or `sensitive-content` with the path and reason as the detail; otherwise
   `all-neutral` skips. The `incomplete-event` rule now requires `sha` and a positive run attempt.
3. `Judgement.lines()` prints `macos-relevance-gate: <run|skip> (<rule>): <detail>`, then one line per judged path
   `  <sensitive|neutral> <status> <path> [<- old path]  <side>:<reason>`, then the skip sentence on a skip.
4. Replay CLI: `--replay-commit <sha>` judges `<sha>^1..<sha>` as an unlabelled pull request, with no `GITHUB_*` needed;
   `--replay-range <rev-range>` iterates the first-parent commits of the range whose subject ends in `(#N)` and prints
   one table row per pull request: number, run/skip, triggering path and reason.
5. Keep each module below ~250 lines; if `macos_relevance.py` grows past that, move the replay into
   `scripts/macos_relevance_replay.py` (add it to the touch set via the execution notes).

### Strategy Rationale

The intent is accepted as is: the previous neutral-list design was measured to skip nothing, and the intent states a
precise inversion (run only on sensitive paths or content) with a fail-to-run default for every unknown. The plan reuses
#315 for everything that is still right (composite action, event rules, `ci-macos` label, step guards, log format,
"always exit 0" contract) and replaces the two parts that cannot express the new rule: the path-only judgement and the
compare-API file list (which has no file contents and caps at 300 files). Reading the pull request's own merge commit
with local git gives old and new contents for free and lets the replay of merged pull requests run the exact CI code
offline.

The main judgement call is the meaning of "filesystem operations beyond pure path joining". Plain reads and writes are
kept neutral because they behave the same on APFS and ext4 and appear in most test files; operations whose results do
differ (symlinks and real paths, permissions, listing order, cwd, home, temp dirs, rename) are sensitive. Step 6 gives
the reviewer the measured consequence of that choice.

Aggregation: entropy is the sum of step entropies (`0.8 + 2.0 + 2.0 + 1.5 + 1.2 + 1.0 + 0.5 + 1.0 = 10.0`); cost is the
sum of step costs (`1.5 + 4.0 + 4.0 + 2.5 + 3.5 + 3.0 + 1.5 + 3.0 = 23.0`); impact (75) is a qualitative judgement of
about 3 minutes off most pull-request heads, below the sum of step impacts because the steps are not independently
valuable. `p_success` (0.72) is set by the bottleneck chain Steps 3, 4, 5 and 8 (each 0.78 to 0.85, with correlated
risk: all depend on the same rule and checkout shape) rather than their raw product (about 0.46), since a failure in any
of them is usually fixed within the same execution. The overall EV is computed in the metrics section:
`EV = 0.72 * 75.0 + 0.5 * 5.5 - 0.3 * 10.0 - 23.0 = 30.75`.

No sub-intents: the predicted entropy (10.0) is within the 15.0 budget, and every step works on the same small set of CI
files, so splitting would only add flow overhead and merge ordering between children.
