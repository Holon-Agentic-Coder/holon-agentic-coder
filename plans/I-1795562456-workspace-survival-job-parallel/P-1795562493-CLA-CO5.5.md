### Implementation Details (No code blocks, only logic/steps)

1. Create `apps/sandbox-executor/tests/stress_support.py` (aim for under 200 lines; module docstring, type hints and
   docstrings per the ruleset). It holds:
   - `ChildContext`, a frozen dataclass with `root`, `home`, `workspace` (`<home>/.holon-sandbox/workspace`), `tmpdir`
     (`<root>/tmp`, a sibling of HOME, never inside it, so creating temporary files cannot touch the whitelisted
     `~/.holon-sandbox` tree) and `basetemp` (`<root>/tmp/pytest-basetemp`). There is no `created_by` or ownership
     field; ownership is shown through the directory layout.
   - A context manager `child_context(label)` that creates one `tempfile.mkdtemp(prefix=f"holon-stress-{label}-")` root
     with `home/` and `tmp/`, and removes it on exit, like the `TemporaryDirectory` it replaces.
   - `child_env(context, sentinel_var)`: it calls `hermetic_fixtures.simulated_container_env(context.home, sentinel)`,
     then sets `TMPDIR`, `TMP` and `TEMP` to `context.tmpdir`. It removes every key starting with `PYTEST_XDIST_` and
     `PYTEST_CURRENT_TEST`, so an outer xdist worker's identity never reaches the child controller.
   - `child_suite_command(context, *extra)`: it returns `pytest_suite_command("--basetemp", context.basetemp, *extra)`.

     reach the other child's directories.

     the wall time from `time.monotonic()`, and the child's final pytest summary line. It prints one line,
     `stress-child <label>: <summary> in <wall>s`, so per-child times show in `-rP` / `-s` output and in the junit
     system-out (needed for the Step 7 measurements).
   - `seed_canary_workspace(context)` reproduces the canary's current layout exactly: `canary.txt` with the same
     content, `important_code.py`, and an empty `.git` directory. It returns the expected state.
   - `canary_violations(context, expected, index_root, index_before)` returns a list of human-readable violations. It
     covers the same conditions the canary asserts today: workspace missing, marker missing or changed, dummy file
     missing, `.git` missing, and knowledge-index changes found with `knowledge_index_snapshot` /
     `describe_index_changes`.
   - `survival_violations(workspace, canary_path, canary_content, head_sha)` returns a list of violations. It covers the
     same conditions as today, in the same order: workspace directory missing, canary file missing or changed, `.git`
     missing, `git rev-parse HEAD` failing, HEAD moved.

## Step 5: Exploratory, bounded: tune child worker counts under concurrency

- **Sub‑intent recommendation:** NO
- **Reasoning:** A short experiment with an unknown payoff. It is cheap to run, and the result is adopted only if it
  clearly helps.
- **Step Type:** EXPLORATION
- **Exploration level:** EXPLORATORY

- **Hypothesis being tested:** When two children run concurrently on 4 vCPUs, `-n auto` in each (8 workers) causes
  enough oversubscription that a fixed 2 or 3 workers per child gives a shorter outer wall time.
- **Learning target:** How the CPU split behaves for nested xdist runs on the CI runner shape. This tells future intents
  whether the stress job, or the macOS unit job, would benefit from fixed worker counts.
- **Maximum acceptable cost for this learning:** 3 outer stress runs (about 15 minutes of wall time) and cost 1.5.

### Intent & Git Integration

- **Git branch:** same execution branch
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

   `PYTEST_XDIST_*` worker-identity keys. Exempt `PYTEST_XDIST_AUTO_NUM_WORKERS` from that removal on purpose, and
   document the exemption.
2. Under `taskset -c 0-3`, run the concurrent outer command once per variant: `auto` (the Step 4 run can be reused), `2`

   performance figure; the reported numbers come from Step 7's N = 3. Record outer wall time, per-test durations and

3. Adopt a fixed count only if it improves the outer wall time by at least 10 % over `auto`. If adopted, set it inside
   `child_env`, never in the workflow, so local and CI runs match. Base it on the CPU count:
   `max(1, os.cpu_count() // 2)` (applied only when an outer xdist worker is detected), and document it in the

### Strategy Rationale

The intent is accepted as written. Planning established three facts:

- Preference (2) is already implemented, because `pytest_suite_command` already passes `-n auto --dist worksteal`.
- HOME and the workspace are already per test.
- The real obstacle to preference (1) is the shared temporary root (`TMPDIR` and pytest's `/tmp/pytest-of-holon`),
  together with the outer xdist worker environment leaking into the children.

The plan therefore fixes isolation first (Step 2) and proves it, along with both guards tripping (Step 3), before it
turns on concurrency (Step 4). This order means no point in the history has concurrent tests that could interfere.

Preference (3) is deliberately gated (Step 6). The guarantees' strength comes from running the whole directory. A
narrower selection that cannot be checked mechanically would weaken them, and its expected cost (a missed hazard of
incident severity) outweighs a further minute of CI. If the gate shows the time is still too high, a follow-up intent is
better value than an improvised rule.

Aggregation:

- `entropy_pred` is the sum of the step entropies: `0.8 + 2.0 + 1.8 + 1.2 + 1.0 + 0.6 + 1.0 = 8.4`.
- `cost_pred` is the sum of the step costs: `2.5 + 3.0 + 3.0 + 1.5 + 1.5 + 0.5 + 4.0 = 16.0`.
- `p_success_pred` (0.72) is a qualitative figure set by the bottleneck chain, Steps 2, 3, 4 and 7. Those steps' risks
  are correlated (all are test-only changes on one branch). The fallbacks lift the probability above the naive product:
  Step 4 can revert to serial, and Step 3 can use in-process controls.
- `impact_pred` (70) is overall impact. The two tests overlap well on a subprocess-heavy suite, and the 600 s ceiling
  failures stop. Steps 5 and 6 are optional.
- `learning_value_pred` (6) is the highest of any step (Steps 1 and 5): nested-xdist behaviour on 4 cores, which is
  reusable for the macOS unit job.

The strongest assumption is that a 4-core `taskset` local run predicts the CI ratio. The real PR job time in Step 7
checks this.
