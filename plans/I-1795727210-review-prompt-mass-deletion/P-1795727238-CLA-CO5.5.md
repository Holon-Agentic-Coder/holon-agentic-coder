### Strategy Rationale

The failure is "Prompt is too long" when a PR deletes thousands of files: both the full review (`build_scoped_diff` in
`review_request.py`, called by `build_review_request` in `review_ensemble.py`) and the scoped delta review
(`build_delta_request` in `flow/review/delta_review_request.py`, via `DeltaRepo.diff`) put the raw `git diff` text into
`ReviewRequest.diff_text`. Both requests flow into the same prompt renderer, so one pure function
`bound_review_diff(diff_text: str) -> str` in `review_request.py`, applied at both diff sources, fixes both modes with
the smallest blast radius. A pure text-in/text-out function is easy to test exhaustively on synthetic diffs and on real
temporary git repositories, and it trivially guarantees byte identity (it returns the input object untouched when no
rule fires).

Alternatives rejected: (a) asking git for `--name-status` and re-running a filtered diff would need extra git calls at
two sites with different pathspec/rename settings (`build_scoped_diff` uses default rename detection, `DeltaRepo.diff`
uses `--no-renames`) and could not enforce the byte cap; (b) a new module would contradict the acceptance criterion that
`review_request.py` holds the step, and the module has ample budget room (~250 lines).

Aggregation: overall `p_success` is the product of the step successes, softened because Steps 2-4 are low risk and
mostly fail only if Step 1 is wrong: `0.86 * 0.97 * 0.95 * 0.98 ~= 0.78`. Entropy is the sum of step entropies
`2.5 + 0.8 + 1.5 + 0.7 = 5.5`. Cost is the sum `6.0 + 1.5 + 4.0 + 1.5 = 13.0`. Bottleneck: Step 1 (the parser and the
three rules). EV: `EV = 0.78 * 70.0 + 0.5 * 4.0 - 0.3 * 5.5 - 13.0 = 54.60 + 2.00 - 1.65 - 13.00 = 41.95`.

Strong assumptions: (1) "a directory holding at least 25 deleted files" means the deleted file's immediate parent
directory (not recursive), matching rule 3's "parent directory" wording; a deletion spread over many small directories
is instead bounded by rule 3's byte cap. (2) The summary block is appended after the inlined sections; its size is not
counted against the 400000-byte cap but is itself bounded (see Step 1). (3) `test_delta_review.py` stays unchanged
(acceptance criterion "pass unchanged"); new delta-path coverage goes in the new test file. It remains in the scope list
only because the intent lists it.

## Plan Description & Strategy

Add a pure `bound_review_diff` step to `review_request.py` that splits a unified diff into per-file sections, classifies
each section (bulk deletion, generated, ordinary), inlines ordinary sections in git order up to 400000 UTF-8 bytes, and
appends a summary block for everything not inlined. When nothing is summarised or omitted, the original string is
returned unchanged. `build_scoped_diff` returns the bounded text; `build_delta_request` bounds the delta diff before
redaction. A new test module builds real git repositories in `tmp_path` to cover every acceptance criterion, then the
affected tests, lint and the full suite run once each in the foreground.

### Intent & Git Integration

### Implementation Details (No code blocks, only logic/steps)

1. Module constants in `review_request.py` (domain-named, near the top): `BULK_DELETION_MIN_FILES = 25`,
   `SUMMARY_SAMPLE_SIZE = 5`, `GENERATED_PATTERNS = ("*.lock", "package-lock.json", "*.min.js", "*.map")`,
   `INLINED_DIFF_MAX_BYTES = 400_000`. Import `fnmatch` and `posixpath` from the standard library.
2. A small frozen dataclass `DiffSection` with `path: str`, `text: str`, `deleted: bool`. Keep it private to the module
   (leading underscore) unless tests need it; tests should go through the public `bound_review_diff`.
3. `_split_sections(diff_text) -> tuple[str, list[DiffSection]]`: split with `str.splitlines(keepends=True)` so
   concatenating sections reproduces the input exactly. Every line starting with `diff --git ` opens a new section;
   anything before the first header (normally empty) is a preamble kept verbatim. Lines are appended to the current
   section unchanged.
4. `_section_path(lines) -> str`: prefer `+++ b/<path>` and, for deletions, `--- a/<path>` (strip trailing newline,
   strip a trailing tab-suffix if present); for sections without `---`/`+++` lines (binary or mode-only changes, pure
   renames) use `rename to <path>`, else parse the `diff --git a/X b/Y` header: when unquoted, `X == Y` for non-renames,
   so take the first half of `rest = line[len("diff --git a/"):]` of length `(len(rest) - 3) // 2`. Quoted paths
   (`"a/...`) are C-unquoted best-effort by stripping quotes and the `a/`/`b/` prefix; the exact display form only
   matters for directory grouping and sample text.
5. `deleted` is true when a header line (before the first `@@` or `---`) starts with `deleted file mode`.
6. `_is_generated(path)`: `fnmatch.fnmatchcase(posixpath.basename(path), pattern)` for any pattern in
   `GENERATED_PATTERNS` (so `package-lock.json` matches at any depth and `*.lock` matches `uv.lock`).
7. `_parent(path)`: `posixpath.dirname(path) or "."`.
8. `bound_review_diff(diff_text: str) -> str`, kept under the complexity limits by delegating:
   - Parse sections; count deletions per parent directory with `collections.Counter`; the bulk directories are those
     with a count of at least `BULK_DELETION_MIN_FILES`.
   - Partition in git order into `generated` (generated pattern, checked first, whatever the change kind), `bulk`
     (deleted and parent in the bulk set) and `ordinary` (everything else).
   - Walk `ordinary` in order, accumulating `len(section.text.encode("utf-8"))`; a section is inlined only if the
     running total plus its size stays at or below `INLINED_DIFF_MAX_BYTES`; otherwise it goes to `omitted` and the walk
     continues (a later smaller section may still fit; it is still emitted in git order relative to other inlined
     sections). No section is ever truncated.
   - If `generated`, `bulk` and `omitted` are all empty, return `diff_text` itself (byte-identical, same object).
   - Otherwise return preamble plus the inlined sections joined in original order, followed by the summary from
     `_summary_block`.
9. `_summary_block(bulk, generated, omitted) -> str`: a plain-text block starting on a new line (ensure the inlined text
   ends with a newline before appending), headed `# Review diff summary (not inlined)` so it reads as a diff comment
   outside any hunk. It contains:
   - The rule sentence, once, when bulk or generated sections exist: "Bulk deletions (a directory with at least 25
     deleted files) and generated files (_.lock, package-lock.json, _.min.js, \*.map) are not inlined; judge a bulk
     deletion by its file count and sample paths, and a generated file by its count and sample."
   - For each bulk directory (sorted by path): `- <dir>/: <n> deleted files; sample: <p1>, ..., <p5>` (first five in git
     order).
   - For generated files: one line per parent directory with count and up to five sample paths, labelled as generated.
   - When `omitted` is non-empty: a sentence that the inlined diff is capped at 400000 bytes and these whole file
     sections were left out, then one line per parent directory with its file count, `- <dir>/: <n> files not shown`.
   - Keep each formatter a separate helper (`_grouped_lines`, `_sample`) so every function stays well within `C901`,
     `PLR0912` and `PLR0915`. Optionally cap each listing at 200 directory lines plus an "and N more directories" line
     so the summary itself stays bounded even for pathological trees.
10. In `build_scoped_diff`, return `bound_review_diff(diff_text), scoped` (apply after the scoped-empty fallback, so the
    fallback check still inspects the raw diff). Update the docstring to say the diff is bounded.
11. Update the module docstring to mention the bounding step. Do not touch `ReviewRequest`, the placeholder rendering or
    `_missing_inputs`.
