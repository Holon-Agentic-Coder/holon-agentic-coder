  - A stage-start template built from a session fixture would run production code before the autouse guards.
  - A template built inside the first test's guards inherits that test's monkeypatches, for example
    `consult.DEFAULT_LEDGERS` pointing at that test's own host and `HOME`. Its contents could then depend on which test
    asked first.
  - Branch names embed `time.time()` (P- and E- ids). A template that is minutes old has older ids than the current
    clock, and stale-branch or clock-skew logic might treat it differently.
  - A checkpoint or context saved in a template names the template's absolute paths.
  - Merging tests creates a longer test whose first failing assertion hides the later ones. This lowers diagnosis
    quality, but not what the tests prove.
  - A module-scoped scenario could create order dependence under `-p no:xdist`.
  - Collapsing a named edge case (the depth limit, a kill window, a crash) would weaken the suite.
- **Mitigations built into the plan:**
  - Stage-start templates are asked for only through function-scoped fixtures (`shared_template` from a function
    fixture, the pattern `flow_history_copy` already uses).
  - The builder sets its own `consult.DEFAULT_LEDGERS`, `HOME` and working paths to the template root with a
    `pytest.MonkeyPatch.context()`, so the template does not depend on which test triggered it.
  - The rebuilt context comes from the values the build returns (pickled), with `repo_dir` and `target_worktree`
    re-pointed at the copy and a fresh dispatcher.
  - Step 4's equivalence check compares a templated start against a fresh run of the same stages: equal refs (modulo
    ids), equal ledger rows (modulo ids and times) and equal context fields.
  - Shared scenarios are done as one test with all the assertions (the intent's second option), not as module-scoped
    fixtures. This removes order dependence by construction and keeps every run under the function-scoped guards.
  - Kill-window (`w1`/`w2`/`w3`), crash, regression and incident-named tests are never collapsed. Only their start state
    may come from a template, and only where they assert nothing about the stages the template replaces.
  - For the depth-limit collapse, the edge-case-named case (`[at-the-depth-limit]`) is the one that survives.

- **Hypothesis being tested:** A host and origin pair captured after the real Stages 1, 2 or 3 have run once, together

### Intent & Git Integration

- **Git branch:** the execution branch (two commits: the helper with its equivalence check, then the users)
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. New module `tests/flow/stage_templates.py`:
   - The function `stage_start_copy(tmp_path_factory, target, through, agents_spec)` returns the host, the origin and a
     rebuilt `FlowContext`. `through` is "intent", "plan" or "execute". `agents_spec` is a small frozen description of
     the `FakeRoleAgents` options that affect the stages being skipped: the class, `planner_records_decision`, the
     `BudgetRoleAgents` plans and the intent-data overrides.
   - The template name comes from `tests.flow_repo_templates.template_name` over (`through`, `agents_spec`), so equal
     requests share one build in the run, across xdist workers.
   - The build runs only when a function-scoped fixture or test asks for it (rule four). It copies the flow template
     (`_flow_repos_template`'s tree) into the template root.
   - Inside a `pytest.MonkeyPatch.context()`, the build points `HOME` and `consult.DEFAULT_LEDGERS` at the root's own
     host, so the template does not depend on the test that triggered it.

     under `stage4_halts_at_consensus()` where needed.

   - The build returns the context fields set by those stages as plain data: the intent, plan and execution branches,
     `intent_data`, and the stage results as their serialised form. Use the checkpoint serialiser that `save_checkpoint`
     and `load_checkpoint` already use, so no new format is invented.
   - Per test, the copy is made with `copy_template`, the context is rebuilt with `_dispatch_context` or
     `_budget_context` on the copy's host, and the saved fields are applied. `repo_dir` and `target_worktree` are
     re-pointed at the copy, and the test's own fresh dispatcher is attached, so dispatcher-call assertions only see the
     stages the test runs.

2. Clock: the P- and E- ids in a template carry its build time, which is seconds to minutes before the test. Before

   beyond "they succeeded", which another surviving test already proves (for example

   - `test_dispatch.py`: the Stage 3 tests that only run Stages 1 and 2 as set-up move to `through="plan"`:

     - agent failure;

   fraction of what the helper saves.
