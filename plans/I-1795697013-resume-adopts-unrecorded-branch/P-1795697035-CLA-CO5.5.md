## Plan Description & Strategy

**Current behaviour (verified by reading the code):**

- `ExecuteStage.salvage_partial` (`flow/stages/execute.py:241-257`) calls `salvage_for_resume` and then
  `_resumable_partial_branch`. That function only returns a branch whose latest summary row is a failure carrying
  `partial_head` (`flow/partial_head.py:failed_partial_head`).
- The executor container (`entrypoint/execution_workspace.py:resolve_partial_head`) checks the same
  `failed_partial_head` row on `refs/remotes/origin/<branch>` again, and only then resumes and adds `continuation_note`.
  So a branch with no row is ignored on both sides.
- `salvage_leftovers` only commits leftovers when non-engine-owned files are dirty. Its first status read excludes
  `executions/E-*.md`, and the commit always excludes the run's own notes file. A worktree whose only change is its
  notes file is therefore never salvaged. The executor's `checkout -b <exec> <start>`
  (`entrypoint/partial_resume.py:154`, `check=True`) then fails with git's opaque "would be overwritten" exit 1.
- `hold_unrecorded_executions` keeps a crashed run's unrecorded branch local and does not push it. So an unrecorded
  branch can be on origin (the case the intent names) or local only (the most likely result of a host crash).
  `publish_with_first_row` already handles the local-only case.

**Strategy:**

1. Add a new module `flow/unrecorded_branch_adoption.py`, at most 350 lines and expected to be about 150. It holds the
   read-only detection and diagnostics:
   - `find_unrecorded_branch(repo_dir, plan_branch, plan_prefix, existing)`. It returns an `UnrecordedBranch` (branch,
     exec id, tip sha, whether the tip is local only or ahead of origin, whether the worktree is checked out on it, and
     the commit count past the plan tip), or None.
   - Only the newest execution branch of the plan, by `E-<seq>`, is considered. The candidates are the origin snapshot
     plus local-only branches. The branch must carry no summary row for its id at either its origin ref or its local
     head. It must also have at least one commit past the plan tip, and a non-empty diff from the plan tip outside
     metadata paths (`changed_paths`).
   - If the newest branch has a row (success or failure), the function returns None, so today's behaviour holds exactly.
   - `checkout_blocking_paths(repo_dir, start_refs)` lists the files a checkout would refuse to overwrite: tracked dirty
     files (`git diff --name-only HEAD`) that also differ between HEAD and a start ref.
   - `blocking_checkout_error(paths, start)` turns that list into a readable message that names the files.
2. Hook it into `salvage_for_resume` in `flow/partial_salvage.py` (224 lines now, about 270 after, under the 400-line
   default budget). The call goes into this existing resume entry point, so `execute.py` does not change:
   - Detect first. If the worktree is on the unrecorded branch, run the existing salvage with the branch's own notes
     file included, using the same `partial work (interrupted)` label, so `_unrecorded_salvage_commit` still recognises
     it on a retry.
   - If nothing was left to salvage, record the adoption. Reuse `_salvage_row` and `_publish_partial`, with an
     origin-only path that appends the row directly and needs no push. The row is a superseding `failure` row with
     `failure_reason: "interrupted"`, `partial_head = tip` and `adopted_unrecorded: true`.
   - Refresh the snapshot so the adopted branch is never mistaken for the executor's new branch.
   - Set `context.execution_branch` to the adopted branch so the checkpoint follows it.
   - Finally, fail with the blocking file names if a tracked dirty file would still block the checkout.
3. `execute.py` stays at 430 lines. Its `_resumable_partial_branch` then finds the adopted branch through the new row
   and logs "continuing partial work from …". After dispatch, `adopt_execution_branch` discovers only the executor's new
   branch, because the adopted branch is now in the snapshot. It reads the summary row under the id in that branch name,
   which is the id the executor actually wrote.

## Step 2: Add `flow/unrecorded_branch_adoption.py` (detection and checkout-blocking diagnostics)

- **Sub‑intent recommendation:** NO

### Intent & Git Integration

- **Step Intent:** Detect the plan's newest execution branch when it has commits past the plan tip and no summary row.
  Compute which dirty files would block a checkout.
- **Git branch:** the plan's execution branch
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. Module docstring: explains the host-crash scenario, that only the newest execution branch is considered, and that a
   branch with any summary row is never touched.
2. Frozen dataclass `UnrecordedBranch` with these fields: `branch`, `execution_id`, `tip` (sha), `needs_publish` (true
   when the local head is missing from origin or strictly ahead of it), `checked_out` (true when the worktree HEAD is on
   this branch) and `commits_past_plan`.
3. `_execution_seq(branch)`: the same `/E-(\d+)-[^/]+/_$` ordering `_resumable_partial_branch` uses, defined locally
   because the one in `execute.py` must not move.
4. `_candidates(repo_dir, plan_prefix, existing)`: `existing` (the origin snapshot) plus
   `host_remote.new_local_child_branches(repo_dir, plan_prefix, "E", existing)` (local only). Sort by seq, highest
   first, and keep only the newest.
5. In `partial_head.py`, add a public helper `has_summary_row(repo_dir, ref, execution_id)` of about 6 lines, reusing
   `_read_ledger_rows` and `_latest_execution_summary`. The new module calls it for both `refs/remotes/origin/<branch>`
   (when present) and `refs/heads/<branch>` (when present). Any row means the branch is recorded, and the function
   returns None.
6. Pick the tip. Use the local head when it exists and is not behind origin (an `_is_ancestor_commit` check from
   `git_refs`); otherwise use the origin tip. If local and origin have diverged, return None and log nothing here; that
   is a manual case, and the caller logs "not adopted: diverged".
7. Find the plan tip with `_resolve_branch_ref(repo_dir, plan_branch)`. Count `rev-list --count <plan_ref>..<tip>` and
   require more than 0. Also require `git.changed_paths(repo_dir, plan_ref, tip)` to be non-empty; this is the shared
   empty-diff definition, so a branch with only notes or ledger commits is not adopted. Wrap the read in a try for
   `RuntimeError` and `TimeoutError`, and return None on failure.
8. `checked_out` comes from `git symbolic-ref --short -q HEAD` compared with the branch name.
9. `find_unrecorded_branch(repo_dir, plan_branch, plan_prefix, existing) -> UnrecordedBranch | None` wires steps 3 to 8
   together. Any git read that returns non-zero gives None, so a broken or mocked repository behaves exactly as today.
10. `checkout_blocking_paths(repo_dir, start_refs)`. Tracked dirty files come from `git diff --name-only HEAD` (staged
    and unstaged, tracked only). For each start ref that resolves, take the files from
    `git diff --name-only HEAD <ref>`. Return the sorted intersection. This is the case where git refuses a checkout
    with "would be overwritten".
11. `blocking_checkout_error(paths, start_label)` returns a message like
    `Execute stage failed: the mounted worktree has uncommitted changes that would be overwritten by checking out <start_label>: a.py, executions/E-….md; commit or discard them in the host worktree before resuming`.
    Paths are passed through `redact_agent_secrets` and the list is capped at 20 names plus "and N more".
12. Every function stays within the complexity limits (C901 ≤ 10, PLR0913 ≤ 5; group arguments into a tuple where
    needed, as `_publish_partial` does). Add docstrings and type hints, and no `# noqa`.
13. Imports only from `flow.git_refs`, `flow.host_remote`, `flow.partial_head`, `sandbox_executor.git` and
    `sandbox_executor.redaction`. It must not import `partial_salvage` (no cycle) or `stages.execute`.

### Strategy Rationale

**Assessment.** The intent is sound and worth doing. A host crash during Stage 3 currently throws away a whole
execution's commits. The fix is local to the resume path, and the system already has the right primitives:

- salvage commits with a recognisable label;
- superseding `failure` rows carrying `partial_head`;
- `publish_with_first_row` for branches that were never pushed;
- a continuation prompt on the executor side.

**The reframe.** It only moves where the hook lives:

- `execute.py` is exactly at its frozen 430-line budget.
- Existing tests patch `execute.salvage_for_resume` and `execute._resumable_partial_branch`, so changing those call
  sites would break "existing tests pass unchanged".
- Hooking detection into `salvage_for_resume` reaches the same resume path with zero lines changed in `execute.py`.
- Recording a standard failure row means the executor container, which is outside scope, needs no change.

**Design choices.**

- **Newest-only rule.** Only the plan's newest execution branch is considered for adoption. So a branch with any summary
  row behaves exactly as today, and an old abandoned branch is never revived over newer recorded work.
- **Snapshot refresh.** Refreshing the snapshot after adoption is what makes the second resume pick the executor's newly
  minted id instead of failing as ambiguous.

**Aggregation of the metrics.**

- **Entropy** is the sum of the step entropies: `0.3 + 1.5 + 1.8 + 1.2 + 0.5 = 5.3`.
- **Cost** is the sum of the step costs: `1.0 + 3.0 + 4.0 + 4.0 + 2.0 = 14.0`.
- **Success probability.** The naive product of the step probabilities is about 0.50
  (`0.97 * 0.88 * 0.80 * 0.82 * 0.90 = 0.50`). That understates it, because a failing step is retried within the same
  run and the failures are strongly correlated. All of them sit in Step 3. So the overall p_success is
  bottleneck-anchored on Step 3 (0.80) with a small discount for test and lint friction: 0.75.
- **Impact** is 70 at plan level. It is not the sum of the step impacts (95); it reflects how much one avoided full
  re-execution after a crash is worth.
- **Learning value** is 5.0, a qualitative judgement: moderate.
- **EV:** `EV = 0.75 * 70.0 + 0.5 * 5.0 - 0.3 * 5.3 - 14.0 = 52.50 + 2.50 - 1.59 - 14.00 = 39.41`.

**Bottleneck:** Step 3 (the side-effecting integration).

**Strong assumptions:**

- `push_branch` pushes the local head, so the origin-only adoption skips the push (verified in Step 1).
- The pipeline saves the checkpoint after a Stage 3 result, so setting `context.execution_branch` is enough for the
  checkpoint to follow. The plan does not call `save_checkpoint` mid-stage, to avoid writing the checkpoint path in
  tests.
