## Plan Description & Strategy

Add one top-level `concurrency` block to `.github/workflows/docker-build.yml`, placed between the top-level
`permissions` block and `jobs`, mirroring the position and style of `make.yml`, `test-unit.yml` and the other test
workflows. The group expression is
`${{ github.workflow }}-${{ github.event_name == 'pull_request' && github.head_ref || format('{0}-{1}', github.ref, github.sha) }}`
and `cancel-in-progress` is `${{ github.event_name == 'pull_request' }}`. Pull request runs therefore share one group
per head branch and a newer push cancels the older run; every `push` to `main` and every `workflow_dispatch` run gets a
group unique to its commit, so with cancel-in-progress false no main run is ever cancelled or evicted from the
single-pending slot. Nothing else in the file or repository changes. Verification is the three named test modules, then
the full suite once, then lint (prettier on YAML, module budgets untouched), then an observation on the live pull
request.

### Strategy Rationale

The intent is precise, scoped to one file, has strong precedent and positive EV, so it is accepted as is. A plain
`workflow-ref` group (as the siblings use) was rejected for this file because on `main` with cancel-in-progress false
GitHub keeps only one pending run per group and cancels older pending ones, which would silently drop main pushes;
keying non-pull-request runs by SHA avoids that. Including `github.workflow` in the group keeps Docker Build from
colliding with other workflows' groups.

Aggregation: overall `p_success_pred = 0.97 * 0.95 = 0.92`, rounded up slightly to 0.93 because Step 3 is not a
bottleneck and Step 2's main risk (unrelated flake) is recoverable by a single re-run. `entropy_pred` is the sum of step
entropy, `1.0 + 0.5 + 0.5 = 2.0`. `cost_pred` is the sum `2.0 + 1.5 + 0.5 = 4.0`. `impact_pred` is the intent-level
impact (40.0, dominated by Step 1). `learning_value_pred` is 2.0, taken from Step 3. Overall
`EV = 0.93 * 40.0 + 0.5 * 2.0 - 0.3 * 2.0 - 4.0 = 37.2 + 1.0 - 0.6 - 4.0 = 33.6`. The bottleneck is Step 1 (a typo in
the expression would break the workflow), guarded by Step 2.

Assumption: fork pull requests that share a head branch name (for example two forks both using `patch-1`) would share a
group and cancel each other. The intent prescribes `github.head_ref` and the repository's pull requests come from
in-repo `I-*` branches, so this is accepted rather than adding the pull request number.
