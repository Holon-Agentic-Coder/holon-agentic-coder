## Plan Description & Strategy

Two standalone, stdlib-only scripts under `scripts/` (run as `python -m scripts.<name>` from the repository root, the
same way `.github/actions/bookkeeping-gate` runs `scripts.ci_bookkeeping_gate`), each exposing small importable
functions plus a `main(argv) -> int`. Neither imports `sandbox_executor`, so the workflow needs no `uv sync`, and
neither writes any file.

Shared vocabulary (defined once in `scripts/check_ledger_stores.py` and imported by the diff check):
`LEDGER_DIR = "holon-knowledge/ledger"`, `LEDGER_KINDS = ("executions", "intents", "plans")`, canonical path
`holon-knowledge/ledger/<kind>.jsonl`, fragment path `holon-knowledge/ledger/pending/<kind>/<name>.jsonl`, and the
excluded knowledge folders `holon-knowledge/kb/failure_modes/` and `holon-knowledge/wisdom/`.

1. Store check (`scripts/check_ledger_stores.py`): list the repository files with
   `git ls-files -z --cached --others --exclude-standard` (tracked plus untracked-not-ignored, so `.venv` and caches
   never count, and a fresh uncommitted fourth store does), classify every path into canonical ledger, fragment, foreign
   store or not-a-store, and fail when any foreign store exists or the set of kinds is not exactly the three.
2. Diff check (`scripts/check_ledger_rows_append_only.py`): resolve `git merge-base BASE HEAD`, list the ledger files
   and fragments at that commit with `git ls-tree`, read each blob at the merge base and at the head with
   `git cat-file`, and require every base row (line, without its terminator) to be present at the same index on the head
   with identical bytes. A missing head row is `deleted`, a differing row that occurs elsewhere on the head is `moved`,
   otherwise `changed`. A fragment gone on the head is accepted only as a promotion (all its non-blank rows present in
   the head canonical file of its kind). Any git failure reading the base (unknown ref, no merge base, unreadable blob)
   exits 2: fail closed.
3. Workflow `.github/workflows/test-ledger-invariants.yml`: on `pull_request` (no base-branch filter, as
   `test_workflow_triggers.py` requires), full-history checkout, Python 3.13 via `astral-sh/setup-uv`, run both scripts;
   the base and head SHAs reach the shell through `env:` only, never interpolated into the script.
4. Tests: one hermetic temporary repository per case, built with plain `git init` under `tmp_path` with
   `GIT_CONFIG_GLOBAL`/`GIT_CONFIG_SYSTEM` pointed at `/dev/null` and a fixed identity, never touching the real
   checkout.

Every new module stays at or under 200 lines, has no docstrings and only `# why:` comments, and keeps functions within
the ruff complexity limits. `holon-config/hygiene/module_budgets.json` is not touched (the 400-line default already
covers 200-line modules).

- Module constants: `LEDGER_DIR`, `LEDGER_KINDS`, `PENDING_DIR = LEDGER_DIR + "/pending"`, `EXCLUDED_DIRS` (the

  fragment hits, sorted foreign paths.
- `store_problems(stores: LedgerStores) -> list[str]`: one message per foreign path (`fourth ledger-like store: <path>`)

  `Path(__file__) .resolve().parent.parent`); print the stores found and each problem to stderr; return 0 when no
  problems, 1 on problems, 2 when `git ls-files` fails (fail closed, message names the repository).
  `if __name__ == "__main__": raise SystemExit(main())`.

## Step 3: Add the append-only row diff check script

- **Sub‑intent recommendation:** NO
- **Reasoning:** The most logic-dense module (row comparison, promotion allowance, fail-closed git reads) but still

### Intent & Git Integration

- **Step Intent:** Provide `scripts/check_ledger_rows_append_only.py` that fails when a base row of any ledger file or
  fragment changed, moved or disappeared on the head, passes additions and new fragments, and fails closed when the base
  cannot be read.
- **Git branch:** same execution branch as Step 1
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

- Import `LEDGER_DIR`, `LEDGER_KINDS`, `canonical_path`, `fragment_dir` from `scripts.check_ledger_stores`.
- `class UnreadableBase(Exception)`; a `_git(repo, *args) -> bytes` helper running `git -C repo ...` capturing output
  and raising `UnreadableBase` with the command and stderr on a non-zero exit.
- `merge_base(repo, base, head) -> str`: `git merge-base base head`; a `# why:` comment records that rows added to the
  base branch after the branch point are not this pull request's edits, so the comparison starts at the merge base.
- `ledger_paths_at(repo, commit) -> list[str]`: `git ls-tree -r -z --name-only commit -- holon-knowledge/ledger`, kept
  when the path is a canonical ledger or a `.jsonl` file directly under `pending/<kind>/` for one of the three kinds. An
  empty list is valid (a base without ledgers has nothing to protect).
- `read_blob(repo, commit, path) -> bytes | None`: `git cat-file -e` decides existence on the head (`None` when absent);
  on the base side the caller uses a strict variant that raises `UnreadableBase`.
- `rows(data: bytes) -> list[bytes]`: `data.splitlines()` on `\n` only (split on `b"\n"`, dropping the final empty
  element), so a trailing newline added to an unterminated last line by promotion does not count as an edit; a `# why:`
  comment records that.
- `compare_rows(path, base_rows, head_rows) -> list[str]`: for each base index, missing head index gives
  `<path>:<n>: deleted`; a differing row gives `moved` when the base row occurs elsewhere in the head rows, otherwise
  `changed`. Cap the reported problems per file (for example 20, then a `... and N more` line) so a mass rewrite stays
  readable.
- `promoted(fragment_rows, head_canonical_rows) -> bool`: every non-blank fragment row occurs in the head canonical rows
  (a set lookup). A `# why:` comment cites `holon ledger promote`, which appends fragment rows verbatim and then deletes
  the fragment.
- `check_append_only(repo, base, head) -> list[str]`: resolve the merge base; for each base ledger path read base bytes
  (strict) and head bytes; when the head file is absent: a canonical file is `deleted`, a fragment passes only if
  `promoted` against the head canonical file of its kind, else `<path>: fragment removed`; otherwise extend with
  `compare_rows`. Head-only files are never inspected (new fragments pass by construction).
- `main(argv)`: argparse `--repo` (default repository root), `--base` and `--head` (required). Return 0 and print
  `ledger rows append-only: N files checked` on success; print each problem to stderr and return 1 on a violation; catch
  `UnreadableBase`, print it and return 2.
- Keep functions under `C901 <= 10`; at most 200 lines (target about 130); no docstrings; only `# why:` comments.
- Run it on this checkout: `uv run python -m scripts.check_ledger_rows_append_only --base origin/main --head HEAD` must
  exit 0 (the plan branch only adds this plan file and ledger rows in fragments).

### Strategy Rationale

The intent is well posed, cheap and directly protects the audit invariant, so it is accepted with three precisions
rather than reframed in substance. Planning surfaced two facts that a literal reading would get wrong: promotion deletes
fragments after copying their rows into the canonical file (so "a base fragment disappeared" must allow that case), and
the existing wiring test forces every pull-request workflow through the bookkeeping gate (which would skip exactly the
ledger-only pull requests this gate exists for). Comparing against the merge base avoids false positives on branches
that are behind `main`.

Aggregation: entropy is the sum of the step entropies, `1.0 + 0.8 + 1.5 + 1.0 + 1.2 + 0.5 = 6.0`. Cost is the sum of
step costs, `1.5 + 1.5 + 2.5 + 2.0 + 1.5 + 1.0 = 10.0`. Impact is a qualitative judgement for the whole gate (70.0, not
the sum of step impacts, since the steps only have value together). p_success is bounded by the bottleneck chain (Steps
1, 3, 5, 6); the product `0.95 * 0.88 * 0.90 * 0.92 = 0.69` is too pessimistic because failures in these steps are cheap
to fix within the same execution, so the overall value is set at 0.85, slightly below the weakest step (Step 3, 0.88).
Learning value 4.0 is the sum of the step values rounded up for the knowledge gained about promotion and workflow
guards. Overall `EV = 0.85 * 70.0 + 0.5 * 4.0 - 0.3 * 6.0 - 10.0 = 59.5 + 2.0 - 1.8 - 10.0 = 49.7`.

Strong assumptions: `git ls-files '*.jsonl'` today lists only the three ledgers and their fragments; the one-time
chronological sort (`scripts/normalise_ledgers.py`) is already on `main`, so no open pull request's merge base predates
it in a way that matters for new flows.
