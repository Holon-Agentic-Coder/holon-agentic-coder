### Strategy Rationale

Accepting the intent as-is and executing it as a single cohesive plan yields high EV (`66.55`) with low entropy (`5.0`,
well below the `15.0` budget). The root cause is that multi-line `HOLON_REPLAN_FEEDBACK` values fail `_fits_env_file` in
`launcher/env_files.py` and therefore fall into `passthrough_env` (`-e HOLON_REPLAN_FEEDBACK`); once target-merge or
replan feedback exceeds Linux `MAX_ARG_STRLEN` (`128 KiB`), both host `subprocess.run` and container `execve` fail with
`E2BIG`.

The strategy addresses both layers cleanly:

1. On the host flow side (`flow/stages/plan_support.py`), `replan_feedback_env` spills feedback exceeding a safe inline
   threshold (`32 KiB`) to a `0o600` temporary file referenced by `HOLON_REPLAN_FEEDBACK_FILE` and omits
   `HOLON_REPLAN_FEEDBACK` from `os.environ`, preventing host-side `E2BIG` while preserving all existing small-feedback
   unit tests.
2. On the container launcher side (`launcher/containers.py` and `launcher/env_files.py`), `ContainerLaunch` stages any
   `HOLON_REPLAN_FEEDBACK_FILE` or `HOLON_REPLAN_FEEDBACK` as a read-only mount (`/tmp/replan_feedback.txt:ro`),
   forwards only the short path in `HOLON_REPLAN_FEEDBACK_FILE` via `--env-file`, strips `HOLON_REPLAN_FEEDBACK` from
   the `docker` child environment, cleans up owned temp files in `_release()`, and validates all `-e` / forwarded env
   vars against the `128 KiB` Linux per-variable limit before invoking `docker`.
3. Inside the container (`entrypoint/planner.py` and `entrypoint/executor/run.py`), both entrypoints read feedback
   through a shared `read_replan_feedback` helper in `budgets.py` that prefers `HOLON_REPLAN_FEEDBACK_FILE` and falls
   back to `HOLON_REPLAN_FEEDBACK` only when unmounted/unset.
