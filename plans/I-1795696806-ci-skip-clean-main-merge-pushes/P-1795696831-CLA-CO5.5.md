### Strategy Rationale

**Assessment.** The measured waste is real and large: 11 mechanical main-merge pushes in one hour, each re-running all
seven workflows for 7 to 9 minutes. The pull request's own diff did not change and `main` already tested the merged-in
commit. The existing gate takes the 2-dot compare `before...head`, which for a merge push holds every file `main`
changed. It always answers `non-bookkeeping-change`, or `diff-too-large` once 300 files are reached, and the measured
merges were 500 files or more.

**Why the reframe.** Two facts found while reading the repository would push the literal intent's expected value close
to zero:

1. **The compare API cannot see the base side.** It lists at most 300 files (`COMPARE_FILE_CAP`), with no paging for
   files. The measured base-side deltas are 500 files or more, so any compare-based base-side file set is truncated, and
   every measured push would end in "truncated compare, run". Recursive git trees (one request per commit, a `truncated`
   flag at 100,000 entries) give the full set of paths and blob ids for the merge base B, the previous head P1, the
   merged-in base commit P2 and the new head M. The comparison is then exact and local:
   - PR changes = paths where B and P1 differ (mode, type or blob id).
   - Base changes = paths where B and P2 differ.
   - Clean merge = for every path in the union of the four trees, M holds exactly what a file-level three-way merge
     yields: P2's entry when P1 equals B, P1's entry when P2 equals B, either one when P1 equals P2, and otherwise a
     conflict, which runs.

   Goal point (3) asks that no file in the merge result differ from what git would produce from the two parents. This
   check is exactly that, at file level, and it is stricter than git, because a path changed on both sides never counts
   as clean.

2. **Bookkeeping paths collide on every flow pull request.** Each flow pull request writes `executions/E-*.md`,
   `plans/I-*/…` and `holon-knowledge/ledger/pending/{plans,intents,executions}/I-*.jsonl`. Every other merged pull
   request adds siblings in the same directories, so a strict parent-directory rule would answer "same directory" on
   every flow merge push. These paths cannot change a test result: that is the premise the existing `bookkeeping-only`
   rule is built on. They still go through the clean-merge check, and the hygiene job, which is never skipped, checks
   their format. Leaving them out of point (4) keeps the safety property and makes the rule usable.

The bidirectional import check is the conservative reading of "any doubt runs". A pull-request module that imports a
module the base side changed was tested only against the old version of that module.

**Aggregation.** Total entropy is the sum of the steps: `0.5 + 1.5 + 1.0 + 3.0 + 1.0 + 2.0 + 1.0 = 10.0`. Total cost is
the sum: `1.0 + 3.0 + 2.0 + 6.0 + 1.5 + 4.0 + 2.0 = 19.5`. The overall probability of success is a qualitative
judgement, `0.72`, set by the bottleneck, Step 4. The steps are strongly correlated, and the failures that are likely
(complexity limits, the 400-line budget, a URL-count assertion in a frozen test) can be fixed inside the same execution,
so the plain product of the step values (about `0.39`) understates the real chance. Impact `70` is the about 90 minutes
of CI wall time saved per hour of queue, discounted for the cases where the rule will still answer "run". Learning value
`6.0` covers the first tree-based merge verification and the first measurement of how often a main merge is provably
independent.

`EV = P(success) * Impact + mu * LearningValue - lambda * Delta_S_intent - Cost`

`EV = 0.72 * 70.0 + 0.5 * 6.0 - 0.3 * 10.0 - 19.5 = 50.4 + 3.0 - 3.0 - 19.5 = 30.9`

## Plan Description & Strategy

Add a merge-push route to the bookkeeping gate, modelled on the existing `ci_main_push_gate.py`.

- `ci_bookkeeping_api.py` gains the REST readers the route needs.
- The new `scripts/ci_merge_push_gate.py` owns the rules and the `decide_merge_push` entry point. Its rule names are
  prefixed `merge-push-`, and its one skip rule is `merge-push-clean-main-merge`.
- `decide()` in `ci_bookkeeping_gate.py` hands over to that route only when the diff of a `synchronize` push decided
  `non-bookkeeping-change` or `diff-too-large`.
- The route answers `None` ("not my case, keep the original decision") for anything that is provably not a two-parent
  merge. Otherwise it answers a `Decision` that is printed on the gate's one output line, as today.

The route checks its rules in this order and returns at the first one that fails. The order is cheapest first, so most
merge pushes that cannot skip spend only one to five requests.

1. **Job eligibility, no request.** The job is not `hygiene` and the workflow is not `test-hygiene.yml`. Otherwise
   `merge-push-hygiene-never-skipped`.
2. **Merge shape, one request.** `git/commits/{head}` has exactly two parents and the first is `before`.
   - One parent, or a read error, returns `None`: the original decision, exactly as today.
   - Three or more parents is `merge-push-not-two-parents`.
   - A first parent that is not `before` is `merge-push-first-parent-not-previous-head`.
   - The event must name a base branch (new `GateContext.base_ref`). Otherwise `merge-push-incomplete-event`.
3. **Previous head evidence, existing chain.** `find_real_success` with target `before`. Its chain rule decides for a
   run. When the real success is on an older commit, `diff_rule(real_sha, before)` must be bookkeeping-only, and the
   existing rule names apply.
4. **Merged-in base evidence.** The newest `push` run of the same workflow on `base_ref` with `head_sha` equal to the
   second parent holds the same job (`match_job`) and classifies `REAL_SUCCESS`. Otherwise one of:
   `merge-push-base-run-missing`, `merge-push-base-run-not-finished`, `merge-push-base-run-not-successful`, or
   `merge-push-base-run-unverified` (gate-skipped or without a marker).
5. **Merge base, one compare.** `compare(P1...P2)` names a merge base B and the trees of B and P1. Otherwise
   `merge-push-no-merge-base`.
6. **Trees, four requests.** Recursive trees of B, P1, P2 and M. A `truncated` tree is `merge-push-tree-truncated`.
7. **Clean merge.** The file-level three-way rule holds on every path. Otherwise `merge-push-conflict-resolution`, and
   the detail names the path.
8. **Disjoint changes.** The non-bookkeeping PR changes and base changes share no path and no parent directory.
   Otherwise `merge-push-overlapping-change`, and the detail names the path or directory.
9. **No relation in apps/ or scripts/.** For each top-level directory, `apps` or `scripts`, where both sides changed
   non-bookkeeping files: every changed file there is a `.py` regular file that parses under Python 3.9 grammar, and no
   file of one side imports a module of the other side or is its test (the name `test_<stem>.py` paired with
   `<stem>.py`). The failing rules are:
   - `merge-push-related-change`
   - `merge-push-unanalysable-change`
   - `merge-push-scan-too-large`
10. **Skip.** `merge-push-clean-main-merge`, with the detail
    `"{n} base-side paths merged from {P2[:12]}; real successes on {before[:12]} and {P2[:12]}"`.

Every exception from step 3 on is `merge-push-api-error` with the class name and the HTTP status, never the text.

   evidence only" principle, the bookkeeping exclusion and its reason, the hygiene exclusion, the bidirectional import

2. **Constants:**

3. **`_merge_parents(context, client)`:** reads `commit_ref(head)` inside a `try` that returns `None` on any exception.

4. **`_previous_head_check`:** builds `JobQuery(... target_sha=before)`, calls `find_real_success`, and returns

   `ci_bookkeeping_gate.diff_rule(client, real_sha, before)`. To avoid an import cycle, pass `diff_rule` in as a
   callable argument from `decide()`, or move a minimal compare check here with `compare` and the `is_bookkeeping_path`

5. **`_base_run_check`:** calls `list_push_runs(workflow, base_ref, P2)` and takes the newest `MAX_BASE_RUNS` runs that
   hold the job (`match_job`). Missing, not completed, not success, and gate-skipped or unverified each map to their
   `merge-push-base-run-*` rule. Only `REAL_SUCCESS` passes.
6. **`_trees`:** calls `merge_base(P1, P2)`, then `commit_ref(P2)` for P2's tree (B's and P1's trees come from the
   compare), then `tree_entries` for B, P1, P2 and M (M's tree comes from step 3's `CommitRef`). Any `truncated` is
   `merge-push-tree-truncated`.
7. **`expected_entry(b, p1, p2)`:** a pure function with three states: P2 when P1 equals B, P1 when P2 equals B, P1 when
   P1 equals P2, otherwise a conflict sentinel.
8. **`conflict_path(b, p1, p2, m)`:** iterates the sorted union of paths and returns the first path where the expected
   entry is the conflict sentinel or differs from M. An absent entry counts as the value `None`.
9. **`changed_paths(old, new)`:** the sorted paths whose entry differs.
10. **`overlap(pr, base)`:** both inputs are filtered with `not is_bookkeeping_path` (imported from
    `ci_bookkeeping_gate`; to avoid a cycle, either the predicate is passed in or `BOOKKEEPING_ROOTS` and the predicate
    stay in the gate module and are passed as a callable). It returns the first shared path, else the first shared
    `posixpath.dirname`, else `None`.
11. **Import scan, `_relation_check`:**
    - For each root in `RELATED_ROOTS` where both filtered sets hold paths, collect the changed paths under that root
      from both sides.
    - A path that is not `.py`, has mode `120000` (symlink), or has type `commit` (submodule) is
      `merge-push-unanalysable-change`.
    - Read each `.py` file's content from M's tree entry: first the local file in the working directory, accepted only
      when its git blob id equals the entry's blob id; else `blob_bytes`, counting toward `MAX_BLOB_READS` (above it,
      `merge-push-scan-too-large`).
    - A file deleted in M is read from its last side tree, or is treated as unanalysable.
    - Parse with `ast.parse(source)` (no `feature_version`; see the guardrails below). A `SyntaxError` or `ValueError`
      is unanalysable.
    - Collect the imported dotted names: `import a.b` gives `a.b`; `from a.b import c` gives `a.b` and `a.b.c`; relative
      imports resolve against the file's own package path.
12. **`module_names(path)`:** the dotted names a path is importable as.
    - The components after a `src` component (for example `sandbox_executor.flow.engine`).
    - For `scripts/…`, the repository-root dotted path `scripts.x`.
    - For `…/tests/x.py`, `tests.x`.
    - `__init__.py` maps to the package name.
13. **Relation:** file F of one side is related to file G of the other side when any import name of F equals a module
    name of G, or is a dotted prefix of it, or has it as a dotted prefix. The two files are also related when either is
    `test_<stem>.py` and the other is `<stem>.py`. Check both directions. The first relation found is
    `merge-push-related-change`, and the detail names the two paths.
14. **`decide_merge_push`:**
    - Hygiene check, with no request.
    - `_merge_parents`: `None` passes through as `None`.
    - Empty `base_ref` is `merge-push-incomplete-event`.
    - Then, inside one `try` that maps any exception to `merge-push-api-error`, the type name and the HTTP status:
      `_previous_head_check`, `_base_run_check`, `_trees`, `conflict_path`, `overlap`, `_relation_check`.
    - Finally the skip `Decision`.
15. **Complexity:** each helper stays at or under `C901` 10, `PLR0912` 12, at most 5 arguments, and at most 50
    statements, with no `noqa`. Use the table-driven `checks` pattern from `event_rule`, and keep the top-level function
