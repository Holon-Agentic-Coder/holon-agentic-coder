### Step 4: Admission under the lock with the oldest-waiter rule, recorded in the checkpoint

- New `flow/admission_order.py` (kept apart so `admission_state.py` imports nothing from discovery): `waiter_key`,
  `blocker_is_clear` and `older_ready_waiter`. An entry naming this flow's own lineage is never clear, so a waiter that
  waits on this flow is not deferred to (otherwise a flow re-checking with its own pull request open would defer to a
  waiter it blocks, a new cycle).
- `admission.py`: `check_admission` takes the lock (outside a dry run), runs `_decide` (touch set, discovery, waiters,
  conflicts, then the ordering rule when nothing overlaps) and `record_admission`, which writes `blocked` (overlap
  refusal), `admitted` or `admitted` with `override` into the checkpoint at its default path; other refusals record
  nothing. A lock timeout or a write failure refuses fail-closed. `AdmissionDecision.blocked_by` carries the entries;
  the Stage 3 payload and the ledger row are unchanged. An override whose ledger row cannot be written restores the
  previous admission state. A dry run neither locks nor writes; `stages/execute.py` needed no change.
- Outside the touch set: `tests/flow/stages/test_decomposition.py` classifies every `FlowContext` field for child
  contexts, so the new `admission` field is classified as reset (a child runs its own Stage 3).

### Step 5: Hermetic tests for every acceptance criterion

- `tests/flow/test_admission.py`: a refusal records `blocked` with `blocked_since` and `blocked_by` naming the pull
  request (`number`, `branch`, `files`) and the local flow (`plan_branch`, `worktree`, `files`); an admission records
  `admitted`; `--allow-overlap` records `admitted` with `override: true`; `blocked_since` kept and `blocked_by` replaced
  across two refusals (injected clock); non-overlap refusals record nothing; a lock that cannot be taken fails closed; a
  dry run writes nothing; an override whose ledger row fails restores the previous state.
- New `tests/flow/test_admission_order.py`: two overlapping flows refused by one pull request; after it closes, the
  newer retrying first is blocked by the older (`local_flow`), the older is admitted, the newer stays blocked by it; the
  reverse retry order; unit cases for `blocker_is_clear` and `older_ready_waiter`.
- `tests/flow/test_admission_lock.py`: the race. Two threads released by a `threading.Barrier` run `check_admission` for
  overlapping flows in two worktrees of one repository; a fake `gh` waits (bounded, 0.5 s) for a second concurrent
  discovery. Exactly one is admitted and the other is blocked by it. Sanity check (not committed): with the lock
  replaced by `contextlib.nullcontext` the test fails (`most_inside == 2`), so it does exercise the lock.
- Hypothesis outcome (Step 4 learning target): the clear-blocker test can be decided from recorded `blocked_by` plus
  current discovery, but one refinement was needed. A field-less checkpoint at execute (a flow that has not yet run
  admission) still counts as in flight, so the first refused flow can record the newer flow as a `local_flow` blocker.
  Treating every own-lineage entry as "never clear" then let the newer flow jump ahead. The rule is now: an entry naming
  this flow itself is clear unless this flow is admitted; own-lineage pull requests and other own-lineage flows are
  never clear. The ordering test caught this.
- Flakiness check: the race and ordering test files each ran 3 times with no failure.
