Implements plan `P-1795425523-CLA-CO5.5`: the shared `sync_with_target` routine with a SHA-keyed `git merge-tree` probe,

## Steps Executed

### Step 1: SHA-keyed `git merge-tree` target probe

- Added `flow/target_probe.py`: `TargetProbe`, `TargetProbeError`, `probe_target`, `merge_tree_conflicts` and the strict
  NUL parser `parse_merge_tree_paths` (tree OID, then paths up to the first empty field; messages ignored).
- Verified against git `2.47.3`: `--write-tree --name-only -z` exits `1` on conflict and lists exact paths, including a
  path with spaces; no fallback to `--messages` parsing was needed.
- Added `build_flow_repos` and `commit_on` fixture helpers to `tests/ledger_conflict_repos.py` and 7 tests in
  `tests/flow/test_target_probe.py` (unchanged target runs no `merge-tree`, cache hit, clean, conflicting, parser
  ignores the messages section, broken remote and unresolvable target raise).
- Probe timing, one serial run per scenario with `time.perf_counter` on the local fixtures (bare `origin` on disk, so
  the fetch is a local transport): unchanged `4.1 ms`, changed-clean `5.8 ms`, changed-conflicting `5.7 ms`. A bare
  `merge_tree_conflicts(HEAD, main)` on this repository took `12.1 ms`. All far under the `2 s` threshold, so sibling
  child 3 can probe at every turn boundary; a networked fetch will dominate the real cost.

### Step 2: Mechanical conflict classifier and resolvers

- Added `flow/conflict_classes.py` (`ConflictClass`, `ConflictSides`, `read_sides`, `unmerged_stages`, `classify_sides`,
  `classify_merge_conflicts`), reading index stages 1/2/3 during an in-progress merge.
- Added `flow/conflict_classes_lists.py` (`appended_list_union`): the `ast` check and rebuild for `APPENDED_LIST`
  (single-name list or dict literal, every other top-level statement identical, both sides base-plus-appended; the
  result is re-parsed and compared with the target before use). Split out so each module stays well under 200 lines.
- Added `flow/conflict_classes_resolve.py` (`resolve_path`, `resolve_mechanical`, `MechanicalResolution`): `LEDGER`
  writes the target ledger as an untouched prefix plus the branch-only rows via `ledger_reconcile._append_only_union`
  and checks the prefix, markers and every branch row; `KB_TIMESTAMP_ONLY` keeps `--theirs`; `DELETE_VS_TOUCH` runs
  `git rm`; any failed check restores the conflict with `git checkout -m` and the path becomes `CODE`.
- Deviation: the new classifier is named `classify_merge_conflicts`, because the package already exports
  `classify_conflicts` from `stage_conflict_resolution` and the export guard forbids duplicate public names.
  `ledger_reconcile.py` needed no new helper.
- 11 tests in `tests/flow/test_conflict_classes.py`, one positive and one negative per class on real conflicting merges,
  plus list-layout and removed-entry cases. No agent exists at this layer; the "never invoked" assertion is made at the
  routine level in Step 3.

### Step 3: `sync_with_target` and its single ledger row

- Added `flow/target_sync.py` (`sync_with_target`), `flow/target_sync_result.py` (`SyncBoundary`, `SyncRequest`,
  `SyncResult`, `CodeResolution`, `CodeResolver`, `fail_closed_code_resolver`), `flow/target_sync_merge.py`
  (`merge_target`, `abort_merge`, `merge_in_progress`, `unmerged_paths`, `merge_verification_error`) and
  `flow/target_sync_record.py` (`append_sync_row`, `sync_row`, `superseded_sync_conflict`).
- A `SyncRequest` dataclass carries the arguments, keeping `sync_with_target` within `PLR0913 <= 5`.
- Deviation: the merge runs `git merge --no-ff --no-commit <target SHA>` instead of `--no-edit`, so the `merged` row is
  appended and staged before the routine commits the merge itself; the row is therefore part of the pushed merge commit
  as planned. The merge uses the probed SHA, so `MERGE_HEAD` is exactly the probed target.
- Deviation: the row uses `category: code` with `action: target_sync` and `labels: [target_sync, <boundary>]`, because
  `ledger.rows.VALID_CATEGORIES` has no `git` category and `ledger/rows.py` is outside the touch set. Extra keys
  (`boundary`, `target_sha`, `conflicted_paths`, `resolutions`, `resolver_tier`, `attempts`, `test_result`,
  `supersedes`) are kept with `append_action_record(..., preserve_shape=True)`.
- `supersedes` names the latest `sync_conflict` summary row of the execution as `<execution_id>@r<ledger_revision>`
  (summary rows carry no row id).
- Pushes use `host_remote.push_commit(worktree, <merge SHA>, branch)`: `push_commit` only accepts a full object id or a
  `refs/heads/` ref, so `HEAD` from the plan is passed resolved.
- 9 tests in `tests/flow/test_target_sync.py`: unchanged, deferred at `TURN`, merged and pushed with two parents,
  ledger-only conflict with the resolver never called, default resolver blocks with no `MERGE_HEAD` and nothing pushed,
  injected resolver merges with its tier, resolver exception aborts cleanly, push failure keeps the local merge with one
  row, `supersedes`; a `run_git` spy shows no `rebase`, `--force` or `+` refspec push, and the module budget file hash
  is unchanged.

### Step 4: Adopt an in-progress merge on resume

- Added `flow/target_sync_resume.py` (`adopt_merge_in_progress`, `MergeAdoption`). It takes a `SyncRequest` (not the
  plan's `(worktree, target_branch, code_resolver)`) because finishing the merge also records the row and pushes. A
  `MERGE_HEAD` not reachable from the fetched `origin/<target>` is `refused` and left untouched; an older target SHA is
  aborted for a redo; the current target SHA is finished through the new `target_sync_merge.complete_merge`, which
  shares the resolve, verify, commit and push path with `merge_target` (refactored into `_complete` and `_guarded`). An
  unfinishable adopted merge is aborted without a row; the redo through `sync_with_target` records it.
- `flow/resume_guard.py`: `resume_merge_error` runs from `_resume_context_error` for resumed runs only, adopts the merge
  in `context.target_worktree` on the checked-out branch, reports without adopting on a dry run, and returns an error
  only when a merge is still in progress afterwards. `pipeline.py` is untouched.
- 5 tests in `tests/flow/test_target_sync_resume.py` and 3 added to `tests/flow/test_resume_guard.py` (adopt before the
  guard passes, dry run leaves the merge, a Stage 1 run never adopts).

### Step 5: `check_and_resolve_stage_conflicts` as a thin wrapper over the conflict classes

- `flow/stage_conflicts.py`: the word-scraping `_merge_tree_conflict_paths` and `_conflict_line_paths` are gone; the
  upstream probe calls `target_probe.merge_tree_conflicts` (structured `--name-only -z`, no fetch in the container).
  Signature and return keys are unchanged; `resolved_paths` (path and class) is added. The error says "code conflicts"
  only when every unresolved path is `CODE`, else keeps "merge conflicts".
- `flow/stage_conflict_resolution.py`: `ConflictKind` keeps its members and mirrors the new `ConflictClass` values;
  `classify_conflicts(detection, repo_dir="")` classifies unmerged non-ledger paths with `conflict_classes`, while
  probed-only paths stay `CODE` and probed ledgers on a non-`HEAD` branch stay `DEFERRED_LEDGER`. Ledgers keep the
  existing unstaged pure-append resolution; the other mechanical classes go through `conflict_classes_resolve`.
- `flow/lazy_exports.py` and `flow/__init__.py`: every new public name is registered (the export guard requires all
  public definitions), including `resume_merge_error`.
- `tests/flow/test_stage_conflicts.py`: the merge-tree probe test now feeds NUL output through `target_probe.run_git`,
  the old word-parser test is replaced by a failed-probe test, the code-conflict match is updated, and a KB
  timestamp-only unmerged file is resolved by the wrapper. `tests/test_ledger_fast_conflict.py`,
  `tests/test_pre_push_sync_conflict.py` and `tests/flow/test_package_exports.py` needed no edits.
