## Plan Description & Strategy

The review stage shares one host worktree (the flow worktree) between the host flow engine and the `review-loop` role
container that mounts it. The host engine needs that worktree on the execution branch: it appends review ledger rows
there, and `_checkout_execution_branch` / `fast_forward_local_branch` assume the branch is checked out. Inside the
container, `_validate_mounted_workspace` (`entrypoint/review_loop.py`) refuses a detached HEAD for a branch target. That
refusal is the "Stage 4 resolver refused to run" in the incident.

Findings from reading the code (the planning baseline):

1. `flow/stages/review.py`, `flow/review/*.py`, `flow/stage_conflicts.py`, `flow/git_refs.py` and `resolver_evidence.py`
   run no `git checkout` / `git switch` of a bare commit in the flow worktree. Diff summary, mergeability
   (`merge-tree`), commit lookup (`rev-parse`) and ledger appends (a temporary `worktree add --detach`) are read-only or
   work in separate directories.
2. Reviewer turns (`review_ensemble.run_reviewer` → `supervise_authoring_turn(..., cwd=request.repo_dir)`) and the
   resolver turn (`entrypoint/review_loop._run_resolver_agent`, `run_turn(cmd, cwd=repo_dir)`) run coding agents with
   shell access **inside the mounted worktree**. Their prompts include the head SHA. A reviewer that checks out the
   reviewed commit "to look at it" leaves HEAD detached at exactly the execution branch tip. This matches the incident
   signature (detached at the tip, only the review container mounted it).
3. `flow/calibrate_sync.restore_starting_branch` runs `checkout --detach <sha>` on every pipeline exit when the first
   stage that recorded the start saw a detached HEAD. This is a secondary suspect for resumed runs.
4. `git_flow.provision_reviewer_worktree` (an ephemeral `flow-<slug>-rev<i>` sibling worktree) exists but nothing calls
   it, and its sibling path is outside the container mount. Moving reviewer turns into it would need mount changes,
   which is out of scope and riskier, so the plan guards the HEAD state instead.

Strategy:

- **A shared HEAD guard module** (`sandbox_executor/worktree_head.py`, outside both `flow/` and `entrypoint/` so both
  can import it without a new entrypoint→flow edge). It reads the HEAD state, re-attaches a HEAD detached exactly at
  `refs/heads/<branch>` with `git symbolic-ref HEAD refs/heads/<branch>`, and refuses any other detached HEAD with a
  clear message. `symbolic-ref` only rewrites `.git/HEAD`, so the index and the working tree (uncommitted ledger rows
  included) are untouched by construction.
- **Container side:** `_validate_mounted_workspace` re-attaches instead of refusing when HEAD is detached at the target
  branch tip. HEAD is checked before and after each reviewer ensemble pass and resolver turn. A turn that left HEAD
  detached is logged by name (this records the detaching step from now on) and repaired. The reviewer and resolver
  prompts gain one rule: read other commits through `git show` / `git diff` / `git worktree add` into `tmp/`, and never
  run `git checkout`, `git switch`, `git reset --hard` or `gh pr checkout` in the workspace.
- **Host side:** `run_review_stage` restores the execution branch on every exit (approval, failure, exception) with
  `try/finally`. It re-attaches when detached at the tip; otherwise it runs a plain non-forcing
  `git checkout <execution_branch>`, which carries non-conflicting changes and refuses conflicting ones, and warns on
  refusal. `_checkout_execution_branch` reuses the same re-attach. `record_starting_branch` treats a HEAD detached at
  the execution tip as the execution branch, so the pipeline exit never re-detaches it.
- **Tests:** hermetic, real-git tmp repos and the existing `review_fakes.py` seams, no network or containers.

## Step 2: Add the shared HEAD guard module `worktree_head.py`

- **Sub‑intent recommendation:** NO
- **Reasoning:** A small, pure helper module of about 100 lines with a narrow git surface. It is reusable by the host
  stage and the container entrypoint, but too small to justify its own branch and evaluation.
- **Step Type:** IMPLEMENTATION
- **Exploration level:** EXPLOIT

### Intent & Git Integration

- **Step Intent:** One owner for "is HEAD on the branch, detached at its tip, or detached elsewhere", and for the safe
  re-attach.
- **Git branch:** the execution branch of this plan
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. Create `apps/sandbox-executor/src/sandbox_executor/worktree_head.py` at package top level, next to `git.py` and
   `git_flow.py`, so that both `flow/stages/review.py` and `entrypoint/review_loop.py` import it and no new
   entrypoint→flow edge appears. It imports only `sandbox_executor.git.run_git` and `redaction.redact_agent_secrets`.
2. Define a frozen dataclass `HeadState` with fields `branch: str | None` (from `git symbolic-ref --short -q HEAD`),
   `sha: str` (from `git rev-parse --verify HEAD^{commit}`) and `branch_tip: str | None` (from
   `git rev-parse --verify --quiet refs/heads/<branch>^{commit}`). Add properties `on_branch`, `detached_at_tip` and
   `detached_elsewhere`. Every git call takes an injectable `run` parameter (default `run_git`), the same seam style as
   `record_starting_branch(context, run)`, so callers whose tests replace their runner never spawn real git.
3. `read_head_state(repo_dir, branch, run=None) -> HeadState`.
4. `reattach_branch(repo_dir, branch, run=None) -> ReattachOutcome`. `ReattachOutcome` is a small enum or dataclass:
   `ON_BRANCH`, `REATTACHED`, `REFUSED` with a `message`.
   - Already on `branch`: return `ON_BRANCH`.
   - Detached and `sha == branch_tip`: run
     `git symbolic-ref -m "holon: re-attach <branch> at its tip" HEAD refs/heads/<branch>` and return `REATTACHED`.
     `symbolic-ref` only rewrites `HEAD`; the index and the working tree, and so the uncommitted ledger rows, are
     untouched. Never use `checkout -f`, `reset`, `stash` or `switch --discard-changes`.
   - Detached elsewhere, on another branch, local branch missing, or a failed git call: return `REFUSED` with a clear
     message. Example: "the worktree HEAD is detached at <sha12>, not at the tip <tip12> of '<branch>'; refusing to
     re-attach, because that would change the checked-out tree. Check out '<branch>' by hand (uncommitted changes are
     kept by a plain 'git checkout <branch>') and resume." Redact stderr with `redact_agent_secrets`.
5. `head_guard(repo_dir, branch, step_label, log, run=None)`: a context manager that reads the state before the block
   and, in a `finally`, after it. If the block left HEAD detached or on another branch, it logs a warning naming
   `step_label` and the SHA, which is the detection record for goal 1, then calls `reattach_branch`. On `REFUSED` it
   logs the message and never raises over an in-flight exception. A body that already failed keeps its own exception.
6. Keep every function under the ruff limits (`C901 <= 10`, `PLR0913 <= 5`) with no `noqa`, and give each a docstring
   that names its side effects (`holon-config/world/ruleset.md` §2).

### Dependencies & Criticality

- **Depends on:** NONE (Step 1 informs only the log wording)
- **Is Bottleneck:** YES (Steps 3-5 call it), but p_success is high because the git semantics are well known

### Safety & Constraint Considerations

- **Relevant rules:** `docs/safety.md` Invariant 1 (Git discipline); `holon-config/world/constraints.md` §3 (ledger rows

- **Potential failure modes for this step:** re-attaching a HEAD whose tree differs from the branch tip, which would

- **Guardrails and early‑abort checks:** re-attach only on exact SHA equality with `refs/heads/<branch>`, never with a

- **Discard:** if `symbolic-ref` turns out to behave differently on linked worktrees (per-worktree HEAD) in the test

### Strategy Rationale

The intent is accepted with a light reframe of goal 1. The code contains no deterministic review-stage
`git checkout <sha>` in the shared worktree, so "replace the offending command with `git show` / `git diff`" has no
single target. The highest-EV response guards the HEAD state at three points that cover every suspect:

- validation inside the container (goal 3);
- around each agent turn that runs in the mount (goal 1: detection plus repair, and the prompt rule as prevention);
- the host stage's exit (goal 2), with `record_starting_branch` closing the pipeline-exit re-detach path.

The fix holds whichever suspect Step 1 confirms. Moving reviewer turns into the existing but unused
`provision_reviewer_worktree` siblings was rejected for now: the sibling directory is outside the container mount, so it
would need new mounts and container changes. That means higher entropy and cost for the same protection. It can be
proposed as a follow-up intent if Step 1 shows agents keep mutating the mount.

Aggregation: `entropy_pred` is the sum of the step entropies, `0.5 + 1.5 + 2.0 + 2.0 + 1.5 + 1.0 = 8.5`. `cost_pred` is
the sum of the step costs, `2.0 + 2.5 + 3.5 + 3.0 + 2.0 + 1.0 = 14.0`. `p_success_pred` 0.80 is set just under the
weakest bottleneck steps (Steps 3 and 4 at 0.82); they are correlated (same helper, same fakes), so it is not their raw
product (`0.92 * 0.82 * 0.82 * 0.85 * 0.88 = 0.46`, which double-counts the shared risk). Step 1 is not a bottleneck.
`impact_pred` 80 reflects that the defect stops the unattended flow and needs manual repair. `learning_value_pred` 5.5
is weighted towards Step 1's root-cause finding. Overall:
`EV = 0.80 * 80.0 + 0.5 * 5.5 - 0.3 * 8.5 - 14.0 = 64.00 + 2.75 - 2.55 - 14.0 = 50.20`.

Strong assumptions: `git symbolic-ref HEAD refs/heads/<b>` on a linked worktree rewrites only that worktree's HEAD,
which is standard git behaviour and is verified in Step 5. The incident's detach happened at the exact branch tip, as
the intent states; otherwise re-attach correctly refuses and only the clearer message helps.
