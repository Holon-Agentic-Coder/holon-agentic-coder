## Plan Description & Strategy

The test-failure record exists (`entrypoint/test_failure_record.py`: `TestFailureEvidence`, `record_test_failure`,
`failure_signature`, `_row`) and is wired for Stage 3, the Stage 4 resolver and the review-loop local tests. Stage 5
(`flow/stages/calibrate.py` → `check_final_head_ci` → `reverify_and_report` in `flow/github/ci_reverify.py`) computes a
RED verdict from check names and step names only; no test ids, excerpts or signature reach the ledger. Separately,
`knowledge/wisdom.py` only promotes from the SQLite action index by context fingerprint, never by the
`failure_signature` that test-failure rows already carry.

Strategy:

1. Add `STAGE_5 = "stage_5"` and, in `ci_reverify.py`, a small Stage 5 recorder: when the reverified verdict is RED and
   a final head was pushed, look up the failed-check log text for that head, strip the `gh` log-line prefix, parse ids
   and excerpts with the existing helpers, and append one `test_failure` row with `stage: stage_5` through
   `record_test_failure`. No ids parsed → no row. The lookup is a keyword argument of `reverify_and_report` with a
   `gh`-backed default, so `calibrate.py` keeps its call unchanged and tests inject a real captured output.
2. In `wisdom.py`, add `promote_repeated_failure_signatures(ledger_path, kb_dir, dry_run)`: read the executions ledger
   through `ledger.merged.read_merged_rows` (canonical plus pending fragments), group `test_failure` rows by
   `failure_signature`, and for each signature seen in two or more distinct `run_id`s write one `failure_mode` entry
   through `persist_kb_fact` with id `KB-failure-<16-hex signature>` (distinct length from the 8-hex fingerprint ids, so
   no collision with existing files). The failing ids and classification go in `payload`, because `build_kb_envelope`
   keeps no `evidence` keys (`KB_STABLE_EVIDENCE_KEYS = ()`). An existing file means "already promoted", which makes
   repeated runs idempotent. `promote_pending_candidates` calls it with the executions ledger derived from `kb_dir`, so
   Stage 5's existing promote step picks it up.
3. Two new test files cover the acceptance criteria; then the affected suites, the full suite once and lint run in the
   foreground.

The work fits one execution branch (entropy 8.0 against a budget of 15.0), so there is no sub-intent list.
