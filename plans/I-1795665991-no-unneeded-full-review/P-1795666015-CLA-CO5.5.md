## Plan Description & Strategy

Today one fused verdict decides everything. Inside `run_review_loop` (`flow/review/loop.py`),
`decide_returned_consensus(reviewers, ..., ci_green, blockers)` folds the reviewer verdict and the CI result into a
single `ConsensusVerdict`. So when all three reviewers approve but a check fails, the iteration is CHANGES_REQUESTED,
the resolver gets a `FIND-CI` finding, and the next iteration re-runs all three reviewers on the full PR diff. Stage 5
behaves the same way: `review_restart._decide` calls `withdraw_consensus` on any FAILED merged-head check, whether the
failure was a timing gate, a runner failure or a real test failure, and Stage 4 restarts at iteration 1 with a full
review.

The plan separates two facts that are currently one: **the diff is approved** and **the pipeline is green on this
head**. It then makes every re-review proportional to what changed:

1. **Reviewable diff identity (child 1).** The approval fingerprint uses the flow's shared bookkeeping definition
   (`BOOKKEEPING_PATH_PREFIXES` in `flow/github/ci_final_head.py`, matching `scripts/ci_bookkeeping_gate.py`) instead of
   its private exclusion list, under a new `pf2` version. A pre-iteration target merge that is mechanical (clean, or
   ledger/knowledge-base append-only) and leaves the fingerprint unchanged keeps the approval. A resolved code conflict
   always records the resolved paths for a scoped review, even when no scope was recorded before. Today
   `_apply_turn_sync` only adds to an existing scope.
2. **Two independent gates (child 2).** A new `flow/review/approval_gates.py` stores `consensus_on_diff` (approved,
   fingerprint, reviewed head, iteration, review mode) and `pipeline_green_on_head` (head SHA, state, run ids) as
   separate records in a new `context.review_state` dict (one field, checkpointed). "Approved" is their conjunction,
   checked by one pure function. Losing the pipeline gate never clears the diff gate. Losing the diff gate (the
   fingerprint changed) never forges a pipeline result.
3. **Scoped delta review (child 3).** A new `flow/review/delta_review.py` builds the review request for a follow-up
   pass. It contains the diff from the last reviewed head to the current head (bookkeeping excluded), the full
   post-change contents of each modified file (bounded per file), and the findings the delta addresses (id, severity,
   path, summary). It falls back to a full review when the delta exceeds `HOLON_SCOPED_REVIEW_MAX_LINES` (default 400
   changed lines, resolved in `budgets.py`), when the last reviewed head is unknown or not an ancestor, or when the
   previous pass was not approved by all reviewers on the diff.
4. **CI failure routing after approval (child 4).** A new `flow/review/ci_failure_routing.py` classifies a failed
   pipeline into `noise` or `defect`. Noise means a timing-gate-only failure (`_timing_gate_only`), a runner or
   infrastructure failure (no failed test step: setup or teardown step names, `startup_failure`, `timed_out` with no
   test output), or a cancelled run. A defect is anything else. Noise triggers a bounded rerun of the failed runs (one
   rerun per run id per head, reusing `CancelledReruns` / `gh run rerun --failed`) while `consensus_on_diff` is kept. A
   defect, or noise that fails again on rerun, dispatches the resolver with the CI finding (including
   `timing_gate_finding` for a repeated timing failure, which keeps the existing "the fix is in the slowest tests"
   rule). The resulting fix delta then gets a scoped delta review from child 3 instead of a full ensemble pass. This
   applies both inside the Stage 4 loop and in Stage 5 (`review_restart._decide` routes instead of withdrawing).
   Withdrawal stays only for a changed fingerprint or a delta review that rejects.
5. **Accounting (child 5).** A new `flow/review/review_accounting.py` counts `full_reviews`, `scoped_reviews`,
   `pipeline_runs`, `pipeline_reruns` and `non_defect_churn` per reason (`target_merge`, `bookkeeping`, `ci_noise`) in
   `context.review_state`. They are rendered in the flow summary (`review_summary_lines`) and in a "Review churn"
   section of the calibration report (`calibration.py`).

The root branch then runs one integration verification (Step 6) across all five children.

**Size discipline.** `flow/review/loop.py` is at 950 of its frozen 952-line budget, `records.py` 316/316,
`sync_points.py` 200/200, `conflict_gate.py` 200/200 and `context.py` 273/280. Every child that touches one of these
first moves a cohesive block out into a new focused module, so the touched file ends no longer than it started. For
example, child 2 extracts the "3. CI status inspection" branch of the loop into `flow/review/ci_inspection.py`. No child
edits `holon-config/hygiene/module_budgets.json`, and no child adds a `# noqa`.

**Execution order.** The children are serial, because each builds on the previous one: 1 then 2 then 3 then 4 then 5.
Each runs its affected tests with `uv run pytest <paths>`, then `uv run task test` once and `uv run task lint`, all in
the foreground.

## Step 3: Add scoped delta review with a size-limited fallback to full review

- **Sub‑intent recommendation:** STRONGLY_YES
- **Reasoning:** This is the exploratory part of the plan: a new review request shape whose effect on reviewer
  strictness is unknown. Isolating it lets calibration measure the outcome on its own, and keeps it revertable.
- **Step Type:** EXPLORATION
- **Exploration level:** BALANCED

- **Hypothesis being tested:** A follow-up review that shows reviewers only the delta since the last reviewed head, with
  full-file context and the addressed findings, catches the same defects in that delta as a full review. It also stops
  reviewers raising new nits on previously approved, unchanged code.
- **Learning target:** The ratio of scoped to full reviews per flow, the number of findings raised outside the delta
  (should be zero), and whether any scoped approval is later contradicted by a full review or CI defect.
- **Maximum acceptable cost for this learning:** 1.5 times `cost_pred` (13.5); beyond that, ship the fallback-only path
  (always full review) with the request builder dormant.

### Intent & Git Integration

- **Step Intent:** When a diff gate exists and the head moved by a resolver fix or a resolved conflict, review only the
  delta (with context) instead of the whole PR diff.
- **Git branch:** `I-1795665991-no-unneeded-full-review--3-scoped-delta-review/_`
- **Sub‑intent:** NEW

### Implementation Details (No code blocks, only logic/steps)

1. Add `HOLON_SCOPED_REVIEW_MAX_LINES` (default 400; 0 disables scoped review) and `HOLON_SCOPED_REVIEW_CONTEXT_BYTES`
   (default 40000 per file) resolvers to `budgets.py`, and document both in `docs/environment_variables.md`. The
   environment-reference test (`test_environment_reference.py`) enforces the documentation.
2. Add `flow/review/delta_review.py`:
   - `decide_review_mode(context, repo_dir, head)` returns `full` or `scoped` with a reason. It is `scoped` only when
     the `DiffGate` (Step 2) is approved, its `reviewed_head` is an ancestor of `head`, the reviewable delta (Step 1
     pathspecs) is non-empty and at or below the limit, and no reviewer on the gate returned CRITICAL. Otherwise it is
     `full`, and an unknown state always gives `full`.
   - `build_delta_request(...)` returns a `ReviewRequest` whose `base_ref` is the last reviewed head, whose diff is
     `reviewed_head..head` over the reviewable pathspecs, and whose body appends the full post-change content of each
     modified file (bounded, with truncation marked) and the addressed findings (from `carried_findings` and the
     iteration's resolver input, rendered as id, severity, path and summary).
3. In `review_request.py`, add an optional `context_files` and `addressed_findings` rendering helper used by
   `build_review_request` (keyword-only, default None, so full reviews are unchanged).
4. In `ensemble.py` (`_ensemble_iteration` and `_dispatch_review_ensemble`), take a `ReviewMode` and pass
   `--review-base=<sha>` and `--review-mode=scoped` to the container path. Check the entrypoint parsing in
   `entrypoint/review_loop.py`: if it lacks these flags, the sandboxed path stays full-review in this child and the gap
   is recorded (do not widen the touch set into entrypoints).
5. In `loop.py`, call `decide_review_mode` before the ensemble (net zero lines: it replaces the inline
   `review_scope_paths` kwargs block in `ensemble.py`, not in the loop) and store the mode on the `DiffGate`. Path
   scoping from Step 1 (`review_scope_paths`) becomes an input to the delta builder: resolved conflict paths force those
   files into the context set.
6. A scoped pass that approves re-records the `DiffGate` with the new fingerprint and `reviewed_head = head`. A scoped
   pass that requests changes behaves like today's CHANGES_REQUESTED, and the next pass is scoped again against the new
   head while within the limit.
7. Tests: new `tests/flow/review/test_delta_review.py` (mode decision table; limit fallback; non-ancestor fallback;
   request carries the delta, the context files and the addressed findings; bookkeeping excluded). Extend
   `tests/flow/review/test_ensemble.py` and `tests/test_review_ensemble.py` (full request unchanged when the mode is
   full).
8. Run `uv run pytest` on the affected paths, then `uv run task test` and `uv run task lint` once, in the foreground.

### Strategy Rationale

**Intent assessment.** The intent is accepted, but split into five serial child intents plus a root verification. A
single plan would touch about 25 modules across Stage 4 and Stage 5, including four modules already at their frozen line
budget. Its predicted entropy (23.5) is well above the 15.0 budget. Each child fits the budget on its own: 3.0 to 5.5.

**Order and bottleneck.** The bottleneck is Step 2, the split of the fused verdict inside `run_review_loop`. It is a
refactor of the largest, budget-capped and complexity-suppressed function in the flow, and Steps 3-5 build on its gate
records. Step 1 comes first because the gate records need a stable, bookkeeping-aware identity for "the reviewable
change". Step 3 comes before Step 4 so that a CI defect's fix delta can get a scoped review; if Step 3 is discarded,
Step 4 still works and falls back to a full review. Step 5 is last because it counts events the earlier children create.

**Aggregation.**

- `entropy_pred` is the sum of the step entropies: `4.0 + 5.0 + 5.0 + 5.5 + 3.0 + 1.0 = 23.5`.
- `cost_pred` is the sum of the step costs: `7 + 9 + 9 + 10 + 5 + 2 = 42`.
- `impact_pred` (90) is a qualitative judgement. Steps 2-4 deliver the intent's saving (no full-ensemble re-runs from
  pipeline noise and smaller follow-up reviews). The step impacts sum to 110, discounted because they overlap.
- `learning_value_pred` (8) is the sum of the step learning values (10.5), discounted because Steps 1 and 6 overlap with
  the others.
- `p_success_pred` (0.55) is a qualitative judgement. The strict product of the step probabilities (about 0.17)
  understates success, because children are retried through the full pipeline and Steps 3 and 4 have discard paths that
  still satisfy most acceptance criteria. It is anchored on the bottleneck Step 2 (0.70) and the riskiest Step 4 (0.62),
  and matches the comparable decomposed intent I-1795425253 (0.55).

**Strong assumptions.**

- `BOOKKEEPING_PATH_PREFIXES` in `ci_final_head.py` is the right definition of "bookkeeping" and matches
  `scripts/ci_bookkeeping_gate.py`.
- GitHub step-level failure detail (already used by `describe_failure`) is enough to tell infra failures from test
  failures.
- `entrypoint/review_loop.py` can accept a review base, or the sandboxed path keeps full review until a follow-up intent
  adds it.

**Reconciled conflict with a prior decision.** `ci_timing_finding.py` says a timing-gate failure is fixed in the slowest
tests, "never a rerun". The intent asks to rerun timing-gate failures as noise. The plan allows exactly one rerun per
run id per head and keeps the slowest-tests resolver finding for a repeat failure. This honours both rules and is
visible in the accounting.
