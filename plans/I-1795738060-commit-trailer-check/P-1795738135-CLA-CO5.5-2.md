Facts found during planning that shape the plan:

1. **Wiring test coupling.** `apps/sandbox-executor/tests/test_ci_bookkeeping_wiring.py` checks
   `{workflows containing "\n  pull_request:"} == set(WIRING)`. Adding `test-commit-trailers.yml` with a normal
   `on:\n  pull_request:` block fails that test. Three options were compared:
   - (a) wire the new workflow into the bookkeeping gate (gate step, timing gate, marker step, `actions: read`, plus a
     `WIRING` row). Rejected: a bookkeeping-only push is still made of commits whose messages can carry trailers, so
     skipping the check on such pushes would leave a hole, and the job would gain about 5 steps of coupling.
   - (b) write the trigger as `on: [pull_request]` so the substring scan misses it. Rejected: it gets around a guard
     without telling anyone, and a reviewer would rightly flag it.
   - (c) **chosen:** add a named set `GATE_FREE_WORKFLOWS = {"test-commit-trailers.yml"}` with a `# why:` comment, and
     compare against `set(WIRING) | GATE_FREE_WORKFLOWS`. It is one explicit, reviewable line, and the intent's ban
     covers existing workflows and the README, not tests.

### Implementation Details (No code blocks, only logic/steps)

1. Shebang `#!/usr/bin/env python3`; no module docstring, no comments except `# why:`; only stdlib imports (`argparse`,
   `re`, `subprocess`, `sys`, `collections.abc`, `pathlib`).
2. Constant `ATTRIBUTION_PREFIXES` is a tuple of the lowercase prefixes `co-authored-by`, `co-developed-by`,
   `generated-by`, `assisted-by`, `generated with [claude code`. Constant `ROBOT_EMOJI` is `🤖`, with a `# why:` comment
   saying Claude Code writes its footer as `🤖 Generated with [Claude Code](...)`.
3. `is_comment_line(line)` is true when the raw line starts with `#` (no stripping, per the intent).
4. `is_attribution_line(line)`: strip leading whitespace, then remove one optional leading `ROBOT_EMOJI` plus the
   whitespace after it, lowercase the rest, and check `startswith(ATTRIBUTION_PREFIXES)`.
5. `find_attribution_lines(message: str) -> list[str]` returns the original lines (right-stripped of the newline) for
   which `not is_comment_line(line) and is_attribution_line(line)`, in order.
6. `commit_messages(revision_range: str) -> list[tuple[str, str]]` runs `git log --format=%h%x1f%B%x1e <range>` with
   `check=True, capture_output=True, text=True`, splits records on `\x1e` and fields on `\x1f`, and returns pairs of
   short sha and message. Short sha comes from `%h`, so it matches `git rev-parse --short` in the same repo.
   `--no-show-signature` is not needed. The range is passed as one argv item, never through a shell.
7. `offences_in_file(path) -> list[tuple[str, str]]` gives pairs of the path and each offending line;
   `offences_in_range(range) -> list[tuple[str, str]]` gives pairs of the short sha and each offending line.
8. `report(offences) -> int` prints each as `<where>: <line>` to `stderr`, plus a final summary line naming the rule
   (for example `attribution trailers are not allowed in commit messages`) when any exist. It returns 1 if there are any
   offences, else 0.
9. `parse_args(argv)` sets up a mutually exclusive, required group: `--message-file PATH` or `--range RANGE`.
   `main(argv: Sequence[str] | None = None) -> int` sends each mode to its offences function and calls `report`. A git
   failure in `--range` mode (bad range) prints git's stderr and returns 2, so the CI job never passes when git fails.
   End with the `if __name__ == "__main__": sys.exit(main())` guard.
10. Keep every function within `C901 <= 10`, `PLR0913 <= 5`; full type annotations; ruff format.
