- **Potential violations or edge cases:**
  - Converting a reason-carrying comment to `# why:` counts as an added comment line; it must start with `# why:` and
    state a reason, not a description, or the lint gate fails.
  - Renaming a private helper or constant that another module or test imports (e.g. `_approved_post_gate`,
    `_posting_failure_context` style underscore names are imported across modules) would break callers.
  - Trailing field comments on dataclasses (`PostFacts`, `PostDecision`) carry semantic definitions; dropping them loses
    meaning unless the meaning moves into the name, and renaming a field changes a name used by other modules.
  - Removing a docstring that is a class's or function's only body statement leaves an empty body (syntax error).
  - Log, error and `reason` string literals (e.g. `_HALTED`, `_FAILED_VERDICT` in `posting.py`) must stay
    byte-identical.
- **Mitigations built into the plan:**
  - Rename only module-private locals or constants after a repository-wide grep proves no other module or test uses the
    name; never rename dataclass fields, public functions, or anything imported elsewhere. Where a field comment states
    a reason, keep it as `# why:`; where it only restates the name, delete it.
  - Replace a sole-statement docstring with `pass` only if the body would otherwise be empty (expected: none).
  - Diff review: every changed line is either a removed docstring/comment, an added `# why:` line, or a rename proven
    local; string literals are untouched (checked by grepping the diff for changed quoted strings).
  - Affected tests first, then lint, then the full suite once.
- **Residual risk accepted (and why):** Small loss of narrative context from module docstrings (e.g. the posting policy
  summary in `posting.py`); accepted because the intent explicitly requires it, and the reason-bearing parts survive as
  `# why:` comments.
