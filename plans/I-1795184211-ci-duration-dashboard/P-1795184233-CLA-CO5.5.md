## Plan Description & Strategy

The intent adds an observability tool next to the existing CI timing gate. Nothing in the host flow engine changes. The
design reuses what the repository already has. It splits by responsibility so that every new module stays under the
200-line default. Every boundary that touches the network is injectable, so the acceptance tests stay hermetic.

**Module layout (all standard library only, like `scripts/ci_timing_gate.py`, so the workflow runs on the runner's own
`python3` without `uv sync`):**

- `scripts/ci_durations.py`: the CLI entry point (`argparse`, `main(argv, opener, clock)`), orchestration, the JSON data
  file writer and the markdown job-summary writer. Target: about 150 lines.
- `scripts/ci_durations_collect.py`: GitHub REST collection and normalisation into a frozen `JobDuration` dataclass. It
  reuses `build_request` and `default_opener` from `scripts.ci_timing_gate`, which keeps the token in an unredirected
  `Authorization` header. Target: at most 190 lines.
- `scripts/ci_durations_stats.py`: the rolling-median baseline, the slowest-versus-baseline ranking, and the timing-gate
  ceiling lookup, read from the committed workflow files. Target: at most 180 lines.
- `scripts/ci_durations_html.py`: rendering of the self-contained HTML report (inline CSS plus inline SVG built on the
  server side, no external assets, no JavaScript needed). Target: at most 200 lines. If it grows past that, move the SVG
  chart builder into `scripts/ci_durations_svg.py`.

The workflow runs the tool as `python3 -m scripts.ci_durations` from the repository root, so the sibling modules import
as `scripts.ci_durations_*`. This is the same import path the tests use (pytest `pythonpath = ["."]`, and `scripts` is
already a namespace package for `scripts.ci_timing_gate`). It avoids a `sys.path` hack.

**Data definitions (pinned and tested):**

- `duration_seconds = completed_at - started_at` for the job. `queue_seconds = started_at - created_at` for the job,
  clamped at 0. Jobs still running (`completed_at` is null) are dropped. Skipped jobs (conclusion `skipped`) are
  dropped. Cancelled jobs are kept and marked.
- Re-run marker: `run_attempt > 1` on the job. Jobs are fetched with `runs/{id}/jobs?filter=all&per_page=100`, so
  earlier attempts appear too. The latest attempt is not silently the only one.
- PR number: the first entry of the run's `pull_requests` list whose `base.repo` matches. If the list is empty (a PR
  from a fork, or a push), `pr_number` is null and the point is labelled by branch.
- Ref class: `main` when `event == "push"` and `head_branch == "main"`. Otherwise `pr` when there is a PR number or the
  event is `pull_request`. Otherwise `other` (dispatch or schedule).
- Runner OS: `labels[0]` of the job (for example `ubuntu-latest`). The fallback is the `(...)` suffix of the matrix job
  name, then `runner_name`, then `unknown`.
- Links: `run_url = job.html_url` (falling back to `run.html_url`), `commit_url = {server}/{repo}/commit/{head_sha}`,
  `pr_url = {server}/{repo}/pull/{n}` when a PR exists.
- Rolling median: for each `main` point of a (workflow, job, OS) series, ordered by `started_at`, the median of the
  previous `window` successful `main` durations (default window 5, the same as the gate's `--runs 5`). The value is null
  while fewer than `window` exist. The current point is excluded, which matches the gate's semantics.
- Ceiling: taken from the workflow file named by the run's `path`. It is the `--ceiling N` argument of a
  `scripts/ci_timing_gate.py` command in that job's block, or the `max-seconds` input of a
  `./.github/actions/ci-timing-gate` `phase: check` step (default 300 when the input is omitted). If neither is found,
  the ceiling is null ("where defined"). The job block is identified by the job key or its `name:`. Matrix suffixes are
  stripped from the API job name before matching.
- Collection window: `runs?created=>=YYYY-MM-DD&per_page=100&page=N`, with N days defaulting to 30. Pagination stops at
  an empty page or at `--max-runs` (default 500, which keeps `GITHUB_TOKEN` far below its 1000 requests/hour). The
  `ci-durations.yml` runs themselves are excluded. If the API's 1000-result search cap or `--max-runs` truncates the
  window, the report and the summary print a `::warning::`.

**Outputs:** `ci-durations/ci-durations.json` (a schema version, the generation time, the window, and one row per job
point with every collected field plus `baseline_median` and `ceiling`) and `ci-durations/ci-durations.html` (one section
per workflow / job / runner OS, each with an SVG time chart). The chart shows `main` points and PR-head points as
distinct marker shapes and colours, the rolling-median line, a dashed ceiling line, and a stacked queue/run bar strip.
Failures are drawn as hollow red markers and re-runs as a ring. Every point is wrapped in an `<a href>` to its run and
carries a `<title>` tooltip, and a table under each chart lists every point with run, commit and PR links. The step
summary lists the 10 jobs whose latest `main` duration is furthest above their rolling median, plus the window, the run
count and any truncation warning.

**Real data only:** the script has no sample or demo mode. Fakes exist only in the test module. When the token is
missing, the script exits with an error instead of rendering an empty or synthetic report.

**Strategy:** Steps 2 to 4 are pure functions tested first, so their correctness is fixed before the CLI and the
workflow wrap them. The workflow and the documentation come last, then the full lint/test gate runs once. Everything
fits one execution branch (predicted entropy 8.6, below the 15.0 budget), so no sub-intent list is used.

### Implementation Details (No code blocks, only logic/steps)

1. Define a frozen `JobDuration` dataclass with these fields: workflow name, workflow path, job name, runner OS, run id,

2. `parse_time(text)` parses the ISO-8601 `Z` timestamps into an aware UTC `datetime`. `seconds_between(a, b)` clamps at
   0, so clock skew between the queue and start stamps never yields a negative queue time.
3. `runner_os(job)` follows the order fixed in the strategy: `labels[0]`, then the matrix suffix of `name`, then

5. `normalise_job(run, job, repo, server)` returns a `JobDuration`, or None for jobs that are in progress, never

   empty page or reaches `max_runs`. It skips runs whose `path` ends with `ci-durations.yml`, skips runs whose
   `status != completed`, and returns `(runs, truncated)`. `truncated` is true when `total_count` exceeds what was read.
7. `list_jobs(repo, run_id, token, opener)` pages `runs/{id}/jobs?filter=all&per_page=100`.
8. `collect(repo, days, token, opener, now, max_runs)` returns `(rows, warnings)`. A failure from `FETCH_ERRORS` on a
   single run's jobs becomes a warning naming the run id and does not abort the report. A failure listing the runs
   aborts with a clear error (no fabricated data).
9. Import `build_request`, `default_opener` and `FETCH_ERRORS` from `scripts.ci_timing_gate`. Do not copy them.

## Step 3: Add `scripts/ci_durations_stats.py`: rolling median, ceiling lookup, slowest-versus-baseline ranking

- **Sub‑intent recommendation:** NO

- **Step Type:** IMPLEMENTATION

- **Step Intent:** Compute the per-series baseline and ceilings, and rank the regressions for the summary.
- **Git branch:** the single execution branch
- **Sub‑intent:** NONE

### Implementation Details (No code blocks, only logic/steps)

1. `series_key(row)` returns `(workflow_name, job_key, runner_os)`. `group_series(rows)` returns a dict of lists, each
   sorted by `started_at`.
2. `rolling_medians(rows, window=5)`: for each row, return the `statistics.median` of the durations of the previous
   `window` rows of the same series that are `main` with conclusion `success`. The current row is excluded. The result
   is None until `window` such rows exist. PR rows get the baseline in force at their start time, so the PR points
   compare against the same line. Use the gate's `rolling_median` from `scripts.ci_timing_gate` for the median itself,
   if its contract matches (median of a sequence, None when empty). Otherwise use `statistics.median`.
3. `load_ceilings(workflows_dir)`: an indentation-aware line scan of each workflow file's `jobs:` block. It records, per
   (workflow path, job key or job `name:` with the matrix expression stripped), the integer after `--ceiling`, or the
   `max-seconds:` value under a step that uses `./.github/actions/ci-timing-gate` with `phase: check` (300 when
   omitted). `ceiling_for(row, ceilings)` returns an int or None.
4. `slowest_vs_baseline(rows, medians, limit=10)` takes the latest `main` row per series that has a baseline, computes
   `ratio = duration / median` and `delta = duration - median`, sorts by delta descending, and returns typed
   `Regression` tuples.
5. Annotate each row (in a new dict, or with `dataclasses.replace` onto an extended view) with `baseline_median` and
   `ceiling`, for the JSON and the HTML.
