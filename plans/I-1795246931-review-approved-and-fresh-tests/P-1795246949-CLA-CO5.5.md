### Implementation Details (No code blocks, only logic/steps)

1. Create `flow/review/head_test_evidence.py`, a pure module with no subprocess calls. It holds:
   - The evidence source constants `stage_3`, `ci_head`, `review_local` and `resolver_evidence`. Keep the existing
     `TEST_SOURCE_*` names in `local_tests.py` as aliases.
   - A frozen dataclass `HeadTestEvidence`, with fields `rate`, `failed`, `source`, `head_sha` and `detail`.
   - A function `choose_evidence(...)`. Its inputs are the CI probe dict, the Stage 3 `(rate, failed)`, the Stage 3

     returns which source to use, applying these rules in order:
     1. If the current head is in the resolver-evidence set, use `resolver_evidence`: passing, not failed.

        nothing is pending, use `ci_head`: rate 1.0, not failed.
     3. If Stage 3 recorded a passing rate and no failure, and the current head equals the Stage 3 head, use `stage_3`.
     4. Otherwise (Stage 3 failed, or recorded nothing, or the head moved), use `review_local`, which means "measure
        now".

     Keep each function at or below ruff's C901 limit of 10 by splitting the rules into small predicates.

### Strategy Rationale

The intent is accepted as is. It is two defects that share one outcome: an approved, green PR must be reported as
approved and must be able to close its review loop and reach calibration.

**Why one plan and no sub-intents.** The two parts touch mostly separate modules. Splitting them would double the
pipeline cost (two reviews, two calibrations, and a combined PR) and would gain little isolation. The summed entropy,
9.6, is well under the 15.0 budget.

**Design choices.**

- Add a status instead of renaming one. Keeping `HALTED_FOR_HUMAN` as a valid parsed member means:
  - old checkpoints and ledger rows load unchanged;
  - the dry-run path keeps its correct halt meaning;
  - fewer existing tests have to change.
- Move the enum into a new module. This is forced by `flow/context.py` being exactly at its frozen 280-line limit.

**How the overall metrics were derived.**

| metric              | derivation                                                                                    |
| ------------------- | --------------------------------------------------------------------------------------------- |
| p_success_pred      | Bottleneck (Step 3, 0.78) with a small correlated discount for the other steps, giving 0.74 ¹ |
| entropy_pred        | Sum of the steps: `2.0 + 2.2 + 3.0 + 1.4 + 1.0 = 9.6`                                         |
| cost_pred           | Sum of the steps: `3.0 + 3.5 + 5.0 + 2.0 + 0.5 = 14.0`                                        |
| impact_pred         | 82, judged qualitatively ²                                                                    |
| learning_value_pred | 4.0, a qualitative blend dominated by Step 3's new evidence rule                              |
| ev_pred             | `EV = 0.74 * 82.0 + 0.5 * 4.0 - 0.3 * 9.6 - 14.0 = 60.68 + 2.00 - 2.88 - 14.0 = 45.80`        |

¹ The steps share one author, one branch and the same test harness, so their failures are correlated. The naive product,
about 0.46, would understate p.

² Unblocking consensus and Stage 5 calibration for every PR whose Stage 3 tests failed once is high value for the
pipeline's core loop. Correct reporting adds trust and readability.

**Strong assumptions.**

- `gh pr view --json headRefOid` is available wherever `gh pr checks` is. It is the same tool, and when the head cannot
  be read the gate falls back to a local re-run.
- The Stage 3 head can be pinned at gate construction.
